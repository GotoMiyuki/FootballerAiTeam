## 1. 任务摘要与执行顺序

C 负责用户回到旧任务时应该发生什么，以及下一次决策应该记住哪些有来源的信息。恢复执行、阅读历史、解释旧报告和重新评估分别实现，不用一个“继续会话”入口混合处理。

**未指定子任务时先核对实施记录；C1 和 E1.1 已完成，建议按 E1.2 → C2.1 推进。** C2 的行动/反馈依赖明确事件，不能从聊天猜测。不在一轮中重做执行图、所有会话存储和长期记忆。

E1.1 已提供有来源建议与独立 created/superseded/withdrawn 事件查询，见 [E1.1 实施记录](completed/E_E1.1_建议来源与适用性.md)。C2 消费时需核验建议当前来源/适用性；created 不代表用户采纳。选择/执行事件待 E1.2，C1.2 的建议/评估引用解析仍待 E2.2 接通。

| 子任务 | 交付目标 | 前置条件 |
| --- | --- | --- |
| C1.1（已完成） | 明确历史查看、解释、暂停续跑的入口与任务身份 | 当前 A/B 契约 |
| C1.2（已完成） | 创建有关联的新评估任务，冻结最新输入 | C1.1；A 只读快照、B3 |
| C1.3（已完成） | CLI 持久化暂停恢复与历史入口 | C1.1；复用已有 SQLite checkpoint 能力 |
| C2.1 | 保存有来源的长期记忆与更正关系 | C1.2；E1 的建议/行动事件契约已确定 |
| C2.2 | 按生涯、分支、相关性和版本检索并注入任务 | C2.1、B3；E 记录可提供样本 |

C1 可先于实际游戏接入开展。C2.1 的目标/偏好可以先实现，但行动与反馈必须消费 E 的明确记录，不能临时从聊天摘要猜测。C2.2 的真实闭环验收需要 D/E 数据；替身验证不计为真实生涯闭环。

实施前读取适用 AGENTS.md、最新源码和已合并接口。保留已有 A/B 修改。当前预设档案属于测试样本，可重建；无需修复历史样本污染，实际数据与任务记录不能被初始化为 demo。

## 3. 任务身份和最小接口

### 3.1 用户操作对应行为

| 操作 | Mission/thread 身份 | 使用的数据 |
| --- | --- | --- |
| 查看历史 | 读取原任务，不执行图 | 原报告、原快照与原审查范围 |
| 解释旧报告 | 原 Mission 的独立解释消息，不重开成果 | 原任务材料；不能偷偷读新状态作新建议 |
| 补充缺失信息 | 原 Mission、原 checkpoint 续跑 | 原快照，加明确补充的任务输入 |
| 批准生成报告 | 原 Mission 静态暂停续跑 | 原专业结果；不是能力更新或正文审核 |
| 根据新比赛/新约束重新评估 | 新 Mission、独立 checkpoint，关联原任务 | 提交时最新快照与选定相关历史 |
| 从失败任务重试 | 新 Mission，记录 retry 来源 | 明确选择的当前输入；不伪称原执行已恢复 |

服务重启后的 BLOCKED 可按已有 checkpoint 恢复；运行中崩溃、线程取消和任意节点重放仍按 G 处理。C 不承诺恢复缺少 checkpoint 的历史执行。

### 3.2 后续任务应用接口（C 拥有，E 消费）

建议定义一个普通 Python 应用请求与对应 API 适配，字段名可调整：

| 字段 | 要求 |
| --- | --- |
| 操作 | explain / resume / reevaluate / retry；新建任务与执行续跑分开 |
| 来源关联 | parent_mission_id、reason；E 可附 recommendation_id / assessment_id |
| 数据身份 | `PlayerContext`；默认与原任务相同，切换生涯须明确新建普通任务 |
| 输入策略 | explain/resume 使用原快照；reevaluate 使用 latest，提交时冻结 |
| 用户要求 | 新目标/约束及有来源的补充，不复制模型隐藏状态 |
| 历史引用 | 原报告/有效结果版本、选定记忆或反馈记录 id；不是整份 checkpoint 拼接 |
| 请求身份 | 持久化 request_id，用于同一后续创建请求重试；同 id 不同内容拒绝 |

将来源关联、上下文、输入快照引用及必要快照内容存入任务存储，不能只放进 prompt 或 `player_snapshots` 内存缓存。任务创建与同一数据库中的创建请求去重应一起提交；读取玩家快照不需要跨数据库事务。

explain 不改变旧 Mission 的 COMPLETED、审查和报告内容。解释失败作为该消息操作失败，不将旧报告撤回，也不生成新建议兜底。reevaluate 返回新 mission_id，界面切换后仍可查看来源任务。

现有 followup 可保留兼容：BLOCKED 只按原等待原因续跑；COMPLETED 默认解释。用户明确要求重新分析时，界面提供重新评估入口。若引入意图识别，低置信度不得自行重跑；显式操作优先。

## 4. C1.1：历史与续跑的真实语义

1. 公共任务视图记录/展示原数据上下文、快照版本和可用操作，避免“同一聊天”被当成“同一执行”。公开引用不暴露本机路径和内部图状态。
2. 历史 GET、刷新、选择历史记录都不触发图；解释接口只使用当前选中任务材料和相关解释消息。
3. BLOCKED 继续区分缺输入与报告审批，复用已有表单校验；不得将任意聊天文本当 approved=True。
4. 原快照丢失、checkpoint 不兼容或不存在时，明确不能恢复。不得读取 metadata 后 `create_initial_state()` 并显示“恢复成功”。
5. CLI 现有 `--continue` 在 C1.3 前应明确为引用历史的新任务或明确不可恢复；保留旧记录供查看，不覆写旧执行身份。不要因为改了文案就宣称持久化恢复已完成。
6. completed 解释不产生新的 report.created/mission.completed 成功事件，也不更新旧球员事实；消息变更可使用明确的消息事件，保持现有 SSE 快照协议。

验收：查看/解释零次调用专业图；缺输入恢复同 Mission；审批只续跑 document；原数据版本不因新比赛改变；解释失败不损坏旧报告；没有 checkpoint 的 CLI 记录不冒充恢复。

## 5. C1.2：有关联的新评估

1. 实现 3.2 的应用接口，再接 UI/API。复用已有任务提交、模型节点和 B 的发布门槛，不复制第二套图。
2. 重新评估读取同一生涯/分支/球员的最新快照，一次提交冻结，并持久化输入引用；同一请求重试返回原创建结果，不重复新建。
3. 只选取原目标、相关已验证结果/建议、用户新约束和历史引用；原 completed 子任务不直接导入新任务为 completed，复用必须满足 B3 指纹与来源要求。
4. 最新数据不可读时按 A/B 明确失败，不回退 demo，也不默认用旧快照伪装最新评估。用户可另行选择“解释旧结果”。
5. 新任务失败不改旧任务状态/报告；父子关系可追溯，旧报告继续说明适用的旧数据版本。
6. 显式传入历史/评估记录应纳入实际消费方的输入材料与指纹。只显示 parent id 而不消费上下文不算接通。

验收：快照 v1 的报告后出现 v2，解释仍引用 v1，重新评估新 Mission 引用 v2；父子任务互不覆盖；重试不重复创建；非法跨会话/跨生涯引用拒绝；新约束和相关历史进入真实 prompt；创建后数据再变化不改变已冻结输入。

2026-10-02 已完成上述范围，入口为 `MissionService.create_continuation(Continuation)` 与 `POST /api/mission-continuations`。完整输入、来源投影及请求去重保存在已有任务 SQLite；历史注入实际 Manager/专业输入和 B3 指纹。`recommendation_id/assessment_id` 仅预留字段，未接通 E 解析时拒绝非空引用。验收及兼容边界见 [C1.2 实施记录](completed/C_C1_会话恢复与任务延续.md)。

## 6. C1.3：CLI 的持久化暂停恢复

- 复用 SQLite checkpointer 和运行时工厂，显式配置 CLI 任务目录与 checkpoint 位置，关闭连接；不依赖重建 MemorySaver 找旧 thread。
- SessionRepository 仅索引执行身份、上下文、存储格式和记录位置，不负责伪造状态。不要将实际会话索引继续混入可重建 demo 样本根。
- 真正续跑先加载原 checkpoint，确认停在支持的缺输入/报告审批位置，再采用现有 Command/静态续跑方式；不重新调用 `create_initial_state()` 覆盖原任务。
- 同进程/服务重复续跑使用已有活动任务检查；跨进程写入仍按单写入进程约束，不在本轮实现多进程执行平台。
- 查看完成历史只读；新评估使用 C1.2 的新身份和关系。旧 metadata-only 样本可保留为未验证历史或重建，不能推断出原 checkpoint。

验收用两个独立进程/重建运行时验证暂停后退出再续跑，不仅同内存实例；检查原任务 id、原快照、执行计数和报告前审批。运行中崩溃恢复与跨数据库灾难恢复不计入 C1.3 承诺。

2026-10-02 已完成。CLI 任务默认保存于 `local_data/cli/fixture` 或 `local_data/cli/actual`，可用 `FAIT_CLI_DATA_DIR` 指定独立根；`--show/--list` 只读，`--continue` 只恢复原支持的暂停。`--reevaluate/--retry` 复用 C1.2 的来源关系和去重。跨进程验收及兼容说明见 [C1.3 实施记录](completed/C_C1_会话恢复与任务延续.md)。

## 7. C2：长期记忆

### 7.1 C2.1：记录、来源与更正

新增轻量 `career_memory/` 或等价模块，初期复用任务 SQLite 的独立表，不引入向量数据库。记录模型最低包含：

| 字段 | 语义 |
| --- | --- |
| memory_id、schema_version、revision | 稳定身份和更正版本 |
| career/branch/player | 作用生涯；跨分支共享偏好须用户明确指定，默认不共享 |
| kind | 明确目标/偏好、建议引用、选择/行动引用、反馈/评估引用 |
| content 与来源身份 | 用户确认的内容或 E 记录引用；关联 mission/subtask/result version/事件 id |
| 时间与有效范围 | 记录时间、game/real 生效时间及精度、适用窗口；未知保持未知 |
| 状态 | active / superseded / retracted；更正关联，不覆盖旧记录冒充从未发生 |

长期目标与偏好由用户明确设置/核实；模型抽取只产生候选，不直接成为已确认偏好。建议只能来自有效成果；采纳、执行、反馈来自 [E 的独立事件](./E方向_球员业务闭环与交互_Codex任务书_2026-10-01.md)。没有 E 事件时保留空缺，不用聊天中的“不错”推断已采纳。

建议保存来源引用与短投影，事实仍由 A 管理，行动仍由 E 管理。C 不再复制一套可写球员档案或行动权威状态。对 E 事件按事件 id 防重，可先做按需同步/重放，不要求后台消息队列。检查源版本与撤回关系后再显示“当前”，防止漏同步的记忆继续有效。

目标/偏好与 A 的 `long_term_goals` 需明确分工：C 管用户当前偏好/决策记忆；A 保留其来源档案字段。若用户要求将某条确认记录写成 A 事实，只走独立受控入口，不双写两个可变真值。

验收：明确偏好与模型候选不同；建议/选择/执行分别有来源；重复同步无重复记忆；更正、撤回、失败/失效建议不作为当前记录；重建 Repository 后仍可读取；测试记忆不进入实际生涯。

### 7.2 C2.2：检索与上下文接入

1. 先按生涯/分支/球员硬过滤，再过滤撤回、适用期、源版本和结果有效性，最后按目标/capability/事件关联/时间排序。不能先全库语义搜索再希望模型忽略其他球员。
2. 首版用结构字段、关键词和时间即可；“取最近 N 条”仅能限制已相关结果，不能替代相关性选择。
3. 检索返回记录 id/revision、来源、时间、限制和短投影，并记录本次实际选取集合。资料中的指令作为数据，不获得工具或调度权限。
4. 历史解释按原任务视角检索，当前新评估按最新适用视角检索；更正前/后记录不能无提示混合。
5. 提交时冻结选定记忆及版本，与 A 快照一并保存。扩展 B3 输入指纹，只包含该子任务实际消费的记忆 id/revision/内容摘要；无关记忆变化不使全图失效。
6. Manager 和相关专业 Agent 使用同一可复核记忆投影。专业预读取和工具若可访问记忆，也必须使用任务固定集合，不能在运行中任意搜索最新内容。
7. 设上下文预算，明确省略项和关键资料不足；不要把“上次完成摘要”当作完整长期记忆，也不靠扩大 `_short_memory` 掩盖缺失接口。
8. 显式短期对话窗口保留当前任务用户补充和解释，不复活无关的已完成任务私有缓存。语义压缩不丢来源、不创造行动或新事实。

验收：新任务找到相关旧选择/反馈；最近但无关记录不进入 prompt；其他分支隔离；更正后检索新版本；新增无关记忆不改指纹，使用记忆更正使对应结果不可复用；提交后记忆变化不改变在途任务输入。

## 8. 范围、协作与检查

主要文件：`app.py`、`utils/sessions.py`、`backend/service.py/models.py/store.py/main.py`、前端任务对话/历史/API/types；新增记忆模块。`graph.py`、`execution_context.py` 仅做固定输入和指纹的薄适配，不重写 B3 调度、失效或审查策略。

C/D 可在独立目录推进。C 与 E 都涉及 `backend/service.py`、DTO 和任务创建，串行交付接口后接消费方；C 拥有后续创建入口，E 调用它。C2 拥有检索投影，E 拥有行动事件；不互建第二套实现。G 接收 C 的暂停恢复与 lineage 契约，不由 C 实现运行中自动重放。

每轮测试用临时任务库、临时球员根、模型替身；验证真实运行时/服务适配，不调用实际模型。按改动运行专项及 `evaluation.test_looping_plan/evaluation.test_web/test_dependency_context/test_result_invalidation`；修改 UI 时运行类型/事件检查和相关界面场景。CLI 跨进程恢复是 C1.3 专项，不为单纯文档改动运行。

交付说明子任务、身份/快照/记忆接口变化、验证证据、兼容策略和限制。旧样本无需迁移保全；实际记录缺少新字段时明确未验证，不推导丢失来源。完成 C1 不等于完成长期记忆，离线记忆测试不等于真实游戏闭环。
