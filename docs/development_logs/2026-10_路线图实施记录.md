<a id="history-oct-02-2-球员数据接口与配置"></a>
#### 2. 球员数据接口与配置

<a id="history-oct-02-21-只读入口"></a>
##### 2.1 只读入口

`PlayerRepository.read_snapshot(context)` 返回 `PlayerSnapshot`。快照含 `profile/training/matches/career/metadata`，读取属性返回副本；`to_dict()` 用于 Graph/checkpoint 序列化。`snapshot_scope()` 让 Agent 内工具读取任务已冻结的数据。

上下文是 `PlayerContext(career_id, branch_id, player_id)`，三个标识各限制为 1–64 位字母、数字、下划线或连字符。路径解析同时检查目录边界，拒绝路径穿越与符号链接越界。

`metadata` 包含 `schema_version/state_version/snapshot_id`、来源与质量标记。版本是不透明值，消费方只比较相等性。来源映射将字段或历史记录指向样本标识/观察标识；实际数据另提供来源类型、provider、原始/确认引用以及采集与生效时间。

规范投影保留当前领域字段，过滤样本中的预测顶层字段和非规范别名，并记录 `ignored_fields`。未修复历史污染、未猜测别名真值。职业历史估值仍保留在 `estimated_value_eur`，不改成已观察市场价值。

缺字段保持缺失，显式 `null` 保持未知，数值 `0` 保持零。伤病 `"None"` 表示明确记录无伤病；缺失或 `null` 不代表健康。原始游戏量表须由 D/F 提供明确适配，本轮规范能力值为 0–100，其他特征使用各自量表。

<a id="history-oct-02-22-两种数据模式"></a>
##### 2.2 两种数据模式

| 配置 | 用途 |
| --- | --- |
| `FAIT_PLAYER_DATA_MODE=demo` | 默认；显式只读 flat JSON 样本适配器 |
| `FAIT_PLAYER_DATA_ROOT` | demo 可指定替代样本根；actual 必填，且不得与仓库样本根重叠 |
| `FAIT_CAREER_ID`、`FAIT_BRANCH_ID`、`FAIT_PLAYER_ID` | 当前应用上下文；任务提交后固定，不随之后的数据切换改变 |
| `FAIT_DEMO=1` | 独立的工作流演示模式；不等同于球员数据模式，不作为真实运行失败的降级入口 |
| `FAIT_DATA_DIR` | 任务 SQLite/checkpoint 存储；与球员数据根是不同配置 |

例如真实档案配置：

```powershell
$env:FAIT_PLAYER_DATA_MODE='actual'
$env:FAIT_PLAYER_DATA_ROOT='C:\FootballerData\actual'
$env:FAIT_CAREER_ID='career-01'
$env:FAIT_BRANCH_ID='main'
$env:FAIT_PLAYER_ID='player-01'
```

实际档案聚合位于 `contexts/<career>/<branch>/<player>/state.json`。缺档案时读取失败，不自动建档、不复制 demo 数据；API 缺数据返回 404，损坏或不兼容数据返回 503。配置独立根不会自动导入观察。

旧 `PLAYER_FILE/TRAINING_HISTORY_FILE/MATCH_HISTORY_FILE/CAREER_HISTORY_FILE` 配置只接受同一个样本目录；与显式根矛盾时拒绝，不让 API/工具各读一份数据。

应用可通过 `create_app(player_repository=..., player_context=...)`、`MissionService(...)`、`create_initial_state(..., repository=..., context=..., snapshot=...)` 注入数据。工具公开读取函数保持原有形状，内部统一读取快照。

<a id="history-oct-02-23-受控导入"></a>
##### 2.3 受控导入

导入接口仅供受信采集/人工确认应用调用，不注册给模型，未新增 HTTP 事实写入端点。调用方必须在模型之外验证采集来源或人工确认凭据；载荷中的 `source_type` 标签本身不提供权限。

```python
from player_data.models import PlayerContext
from player_data.json_repository import JsonPlayerRepository, EMPTY_VERSION
from player_data.imports import Observation, ObservationImporter

context = PlayerContext('career-01', 'main', 'player-01')
repository = JsonPlayerRepository(
    actual_root, fixture_root=fixture_root, context=context,
)
importer = ObservationImporter(repository, source_type='user_confirmed', provider='manual')
# 这些值来自应用已验证的确认过程，不能直接采用模型建议。
observation = Observation(
    context=context, observation_id=confirmed_observation_id,
    source_type='user_confirmed', provider='manual',
    collected_at=timezone_aware_collection_time,
    effective_at=confirmed_real_effective_time,
    time_domain='real', time_precision='instant', kind='profile_patch',
    payload=confirmed_domain_fields,
    expected_state_version=current_version,  # 首次初始化使用 EMPTY_VERSION
    confirmation_reference=verified_confirmation_reference,
)
result = importer.import_observation(observation)
```

支持 `profile_patch/training_record/match_record/career_event`。游戏观察要求 `game_version/adapter_version/source_record_id/raw_reference`；人工确认要求独立的 `confirmation_reference`。游戏生效时间保留 day/month/week 精度，现实时间使用有时区 instant；未知生效时间必须为 `None` 且精度为 unknown，不用采集时刻猜测游戏日期。

| 导入结果 | 行为 |
| --- | --- |
| APPLIED | 观察和事实投影一起提交，新版本生效 |
| RECORDED_ONLY | 观察归档并更新聚合版本，不覆盖当前事实；用于未知时间、稀疏历史、旧/同时间或无法比较的更新 |
| DUPLICATE | 同 provider/observation_id 同语义重试，返回已提交版本，不再次写入 |
| CONFLICT | 同观察 id 内容变化，或新观察的期望版本已过期；不写入 |
| REJECTED | 来源、身份、字段、数值、时间或更正引用非法；不写入 |

防重语义不包含重试的采集时刻与 CAS token。显式更正使用新 observation id 和 `corrects_observation_id`，保留旧观察；只有可比较且对应当前来源的更正才能更新投影。历史追加不会覆盖当前球员属性；其来源的时间域保留可追溯。

每个上下文的事实、来源、观察、防重索引、revision/hash 放在一个聚合 JSON 中。同进程按上下文路径加锁，同目录临时文件序列化、flush/fsync 后原子 replace；序列化、同步或替换失败保留旧档案。损坏数据明确报错，不通过空状态重置。

**限制：仅支持单写入进程。** 进程内锁不保证跨进程竞争；hash 是完整性检查，不是来源签名。原子替换与 fsync 不宣称提供所有文件系统/断电条件下的灾难恢复。跨进程一致性、备份、取消和全面恢复留给 G。

<a id="history-oct-02-3-执行审查与发布契约"></a>
#### 3. 执行、审查与发布契约

| 层次 | 状态及意义 |
| --- | --- |
| 执行 | SUCCEEDED / NO_RESULT / FAILED / BLOCKED；未形成结果、技术故障、缺必需外部输入分别表达 |
| 子任务 | COMPLETED 只表示专业输出已通过接受校验；FAILED 不映射为业务修订；INVALIDATED 表示旧结果不可用于当前交付 |
| 专业结果 | `validated`、`validity`、递增 `source_version`、`input_fingerprint/input_material`、球员与依赖版本引用 |
| 审查 | NOT_RUN / COMPLETED / UNAVAILABLE；未完成时 decision 为空，不认证 reviewed_subtasks |
| 交付 | NOT_GENERATED / PUBLISHABLE；正文 hash、检查范围、被审查结果版本单独记录 |

全部计划子任务默认必需。PARTIAL 可表示有限观察，但未授权为完整依赖或 Mission 完成；本轮没有新增 Mission.PARTIAL。内部技术故障终止为 FAILED，不让用户补造数据来“修复”；必需外部信息缺失才进入 BLOCKED。

ReAct 退出原因包括 FINAL、BUDGET_EXHAUSTED、MODEL_FAILED、EMPTY_OUTPUT、INVALID_CONTENT、TOOL_ERROR。实际工具调用记录 call id、SUCCESS/ERROR、required、error_type 与有效观察。SearchTool 为可选补充检索，其失败保留为限制；其他当前工具失败不能用后续模型文本冒充成功结果。

专业 schema 校验字段/类型/当前可解释数值范围，排除 bool、NaN、Infinity，不校准科学规则。Plan 校验 id、capability、目标、依赖存在/无环、预算，不接受规划器自报 completed。Reviewer 必须覆盖当前必需结果，严重 finding 不能通过删除范围变成 PASS；REPLAN 要有核心证据，INFO/LOW 不触发无意义循环。

当前发布策略是 **专业输入审查 + 正文确定性门槛**：检查非空、模式、明确任务要求、依据与限制、支持的带标签球员数值及引用 URL；记录 `semantic_review=NOT_PERFORMED`。数值检查覆盖年龄、身高、体重、综合评分等支持标签；未声称验证全部散文、所有数据陈述或引用语义。正文改变后原 hash 无效，支撑结果改变后旧专业审查与交付均无效。

报告生成前的人类确认不代表生成后的正文已审核。CLI/UI 已准确标明审查范围。`MissionService.complete()` 复核当前发布契约，报告 GET/下载和前端按钮还需当前 COMPLETED/PUBLISHABLE。

新增公开事件：`subtask.failed/subtask.invalidated/agent.failed/review.unavailable/review.invalidated`。保留有效子任务的简要专业结果；公共 DTO 不传原始提示词、工具参数与异常堆栈。旧记录缺少审查可用性或发布元数据时显示未验证，旧结果无指纹不能自动复用；没有实施全面历史迁移。

<a id="history-oct-02-4-b3-输入与失效"></a>
#### 4. B3 输入与失效

统一上下文包含 Mission/subtask/Plan 身份、capability/goal、全局与局部约束、实际使用的关键假设、该子任务范围内已确认反馈、固定球员上下文/快照/版本，以及显式依赖的有效 payload、版本、证据与限制。首轮和修订共享构建入口，提示词实际注入；无关 Agent 字符串与全部观察历史不作为依赖来源。

依赖按 capability 最小完整字段投影，超过 64,000 字符明确失败，不简单截断关键证据。上下文为副本，上游文本不会增加工具权限或控制路由。祖先结果指纹变化时，即使直接依赖还带 completed 标签，也拒绝消费；损坏循环同样拒绝。

输入指纹覆盖结果契约版本、capability/goal/purpose、Mission objective、约束、实际使用假设、确认输入、A 的快照与状态版本、依赖集合与 source_version；Plan 版本、优先级、展示语气和读取时刻不造成伪失效。使用整份球员版本进行保守失效，未实现字段级影响分析。

修订目标与传递下游立即失效，独立有效任务保留。重规划先校验新 Plan，再按依赖拓扑认证复用；删除任务转为失效历史，新增任务或相同 id 新语义不能继承旧 Agent 输出。结果变化撤销 PASS、reviewed_data、Document 聚合、正文、摘要和发布状态。Reducer 使用明确的有效性与删除标识，不能靠空字典假定清空旧键。预算耗尽不保留假 completed。

<a id="history-oct-04-1-交付行为"></a>
#### 1. 交付行为

| 场景 | 行为与数据语义 |
| --- | --- |
| 已完成报告后出现新比赛/新约束 | 新 Mission、独立 checkpoint，与原任务保持同一 conversation_id，保存 parent/reason/request_id |
| 来源 v1，提交时 v2，排队期间又出现 v3 | 原解释仍引用 v1；新任务固定 v2，执行不重新读取最新数据 |
| 选择原报告或专业结果 | 冻结有版本/哈希的历史投影；有效结果从原 checkpoint 核验，旧 completed 子任务不继承为新任务成果 |

<a id="history-oct-04-2-应用与公开接口"></a>
#### 2. 应用与公开接口

普通 Python 请求为 `backend.continuations.Continuation`，调用 `MissionService.create_continuation()`；API 使用对应的 `ContinuationRequest` 校验后复用同一入口。返回 `(message_id, mission_id, created)`。

```python
from backend.continuations import Continuation

message_id, mission_id, created = service.create_continuation(Continuation(
    parent_mission_id="mission_source",
    conversation_id="conv_source",
    request_id="request_client_generated",
    reason="新增比赛记录，训练时间改变",
    content="每天只有20分钟，请重新安排训练并说明变化依据",
    include_report=True,
    selected_results=[{"subtask_id": "training", "version": 1}],
))
```

`POST /api/mission-continuations` 接收同名字段，202 返回 `message_id/mission_id/created`。来源不存在为 404，身份、历史、状态或幂等冲突为 409，DTO 格式错误为 422。`operation` 支持 reevaluate/retry；retry 的来源必须 FAILED，且应设置 `include_report=false`。`player_context` 可省略并绑定来源；显式传入时必须与来源的 career/branch/player 完全相同。

`recommendation_id/assessment_id` 仅为 E 预留。当前未接通来源解析，非空引用明确拒绝，不把猜测的记录身份加入 prompt 或权威历史。没有建立 E 的行动/反馈存储。

公开 `MissionView.lineage` 保存父任务、操作、原因、请求身份，以及 report/result 的版本、哈希和来源 id。`available_operations` 增加 reevaluate/retry；来源未知的旧任务不提供这些操作。公开 API 不返回完整固定快照、内部 checkpoint 或本机路径。

<a id="history-oct-04-3-固定输入与实际消费"></a>
#### 3. 固定输入与实际消费

- 复用 `workspace.sqlite3`，增加 `mission_inputs` 与 `creation_requests`。`Store.create()` 在一个事务中写入 Mission、完整固定输入、初始消息/事件及创建去重记录；不做球员库与任务库的跨数据库事务。
- 固定输入包含 schema_version、运行模式、完整 PlayerSnapshot、continuation_context 与整体内容哈希。普通任务和关联任务均通过该入口持久化输入，替代提交至首次执行间的内存快照缓存。
- 关联创建先核验来源、会话和选定历史，再读取同一球员的最新快照。执行从任务库还原固定快照，校验完整性、格式、模式及公开输入引用；缺失或不兼容时失败，不读取当前数据代替。
- 历史投影包含原目标、新要求、发起原因及原输入引用。原报告最多 12,000 字符，保存完整原文的哈希并标记截断；专业结果按能力允许字段投影，附证据、限制、输入引用与结果版本。最多选八个专业结果，总历史预算为 32,000 字符，超过时明确拒绝。

<a id="history-oct-05-3-实现与协作边界"></a>
#### 3. 实现与协作边界

- `backend.cli.CLIMissionService` 是现有 MissionService 的阻塞适配，仅等待现有队列 Future；执行、暂停校验、输入、固定快照、审查、发布和关联创建继续使用同一应用代码。

<a id="history-oct-06-1-来源门槛与映射"></a>
#### 1. 来源门槛与映射

`career_actions/sources.py` 提供同进程、有权限的只读 `MissionResultReader`。它读取原 SQLite checkpoint 和持久化 `mission_inputs`，不调用模型、工具或执行图，不向前端开放完整 checkpoint。

生成和读取建议时核对以下条件：

- 真实任务运行路径、`VERIFIED` 输入、已发布报告；普通读取只接受 `COMPLETED`，交付钩子允许当前任务在提交完成事件前投影。
- B3 的 `publishable` 门槛：专业结果结构合法、已验证、`CURRENT`、输入指纹有效，当前审查与成果版本匹配，正文通过现有确定性发布检查。
- 公开 Plan/Report/Review 与 checkpoint 的版本、被审查结果及最终正文一致；公开审查必须为 `COMPLETED/PASS`。
- 完整输入 schema/mode/hash 合法，持久化快照与 checkpoint 相同，快照身份与公开输入引用相同。
- 每项训练成果再通过现有 `validate_specialist`，然后按子任务读取，不能用 `domain_outputs[Agent]` 或非空报告推断有效来源。

映射版本为 `training-focus-v1`，每个 `focus_areas[index]` 生成一条建议。来源键包括 Mission、subtask、result version、`/focus_areas/{index}` 和映射版本；位置只在对应成果版本内有效。同一个 Coach 的不同子任务分别保留身份，新成果版本创建新 id，旧内容不被覆盖。

建议的目标取原子任务目标，条件复用固定任务约束，限制保留成果 uncertainties/notes。依据说明专业成果已通过版本审查，不将训练焦点包装成确定收益。首版每个成果最多 32 个焦点、结构化 payload 最多 32,000 字符；超预算明确不可投影，不静默截断。没有训练焦点的任务可正常发布报告，但返回空建议列表。

游戏版本只来自固定快照中当前字段 origins 所引用的来源，不使用未应用的 `RECORDED_ONLY` 原记录。`JsonPlayerRepository` 的只读来源元数据增加已存储的 `game_version/adapter_version` 投影，没有写入或猜补游戏字段。游戏模式、有效窗口和比较指标仍未知。

<a id="history-oct-06-2-对象存储与业务事件"></a>
#### 2. 对象、存储与业务事件

`career_actions/models.py` 定义 schema version 1 的对象与公开读取视图：

| 字段 | 当前实现 |
| --- | --- |
| `recommendation_id/revision` | 来源键生成稳定 id，初始 revision 1；成果新版本另建记录 |
| `context` | 原输入的 career/branch/player |
| `source` | Mission/subtask、capability、成果版本、payload 位置/hash、输入指纹、审查版本、映射版本 |
| `content` | 焦点、预期目标、依据与限制 |
| `applicability` | 原输入引用、条件、已知游戏版本；未知模式/有效窗口及原因 |
| `execution_support` | `pending_verification`，操作证据引用为空 |
| `evaluation_spec` | `undefined`，固定基线引用、空指标和未知观察窗口及原因 |
| 读取视图 | `validity/validity_reason/checked_state_version` |

复用任务目录的 `workspace.sqlite3`，新增 `recommendations`、`recommendation_batches`、`recommendation_events` 三张表，不另建球员事实库或修改 B/C 执行状态。

对象插入、旧版替代、业务事件与批次结果在同一数据库事务提交。来源唯一约束和现有 Store 锁支持并发重复投影；同来源内容、审查引用、基线或执行/比较规范冲突时回滚并拒绝覆盖。重放保留原创建时间，已撤回或替代的同来源记录不被自动重新激活。

事件类型为 `recommendation.created`、`recommendation.superseded`、`recommendation.withdrawn`。每项带 event_id、全局递增 sequence、schema_version、建议 id/revision、context、source 和时间。查询按 Mission 和 `after` 筛选，每页最多 200 项。消费者以返回序号推进，不能假设单个 Mission 的序号连续。

E 事件独立于现有 Mission SSE；本轮不修改 SSE 枚举、解析器或 snapshot 协议。C2 后续消费事件时仍需通过应用读取原建议的当前来源和适用性，不能把一次 created 事件当作永久有效或玩家已采纳。

<a id="history-oct-06-3-投影时机与读取接口"></a>
#### 3. 投影时机与读取接口

`MissionService.complete` 在现有报告发布检查通过、正文保存后投影建议，再发布原有完成事件。服务启动时，对已完成任务进行来源校验和幂等补投影；不运行专业图或读取最新球员档案来改旧输入。缺 checkpoint、缺完整输入或来源不兼容的旧任务保留报告，建议返回不可用。

建议存储失败独立处理，不使合法原报告变成失败。事务中事件插入失败时没有半条建议/事件；可保存的情况下记录 `UNAVAILABLE` 原因。任务失败会将其当前建议撤回，重复撤回不重复事件。

公开接口均只读：

```text
GET /api/missions/{mission_id}/recommendations
GET /api/missions/{mission_id}/recommendation-events?after=0
```

列表返回 `mission_id/availability/reason/items`。未知 Mission 返回 404；availability 表示建议来源/投影可用性，不代替每项 validity。列表查询不补投影、不追加事件、不调用模型或写入球员事实。应用 `get(recommendation_id, PlayerContext)` 检查完整生涯/分支/球员身份，供后续业务复用；本轮没有新增选择/执行写 API。

<a id="history-oct-06-4-当前适用性与历史保留"></a>
#### 4. 当前适用性与历史保留

读取时重新检查原成果，并用同一确定性映射核对已保存的建议内容、来源/审查引用、基线、执行支持和比较规范。再读取同 context 的最新快照一次，仅用于适用性检查。

| 情况 | 有效性 |
| --- | --- |
| 原来源有效，最新 state_version/snapshot_id 与固定基线一致 | `current`，仅表示来源和数据一致，操作仍待验证 |
| 最新快照变化、不可读取或身份不一致 | `needs_reassessment` |
| 原成果被新版本替代 | `superseded` |
| 来源失败/失效、审查不可用、checkpoint 不一致或保存记录与原投影不符 | `withdrawn` |

GET 的这些检查只影响返回视图，不回写旧建议、事件或报告。显式写入侧的替代/撤回才产生持久化业务事件。不同球员、生涯或分支的数据不混入适用性判断。原建议在数据变化后仍保留原内容和固定基线，不能以最新数据覆盖旧来源。

<a id="history-oct-06-5-工作台交互"></a>
#### 5. 工作台交互

任务完成或失败后显示“训练焦点建议”面板；支持刷新当前适用性、展开来源/审查/条件/固定基线/游戏版本与窗口，并查看来源报告。网络错误独立展示，可以重试读取。建议缓存随任务身份/序号更新，刷新页面重新核验。

来源一致、待重评、已替代和已撤回分别展示。页面明确建议不等于已采纳或已执行，未提供采纳、执行或自动报告抽取按钮。游戏模式/窗口和比较缺失说明直接可见，不显示虚构效果分。

浏览器截图：`frontend/test-results/e1-1-recommendations.png`，已检查布局与展开内容；该文件由隔离响应样本生成，属于被忽略的验收产物。
