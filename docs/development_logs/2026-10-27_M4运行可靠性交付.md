## 3. 核心内容详解

### 3.1 架构与设计决策（Why & What）

**从实际缺口确定范围。** 原审计没有把旧业务回归通过视为运行契约完成：R1时限/队列/关闭、R2取消、R3请求/暂停身份、R4产品备份、R5跨进程actual丢更新构成阻断，R6计量是必要配套。按契约与隔离试验 → actual写锁 → 请求身份 → 监督执行 → 取消/发布 → 计量 → 重启/兼容 → 备份 → 正式验收推进，避免共享状态多处同时重写。

**保留中断政策。** 两暂停可以继续原任务；执行中断明确失败并允许显式关联重试；完成报告保留，解释是独立操作。没有引入任意节点自动恢复、持久消息队列或跨库分布式事务，也没有改变模型的领域职责。

**隔离卡死执行。** 唯一线程只超时等待不足以释放执行能力，因此采用一个协调者、最多一个受监督执行子进程和有限队列。Windows Job持有进程树，启动门在绑定成功后放行；工作进程传回受限JSON元数据，协调者保留workspace业务写权，checkpoint另持写入租约。

**分开身份和权威。** request标记一次用户意图，operation标记工作流或解释，run标记派发段，pause标记具体表单；网络attempt另计。队列/执行/暂停状态服从操作身份与持久提交门，旧PASS/completed或迟到进程结果不能单独授权报告与E建议。

**分开未知与零。** 失败响应、取消、崩溃的缺失usage保留未知，已知响应部分单列；客户端尝试不是账单。排队、执行、用户等待、墙钟与节点耗时累计分别定义。业务完成后计量未收口的崩溃不能撤销报告，也不能无限累计离线执行时间。

**一致恢复先做停写。** 显式声明整个actual和各Web/CLI任务根，按固定顺序取锁，用SQLite backup保留已提交WAL，再校验来源与固定材料。原生绝对路径用外部source-map重定位，保留观察语义hash；恢复只产生新候选，预检通过后也保持未激活。

简化流程：接收请求并保存回执 → 有限排队 → 监督执行 → 暂停核验续跑 / 原子发布 / 撤权失败或取消。重启读取操作与checkpoint，暂停继续原材料，执行中断不盲重放。
