## 1. 给执行 Codex 的任务摘要

你正在维护 FootballerAiTeam。B 方向解决三个问题：系统是否真的得到有效结果，审查是否真的完成，下游是否真的使用当前有效的上游结果。

**执行单位是子任务，不是整份指南。未指定子任务时，默认只执行 B1.1。** 每个子任务应包含必要的状态、API、事件和界面适配，形成可观察的完整行为；不得以只改内部字段作为完成。

| 子任务 | 交付目标 | 前置条件 |
| --- | --- | --- |
| B1.1 | 明确执行、审查与交付的状态契约，阻止审查失败被转换为 PASS | 建议 A1 已完成；不依赖 A2 |
| B1.2 | 移除运行时固定答案降级，失败明确为未输出结果 | B1.1、A1 |
| B2.1 | 工具循环正确终止，工具错误保留结构化语义 | B1.1–B1.2 |
| B2.2 | 按 capability 校验专业结果与执行计划 | B2.1 |
| B2.3 | 明确最终正文校验、审查范围与发布条件 | B2.2 |
| B3.1 | 首轮与修订统一传递依赖结果和输入版本 | B1–B2、A2.1 的只读上下文/版本接口 |
| B3.2 | 复用判定、传递失效与旧报告失效 | B3.1 |
| B4 | 逐项收敛新旧重复状态 | B1–B3 稳定；后续整理 |

总体顺序仍按路线图推进：A1 → B1 → B2 → A2 → B3。B3 的技术前置是 A2.1 的稳定只读接口，不要求 B 为此实现 A2.2 的导入。B4 不作为首次游戏接入的硬前置。

执行前读取适用的 AGENTS.md、最新源码与已合并接口，核查本文指出的问题是否仍存在。保留已有代码修改；发现其他方向问题时记录并移交，不扩大本轮实现。

当前预设档案均为测试样本，可按需重建。无需恢复历史样本真值或迁移保全；最终功能必须继续满足 A 的事实保护要求，生成、修订、失败和重规划都不能写入实际球员档案。

## 2. 产品行为与核心不变量

用户希望失败时直接降级为“未输出结果”。这不意味着销毁已获得的有效观察，而是不得拿固定训练方案、饮食计划、职业建议或模板报告冒充成功输出。

| 编号 | 不变量 |
| --- | --- |
| I1 | 模型或工具调用失败、空输出、无效结构，不自动生成默认业务结论 |
| I2 | 非空文本、可解析 JSON、模型自报 SUCCESS 均不是完成任务的充分条件 |
| I3 | 审查未运行、不可用、失败与审查通过分别表达；只有有效且覆盖当前输入的审查可产生 PASS |
| I4 | 工具观察和确定性计算可保留，但不能被自动认证为完整专业建议 |
| I5 | 缺少必需外部输入才进入 BLOCKED；内部技术故障不要求用户编造数据来解锁 |
| I6 | 初次执行与修订均使用明确的任务目标、约束、当前快照和所需依赖结果 |
| I7 | 上游、相关输入或约束改变后，受影响的下游结果与报告不能继续作为当前有效结果 |
| I8 | 同一 Agent 的不同子任务拥有各自结果；按 Agent 名聚合的字符串不是子任务权威来源 |
| I9 | 修订、重规划和工具循环都有预算；预算耗尽不等于问题已解决或任务已完成 |
| I10 | Graph、公开 DTO、事件、存储快照和 UI 对同一状态表达一致 |
| I11 | 正常运行失败不能自动切换到 demo；演示数据与替身有明确入口和标识 |
| I12 | 建议、预测和审查活动保持只读事实能力，遵守 A 的数据边界 |

例如：Analyst 得到有效比赛统计，Coach 返回无效 JSON。可以保留并展示已验证的统计及来源，但训练方案显示“未输出结果”；不得填入固定四周计划，也不得让任务显示“完整方案已完成”。

## 5. B1.1：结果与审查状态契约

### 5.1 分开表达执行、审查和交付

先给出小范围契约与状态映射表，再完成消费方。下列字段名可以调整，语义必须保持；这是本指南内的设计步骤，正常实施无需反复询问许可。

| 对象 | 最小表达 |
| --- | --- |
| 执行结果 | outcome、可选有效 payload、缺失输入或错误类型、公开简要原因、可追溯证据 |
| 结果有效性 | 校验是否完成，当前/已失效；B3 增加输入指纹和依赖版本 |
| 审查 | 可用性、可选 decision、审查范围、被审查的具体结果版本；未完成时 decision 为空 |
| 交付 | 最终内容未生成、草稿或可发布；整体是否完整满足当前目标 |

推荐执行 outcome 区分 `SUCCEEDED`、`NO_RESULT`、`FAILED`、`BLOCKED`，以及确有定义时的 `PARTIAL`。`NO_RESULT` 表示未形成可接受结果，`FAILED` 表示技术执行失败；均不能自动转成需业务修订。`PARTIAL` 只包含独立验证过的部分内容，不是把错误文本包进 payload。

审查可用性至少区分 `NOT_RUN`、`COMPLETED`、`UNAVAILABLE`。有效审查的 decision 仍为 PASS/REVISE/REPLAN/BLOCKED；`UNAVAILABLE` 或 `NOT_RUN` 不伪造 decision，也不填充 `reviewed_subtasks`。

Subtask 的 COMPLETED 表示执行产出了已校验结果，不等于 Reviewer 已通过。Mission 的 COMPLETED 表示当前必需成果有效、规定审查已完成、最终正文通过发布门槛。节点函数返回与进程执行结束都不作为成功条件。

### 5.2 默认终态与发布策略

| 场景 | 首版默认行为 |
| --- | --- |
| 必需专业结果未输出/技术失败 | 保留有效观察；Mission 为 FAILED，明确未输出完整结果，无最终报告发布 |
| 必需外部输入缺失 | BLOCKED，提供具体输入要求；无自动业务修订重试 |
| Reviewer 不可用或载荷无效 | 审查 UNAVAILABLE，Mission 为 FAILED；不生成已通过报告 |
| 有效审查要求局部修订或重规划 | 在原有有限预算内执行对应动作 |
| 预算耗尽仍有实质问题 | 未完整交付；保留分析与原因，不用 PASS 或模板报告结束 |
| Document 未输出或校验失败 | Mission 为 FAILED；有效分析可查，`final_report` 不设置为替代正文 |
| 必需成果、审查与正文均有效 | 发布报告并 COMPLETED |

当前任务默认全部计划子任务为必需。只有明确的业务契约将某项定义为可选，才允许它失败后依然完成目标；不能由执行器、模型或“已有一点结果”临时决定可选。首版不强制新增 Mission.PARTIAL；若新增，必须同步终态判断、持久化和全部消费者。

### 5.3 实施要求

1. 去除 Reviewer 异常时的 PASS，并修正 normalise/migrate、legacy 适配、缺失 decision、`review_passed` 和路由中的默认成功路径。原生模型输出校验与旧状态适配分别处理；旧载荷兼容不能认证未知审查已完成。
2. `review_passed` 只能由有效审查推导。未审查不设置 `reviewed_data` 为已通过材料。已有 deterministic findings 可以保留，但不冒充模型深度审查完成。
3. 技术故障不进入 human_input 让用户修复；无外部输入可补时不得 BLOCKED。处理 unavailable 时避免落入重复审查或无限循环。
4. Graph 显式保留终态/失败原因，服务按该状态发布。不能只改服务判断而保留内部旧 PASS，也不能只改 Reviewer 却让服务非空报告即成功。
5. 公开 DTO、事件和 TS 类型同步支持失败与未审查。新增 Subtask.FAILED、review availability 或失败事件时，落实 emitter、事件解析、快照、状态文案和终态判断，不能把 FAILED 映射成 REVISION_REQUIRED。
6. UI 展示“未输出结果”“审查未完成”等真实状态。技术错误提供简要可理解原因；原始提示词、工具参数、堆栈与秘密配置不进入公共 DTO。
7. 兼容旧任务记录时，缺失新元数据显示“旧记录未验证”或明确拒绝不兼容续跑，不补造通过标记。无需为了测试档案编写全量历史迁移。

### 5.4 验收矩阵

| 场景 | 必须满足 |
| --- | --- |
| Reviewer 超时/抛异常/返回空或非 JSON | review 不为 PASS，review_passed 为假，无最终成功事件 |
| 空 review、未知 decision、旧 review.failed | 不被 normalise/migrate/显示适配提升为通过 |
| 有效 PASS 且输入覆盖完整 | 正常完成路径可用，完成标记可追溯到有效审查 |
| 同一技术失败经 Graph、API、SSE、UI | 失败原因和终态一致；Agent 返回不直接标为成功 |
| 内部故障与外部缺输入 | 分别 FAILED 与 BLOCKED；后者保持既有输入验证/续跑行为 |
| 无效终态中残留非空 final_report | 不发布、不得 COMPLETED；不能只凭历史字段结束 |

B1.1 完成后即可作为 C/G 消费的基础状态契约。不要宣称固定答案和全部专业校验已经解决。

## 6. B1.2：移除固定答案降级

1. 检查 Coach、Nutrition、Analyst、Career 的全部正常模式，以及 Document 的 comprehensive_report、pr_statement、commercial_advisory、media_response。模型、解析或关键步骤失败时返回 B1 契约，不生成固定业务结论。
2. 替换 Analyst 的混合兜底：已有确定性计算单独作为有来源、有适用限制的观察保留，固定趋势摘要不作为事实或完整分析。F 后续负责计算规则是否适合游戏，B 不顺手重写风险算法。
3. Manager 的任务理解、计划生成和目标提取也须表达不可用。规划失败不能清空计划后悄悄进入通用报告；但合法的纯文本交付可以有零个专业子任务，应由明确 output_type/交付契约区分，不能一律将空计划当失败。
4. 无效模式不得静默换成另一个业务模式后宣称原任务完成。明确拒绝或采用有文档的兼容映射，并保持输入含义。
5. 移除 Document 的运行时模板报告降级。失败说明是状态消息，不写成 `final_report`；同时检查 `final_result`、`domain_outputs.Document`、完成摘要和 CLI 打印，避免另一入口仍宣称已生成。
6. 确定性 demo 可以保留在明确 demo 入口或测试替身中。真实路径失败不得调用 demo，不因 mock 返回了非空内容就认证真实模型正常。
7. 本任务先移除已知降级路径并表达失败；完整字段/业务约束验证交给 B2.2，不在此轮扩成全部 schema 重构。

验收至少覆盖每个专业 capability 与四种 Document 模式的模型异常、解析失败和正常路径，验证没有固定替代方案、没有虚假完成摘要；合法文档任务仍可正常交付。保留观察的场景验证其展示标签和下游消费限制。

## 7. B2：输出校验与工具循环

### 7.1 B2.1：工具循环的明确退出结果

将 `_run_react_loop()` 的“文本 + 日志”返回扩展为可表达退出原因的结果，或提供等价适配。至少区分最终模型答复、预算耗尽、模型失败和工具调用错误；同步所有专业 Agent 消费方。

- 只有不带待执行 tool_calls 的最终模型答复，才进入专业输出解析。空答复不完成；带工具调用时的附带文本不作为最终结果。
- 达到 max_iterations 返回预算耗尽/未输出结果，保留有效工具观察；禁止使用最后 ToolMessage 内容充当模型结论，即使工具返回恰好是合法 JSON。
- 正确处理 provider 的 content 形状，明确支持字符串/内容块哪些形式；不盲目 `.strip()`，不把任意对象 `str()` 后当业务结果。
- 工具调用记录保留 success/error、工具名、调用标识、错误类型和结果引用；不要仅靠中文错误字符串进行路由判断。
- 工具不存在、参数不合法和执行异常分别表达。多工具调用时明确失败后的策略，已有成功观察不得丢失，也不得将失败解释为正常无数据。
- 必需工具失败时不能产出完整结果；非必需检索失败可继续，但必须显式保留限制。必需性来自任务/capability 规则，不能只凭模型声称工具不重要。
- 参数校验或未知工具请求不给予新的工具权限，特别不能重新绑定 A1 禁止的事实写工具。
- 原有预算和有界修复可沿用；本轮不实现整任务超时、取消线程或网络自动重试平台。

专项验收覆盖：正常最终回复、连续工具调用直至预算耗尽、工具 JSON 看起来像业务结论、空 content、未知工具、参数错误、工具异常、成功与失败工具混合。验证退出原因与有效观察分别保留，失败不能靠专业解析再次转成成功。

### 7.2 B2.2：专业结果与 Plan 校验

按照 registry 的 capability 建立小规模 schema 和验收规则，保持现有业务字段兼容。执行层接收已验证结果；模型自报 status 不能绕过校验。

| capability/对象 | 最小校验重点 |
| --- | --- |
| `skill_training` | 训练安排的字段、类型和任务目标；能力变化始终标为预测 |
| `nutrition_plan` | 当前模式要求的结构与数值类型；游戏不支持的营养内容适用性由 F 后续处理 |
| `performance_analysis` | 数据期/来源、分析结构；未知输入不得生成为已观测趋势 |
| `career_planning` | 规划结构、适用约束；估值与收益不伪装为已观察事实 |
| `transfer_analysis` | 目标与对比结构、来源/限制；没有目标或必要数据时明确缺输入 |
| Plan | capability、唯一子任务 id、依赖引用、无环性、明确目标与输出类型 |
| Reviewer 输出 | decision、findings 类型/范围、有效证据引用、实际覆盖的当前子任务 |

实施规则：

1. 可去除一个合法代码围栏等纯格式包装；字段缺失、错误类型、无效值或语义冲突不得通过固定补值、随意强制转换或删除依赖来“修复”。
2. required 字段按 capability/模式定义；PARTIAL/BLOCKED 另有明确结构，不能让所有字段 optional 导致任何 JSON 都成功。
3. 数值排除 bool、NaN、Infinity；检查当前可解释的范围和内部一致性。游戏属性跨量表换算、科学风险阈值与成长算法归 A/D/F，不在 B 凭空设定。
4. Plan 的未知依赖、重复 id、循环依赖或无执行器 capability 不静默删除。可以拒绝计划或进行有预算的规划修复；规划器不能自报子任务 completed。
5. 非法审查 decision 或非空严重 finding 被丢弃后不能产生 PASS。不存在的 subtask id、无法支持的 REPLAN 或 scope 不明应形成无效审查/受限审查原因，不扩大执行范围，也不默默消除问题。
6. PASS 必须覆盖当前应审查的必需结果版本；未评审的剩余部分显式保留未审查状态。INFO/LOW 只 KEEP；REVISE 只改最小范围；REPLAN 需核心假设/共享假设/目标变化的明确证据。
7. 格式修复如确需调用模型，必须有明确次数上限并再次校验；首版也可直接 NO_RESULT。修复不能填造原输入和引用。
8. 观察提取不把建议字典的所有字段自动归为 facts；区分观察、计算、推断和建议，复用 A 的来源分类。

验收矩阵覆盖：可解析但缺字段 JSON、错误类型、空列表/空字符串、未知状态、自报 SUCCESS 的无效结果、非法数值、缺输入、合法部分观察；以及缺失/循环依赖、未知 capability、严重 finding 指向不存在 id。正常 schema 路径保持可用，模型文本中的状态和来源标签不能自行认证结果。

### 7.3 B2.3：最终正文与审查范围

当前 Reviewer 位于 Document 之前，审查的是专业输入。它无法证明之后生成的正文已经过审查。最终交付至少有以下边界：

1. 记录专业审查覆盖的 subtask id/结果版本；Document 仅消费当前有效的审查范围内结果，按当前 Plan 投影，不能回退到旧聚合文本。
2. 生成正文先保存为草稿或局部返回值。确定性检查至少覆盖非空、对应输出模式、必要任务要求、明确限制、可核对数据/引用的一致性；检查通过后才设置可发布最终内容。
3. 已通过输入审查与最终正文检查分别记录。正文散文的语义正确性不能仅靠非空或关键词匹配认证；无法验证的内容标明范围，不宣称“全文已审核”。
4. 首版可采用“专业输入审查 + 正文确定性门槛”，界面准确注明正文校验范围。若增加模型正文审查，应作为本子任务内明确的扩展：审查实际草稿、记录正文版本/摘要、最多一次局部正文修复，之后重新检查；不能再次无限触发全图循环。
5. 正文审查失败/不可用按 B1 策略不发布。不能将旧专业 PASS 复用于新正文的全文审查。
6. 服务 `complete()` 必须验证当前交付状态与内容版本；失败/失效草稿不写入公开报告、成功摘要或 report.created/mission.completed。
7. 既有 `interrupt_before=['document']` 是报告生成前的人类审批，不代表确认生成后正文正确，不代表实际球员能力改变。B 只修正状态与文案，暂停恢复行为归 C。

验收包括：专业 PASS 后 Document 抛异常/空输出/错误模式；草稿引入可核对的错误数值或无效引用；只有输入审查时的 UI 标识；草稿变化后旧全文审查不可复用。不要将可生成报告文件等同于可交付报告。

## 8. B3：依赖上下文与结果失效

### 8.1 B3.1：统一执行上下文

使用 A2.1 的只读快照、context 和不透明版本；B 不自行定义另一套球员数据路径、版本算法或写入接口。执行上下文建议包含：

| 字段 | 语义 |
| --- | --- |
| 任务身份 | mission id、subtask id、当前 Plan 版本、capability 与目标 |
| 约束 | 当前相关 Mission/任务约束及有来源的关键假设 |
| 球员输入 | career/branch/player、snapshot id、state version 与实际消费的只读快照 |
| 依赖输入 | 每个显式依赖的 subtask id、结果版本、有效 payload/相关证据与限制 |
| 执行阶段 | 首次执行或 revision；后者附加具体 finding 和上次结果引用 |

首次执行与修订通过同一个上下文构建入口；专业提示词实际消费该入口，不只是给 state 添加一个无人使用的字段。覆盖 Coach/Nutrition/Analyst/Career 的全部 capability，必要时调整 `registry.get_active_subtask()` 的薄适配。

要求：

- 只读当前计划显式依赖与必要证据；不能把全部 observations、全部 Agent 历史文本或私有推理塞进上下文。
- 调度就绪检查同时验证依赖 status、结果存在、校验通过和当前有效性，不能只看 completed 标签。
- 默认只消费完整有效依赖；若某 capability 允许部分观察，写明可消费的结构与限制，不用 failed payload 自动顶替依赖。
- 依赖缺失/失效属于调度或状态问题；它本身不一定需要用户输入。追溯真正缺失的外部事实，避免错误 BLOCKED。
- 上下文是可复制的快照，Agent 不原地修改全局结果；任务执行中的身份不能随 UI 切换而改变。
- 有界摘要保留决定当前任务的关键字段。不得因简单截断导致下游拿不到其依赖要求的核心证据；按 capability 定义最小投影及截断提示。
- 上游文本/工具记录作为数据材料传递，不赋予其新的工具权限或控制路由能力。
- 结果记录输入快照/依赖版本，为 B3.2 提供复用依据。球员状态版本与 `source_version`（子任务结果版本）分别表达。

验收用可识别的唯一上游信息验证首次和修订 prompt 均确实包含它、下游结果确实使用它；同一 Agent 执行两个子任务时各自结果正确，两个生涯/分支不会串用，无关历史不进入输入，失效依赖不能被调度为有效。

### 8.2 B3.2：复用与传递失效

为每个接受的结果记录可复核输入指纹。最小内容包括 capability/模式、目标与相关约束、任务读取的球员快照、依赖集合及各依赖结果版本、实际使用的关键假设、结果契约版本。字段顺序和读取时间不应造成伪变化。

首版可用 A 提供的整份球员状态版本保守失效同一上下文的相关结果；不要求实现字段级影响分析。对互不依赖、输入也未改变的子任务，仍须保留结果。没有指纹的旧结果不能仅凭相同目标自动认证复用。

实施规则：

1. capability/goal 相同不足以复用。依赖 id 集合、依赖结果版本、相关约束或实际使用假设改变，都必须使受影响结果失效。
2. 局部修订开始时，标记目标结果及其传递下游为不可作为当前成果；旧数据可以作为历史/修订参考，不能继续授权下游执行或报告发布。
3. 重规划先验证新 Plan，再根据新依赖图自上而下判定复用；被删除的任务只作为历史，新增任务不能借用同 Agent 的旧字符串。任务 id 重用但语义变化同样失效。
4. 上游从有效变为失败/阻塞时，下游不得保留“当前已完成”。影响沿依赖关系传播，不无差别清空所有任务。
5. 输入指纹匹配且结果仍有效，才可复用；记录复用来源。采用递增结果版本时，已接受结果发生变化必须有新版本，版本不能与 Plan 版本混同。
6. 失效是有效性状态，不强制删除历史。合并器和 Reporter 使用当前指纹/版本选择有效结果，不能只取 source_version 最大的陈旧记录。
7. 任何支撑结果或报告正文变更时，关联审查失效。新的专业结果必须重新评审；旧 PASS、`reviewed_data`、`final_report`、`final_result` 和报告摘要不得继续作为新计划当前成果。
8. 检查 LangGraph 字典/列表 reducer 是否支持撤销当前有效标记；仅返回空字典未必能清除已有聚合键。使用明确状态或版本化有效投影，不靠假定覆盖消除旧内容。
9. 预算耗尽导致无法重算时，显示当前结果未完成/已失效；不能为避免失败保留旧 completed。不得引入无限级联重跑。

### 8.3 B3 验收矩阵

| 场景 | 必须满足 |
| --- | --- |
| A → B → C，另有独立 D；A 结果变化 | B/C 失效并按预算重算；输入未变的 D 保留 |
| 同 goal/capability，依赖集合改变 | 不能复用旧 completed |
| 依赖 id 不变，结果版本改变 | 消费新版本；旧下游和旧审查失效 |
| 相关约束/使用假设改变 | 相关任务失效；无关展示字段变化不触发全部重算 |
| 生涯、分支或球员快照改变 | 不跨上下文复用；原任务仍引用其固定快照 |
| 同 Agent 多个子任务、新任务、已删除任务 | 按 subtask 身份消费，历史不混入当前结果 |
| 旧结果缺少输入指纹 | 不自动复用认证，可作为明确的历史参考 |
| 有旧 final_report/PASS 后发生 revision/replan | 新任务视图无当前已发布报告；历史可保留但显式标识 |
| 已失效结果数值恰好与新结果相同 | 不因文本相同跳过输入/审查验证 |
| 预算耗尽或依赖无就绪项 | 有明确终态/原因，无无限循环，无假成功 |

## 9. B4：重复状态收敛

后续每轮只处理一种对象，例如 Plan、SubtaskResult、Review 或 Hypothesis。先列出所有生产者、消费者和持久化入口，再选唯一权威来源，以单向适配供旧调用读取。

- 现有新旧字段通过薄映射维持一致；不允许两个可写版本分别路由，遇到冲突有明确拒绝/选择规则。
- 不顺手重写全部 Agent、CLI 恢复或 checkpoint 存储，恢复策略归 C/G。
- 旧存档可明确拒绝不兼容续跑，不为测试档案开发全面迁移；已有实际产品记录不能靠清库或重置 demo 解决。
- 验收同一对象在调度、审查、报告、API 中含义一致，双向反复迁移不再制造默认 PASS 或旧 completed。

B4 是整理已稳定的执行语义；不得以“先把架构全部重写”拖延 B1–B3 的正确性修复。

| 方向 | B 消费/提供 | 本轮边界 |
| --- | --- | --- |

## 11. 测试与交付规范

### 11.1 专项验证方法

使用隔离临时目录、确定性模型响应和工具替身，尽量调用真实 Agent、normaliser、Graph 路由和服务适配。测试不能只断言删掉的函数没被调用，也不能全用已成功的假节点绕过出错的真实代码。

建议按子任务增加 `evaluation/test_execution_outcomes.py`、`test_agent_output_validation.py`、`test_dependency_context.py`、`test_result_invalidation.py` 等聚焦模块；名称可调整。覆盖正常与失败路径，模型默认离线，不调用 Tavily/真实 RAG 或下载模型。

验证真实 Coach 等节点时必须确保 A1 已移除写入能力，并配置隔离样本。模型 smoke 也不能连接实际生涯档案；真实数据保护是最终要求，历史样本是否污染不是验收指标。

重点端到端场景：规划成功 → 专业有效输出 → 审查通过 → 正文校验 → 报告完成；再分别替换一个阶段为失败，检查 Graph、服务、持久化快照、事件和界面不存在成功残留。

### 11.2 回归检查

按实际修改运行专项模块与已有回归，并报告证据：

```powershell
# 在仓库根目录；专项模块名替换为本轮实际新增模块
& .\venv\Scripts\python.exe -B -m unittest evaluation.test_execution_outcomes -v
& .\venv\Scripts\python.exe -B -m unittest evaluation.test_looping_plan evaluation.test_web -v
```

若修改公开状态/事件或 UI，在 `frontend/` 运行：

```powershell
npx tsc -b --noEmit
npm test
```

必要时使用浏览器检查失败、未审查、BLOCKED 与正常完成各一个实际界面路径；修改截图不替代事件和状态验证。若仓库配置或运行环境导致命令不可用，使用已有适用命令并说明，不能宣称未运行检查通过。

调整既有测试时，不删除体现正确行为的断言来适配新实现。确定性专业节点也须满足新契约；demo 正常路径继续明确为 demo。真实模型/真实游戏 smoke 不是本方向自动验收前提。

### 11.3 每轮最终交付

1. 完成的子任务编号、可观察行为及涉及文件。
2. 状态、schema、事件/DTO 与兼容映射变化；后续方向应消费的接口。
3. 专项与回归结果，哪些使用替身，哪些未运行及原因。
4. 样本是否调整，确认运行验证没有写实际档案；无需历史测试档案修复报告。
5. 已知限制、剩余任务与移交 C/F/G 的问题。

完成 B1.1 不称为 B1 完成；schema 校验不等于建议科学有效；确定性正文检查不等于全文语义审查；B1–B3 通过也不等于游戏生涯闭环或 production-like MVP 已完成。
