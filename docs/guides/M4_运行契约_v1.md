## 1. 身份和所有权

- `request_id`：一次用户提交的身份；客户端发送前保存，重试沿用，修改内容换ID。请求摘要包含目标Mission、intent、context、pause和用户有效载荷，排除接收时间等服务端字段。
- `operation_id`：一次Mission工作流或独立解释；工作流跨暂停保留该身份，解释不修改原工作流终态。
- `run_id`：正整数执行代次；每次派发/暂停恢复递增，SDK内部重试不递增。
- `pause_id`：每次具体等待生成的新身份；恢复需request和pause均匹配，不能只比字段名。
- `contract_version=1`：执行协议版本，工作进程协议已在M4.3接入。M4.2的HTTP接口以必填身份字段定义当前写入格式，任务库核心版本使用user_version=1。

协调进程持有任务目录锁并独占workspace业务写入。执行子进程只持有当前checkpoint写入权，使用协调者提供的固定A、历史、C记忆及E反馈；工具继续只读。工作进程在被分配到其所有者的Windows Job并收到启动信号之前不得打开数据库或执行图。

子进程返回有限、可验证的JSON消息，包含协议版本、operation/run身份、类型和载荷。M4.3限制单帧4MiB、接收队列8帧并施加背压；验证类型、协议和执行身份，违规明确失败并清理。完整提示和密钥不进入stdout控制消息；固定材料通过本地input.json传递，密钥继续使用原受信配置。messages及Interrupt对象留在checkpoint；不从工作进程接收待执行代码或任意SQL。

Windows Job设置KILL_ON_JOB_CLOSE，句柄不继承，父进程异常退出会终止所属进程树。启动采用与当前venv相同的基础解释器和明确的venv导入路径，使Popen.pid等于实际工作PID，避免Windows venv launcher间接PID。只管理本次Popen/Job拥有的进程，不按进程名扫描/停止用户进程。

Job约束进程生命周期，不是文件系统权限沙箱；M4.3可信worker只运行图/checkpoint，workspace、公开事件和E/C写入由协调者持有。M4.4已在持久事务内核对operation/run的运行资格，落实取消与最终发布的先后规则。

当前监督基础显式只支持Windows；其他平台拒绝执行，不能悄悄降级成没有父进程退出保护的模式。此限制在本项目当前Windows本地MVP范围内。

## 2. 状态和竞争

Operation状态：QUEUED、RUNNING、PAUSED、COMPLETED、FAILED、CANCELLED。后三者是终态，原operation不能重新进入运行。正常的重新执行使用关联新Mission/operation。

| Operation | 工作流Mission映射 | 独立解释对原Mission的影响 |
| --- | --- | --- |
| QUEUED | CREATED；公开排队状态另附operation元数据 | 保持COMPLETED及原报告 |
| RUNNING | 继续沿用PLANNING/RUNNING/REVIEWING等图进度 | 保持COMPLETED及原报告 |
| PAUSED | BLOCKED并保存pause_id和原因 | 不适用；解释不进入用户审批 |
| COMPLETED | COMPLETED且满足原结果/正文发布门 | 原报告不变，仅追加成功解释 |
| FAILED | FAILED，结构化原因区分超时/中断等 | 原报告不变，仅解释失败 |
| CANCELLED | CANCELLED | 原报告不变，仅解释取消 |

发布条件是：数据库中的operation仍为RUNNING、operation/run与结果完全一致、原审查/成果/正文门禁通过。必须在最终写事务中重验，不能把执行前校验当成承诺。

取消先提交则撤销该run的业务提交权；完成先提交则取消返回ALREADY_TERMINAL。重复取消返回原结果；目标身份不符拒绝，不转而取消更新的operation。取消回执确认的是持久撤权，资源清理状态单独提供；外部服务已经处理/计费的请求无法保证撤销。

M4.4回执使用accepted/outcome/status及cleanup_status，重复请求返回原回执的初始清理快照；当前进度读取GET operations。清理状态为NOT_NEEDED/PENDING/COMPLETE。工作流取消为Mission CANCELLED；取消独立解释只追加取消消息，原报告继续可读。取消任务可创建新的关联retry；其未交付checkpoint候选不能作为选定专业历史。

报告文本、公开引用、任务/操作终态、相应消息及Mission事件在同一workspace事务中提交。E投影在有效完成后幂等执行；失败显示暂不可用，不重新运行模型。原checkpoint里存在报告候选不等于有效交付。

## 3. 请求和接口

v1接口：

| 入口 | 请求/回执补充 | 规则 |
| --- | --- | --- |
| POST /api/messages | request_id；回执增加operation_id、accepted/replayed | 创建或解释均防重；同ID异内容409 |
| POST /api/missions/{id}/input | request_id、pause_id、values | 一次暂停只被有效恢复一次，重放返回原回执 |
| POST /api/missions/{id}/operations/{operation_id}/cancel | request_id、expected_run_id，暂停时expected_pause_id | 只取消明确目标；返回已接受/已终态以及清理状态 |
| GET /api/missions/{id}/operations | 操作状态、原因、run、revision和原始计量记录 | 报告生成和解释独立；无模型/执行副作用 |
| GET /api/missions/{id}/runtime | 操作与累计usage、时间分账、原报告节点telemetry、sequence/read_at | 只读快照；完整未知用null，已知部分单列 |
| GET Mission / SSE | 增量operation元数据和新状态事件 | 保持Mission sequence及公开快照规则，不暴露checkpoint内部材料 |
| CLI | 创建/解释/续跑支持request身份；取消指定operation | 自动身份发送前保存/输出，显式身份可重用；使用同一应用契约 |

M4.2交付消息/输入/关联创建回执与operations只读列表，M4.3接入执行协议和容量拒绝，M4.4交付取消接口及统一发布门，M4.5增加runtime只读聚合。取消POST返回200：接收撤权为accepted=true/CANCELLED，目标已终态为accepted=false/ALREADY_TERMINAL；run/pause冲突409、未知目标404、字段非法422。旧关联回执的operation_id可能为空，保持其原创建身份，不伪造历史operation。

已接受请求的身份、摘要、原回执与相应业务写入应原子持久。重放首先查原回执，不重读最新A、不重新冻结输入、不重新占队列。创建后未入队的异常退出沿用中断失败政策，原ID重放返回原任务而不隐式重执行。

满队列时返回429、QUEUE_FULL、accepted=false及建议重试等待时间，不创建Mission/operation；同request可稍后重试。已接受后排队超时为FAILED/QUEUE_TIMEOUT，重放仍是原失败。停止服务时的新提交返回503/SERVICE_STOPPING、accepted=false。无效字段422、身份/内容/暂停冲突409；不存在目标404。错误响应不包含密钥、物理路径或提供商原始错误正文。

创建/解释/输入在M4.2后要求新字段。无法提供身份的旧写客户端给出明确协议升级错误；不默默生成新ID制造防重假象。保留旧读取路径；当前前端和CLI需在同一任务完成适配。既有continuation/E/C的防重规则保持兼容。

## 4. 持久化边界和升级

operation和通用request回执表已在M4.2接入，M4.4复用同一表保存带kind的取消回执；主键、摘要和终态理由由应用校验，核心库仍为user_version=1。复用现有Mission/事件/消息/输入及E/C表；不要把request回执、排队内存Future、checkpoint版本或模型输出当成同一种权威状态。

已有Mission无operation的记录按LEGACY_V0只读读取，不能伪造旧调用次数或预算。现有完成/失败报告可读，旧CLI JSON只有元数据仍只读。旧BLOCKED若固定输入/记忆/反馈及checkpoint全部校验通过，可在显式续跑请求中原子接入一个v1 operation及pause身份，记录旧执行预算未知；不默默补为0。如何从未知预算开始一个有界恢复段应公开标注，不冒充整任务历史预算完整。

新增schema采用显式版本和事务升级，在隔离副本验证；已有原始输入和checkpoint不被重写。未来未知版本应拒绝写入。升级前停写、确认旧执行者清理，取得工作区和actual相关锁，保存完整副本与SHA256清单。备份至少含workspace、checkpoint及WAL相关文件、actual聚合、collector绑定/回执、原始来源依赖和非秘密配置/context。

M4.2只在新隔离副本验证v0→v1增表升级和旧暂停接入，没有升级用户实际库。现有单元的停写归档/候选预检使用M4.7工具；旧代码读取新增状态/表的兼容性不能假设，降级使用完整升级前副本和对应代码，不删除新记录假装完成降级。

M4.6增加写前布局检查：workspace支持user_version=1及已知v0核心表；v0中已有的operations/request_receipts也须匹配必需列，不能先升版本再发现旧表不可用。checkpoint仅支持当前SqliteSaver结构、SQLite user_version=0和图内容v=4；检查用只读连接，未知版本/结构拒绝，不自动重建checkpoint。固定输入仅支持schema_version=1与相符模式/摘要/引用。当前范围及实测证据见[M4.6交接](../completed/M4_6_重启政策与必要兼容.md)，不作任意历史版本迁移承诺。

图worker从构造运行时到checkpoint连接关闭持有任务目录的`.checkpoint-writer.lock`；协调者启动先在cleanup_seconds内确认此锁释放，再打开任务库。超时拒绝启动，不按PID杀其他进程。旧版程序不使用此锁，发布前须停写；原任务目录锁与Windows Job继续各自约束协调者和所属进程树。

M4.7提供显式actual+tasks单元的create/verify/restore。固定取得任务目录锁、checkpoint写锁、actual根锁后，用SQLite backup形成成套停写快照；归档保留全context、固定输入/报告/E/C、绑定/回执、原始来源与摘要。restore只向独立新候选复制并预检，RESTORE_READY仍为activated=false，配置切换由用户明确执行。原生绝对路径通过外置source-map迁移，不重写观察语义摘要；缺来源、坏库、错身份/格式/映射拒绝。具体格式和本轮验证见[M4.7交接](../completed/M4_7_停写备份与新目录恢复.md)，不承诺在线热备或任意历史版本迁移。

重启将QUEUED/RUNNING操作及对应失败消息/事件作为一个事务处理；解释中断只影响解释。PAUSED需操作归属/类型/状态/pause一致，并完整比对持久输入与checkpoint的球员、选定历史、记忆、反馈和原目标，再接收恢复。已完成/暂停业务若留有未结算执行时钟，启动时停止其执行投影、保留业务状态，缺失时间与预算历史标为不完整；不能把离线时间累入已知执行耗时。旧历史恢复仅按已保留累计值取得有限预算，不宣称未知旧段已经被完整计量。

## 5. 初始预算

以下为v1试运行初值，均可通过同名`FAIT_RUNTIME_`环境变量覆盖；M4.3已接入Web/CLI服务，服务创建时解析，修改后重启生效。

| 字段（环境变量后缀） | 初值 | 含义 |
| --- | --- | --- |
| MODEL_CONNECT_SECONDS | 10秒 | SDK连接/连接池等待上限 |
| MODEL_READ_SECONDS | 120秒 | SDK读写请求时限，不是整次逻辑调用总时长 |
| MODEL_CALL_SECONDS | 180秒 | 一次逻辑调用包含网络尝试/退避的总时限 |
| TOOL_SECONDS | 90秒 | 一次工具操作总时限，含本地工具 |
| EXECUTION_SECONDS | 1200秒 | 工作流各执行段累计预算；排队/用户暂停分别计时 |
| QUEUE_WAIT_SECONDS | 120秒 | 已接受的执行段最大排队时长 |
| QUEUE_CAPACITY | 3个 | 等待位，不含最多1个运行中执行段；允许配置1—16 |
| NETWORK_MAX_ATTEMPTS | 2次 | 包含首试，SDK max_retries应为1；允许1—3 |
| WORKER_START_SECONDS | 60秒 | 启动并构造运行时的上限，同时扣执行预算 |
| CLEANUP_SECONDS | 3秒 | 本次拥有的进程树资源清理上限 |
| SHUTDOWN_SECONDS | 10秒 | 服务停止接收、有限收尾与清理的总上限 |

单个调用/工具上限还应裁剪至剩余执行预算，父进程监督总截止时间，不能依赖网络read timeout覆盖本地卡死。执行时间以单调钟累计、以UTC记录可展示的时间点；重启不重放，不能用重置计时逃避预算。缺输入/审批等待单独计量，MVP不因用户等待时间自动失败。

M4.3以execution_seconds累计执行段，queue_seconds累计排队；budget_history_complete区分旧历史/崩溃末段未知。崩溃RUNNING只保留已落盘部分并标记不完整，QUEUED未开始的执行时间可知为零。M4.5另以user_wait_seconds累计用户等待，用UTC时间点支持查询时实时投影，timing_history_complete区分完整时间和已知下界。用户等待不扣执行预算，墙钟从操作创建算至收尾。业务暂停/发布早于协调计量结算时，最终operation.updated提供收尾值。

依据：M3基线任务9次调用累计节点耗时186.104秒，反馈任务7次调用159.065秒（本轮只读SQL复核）；M4.0实际图进程冷启动/完成样本约7—10秒。1200秒工作流预算与60秒冷启动预算保留初始余量，不保证真实模型耗时；这两个历史样本不是服务等级或新模型验证。单调用初值是显式策略选择，需后续故障及运行数据检验。

所有秒数必须有限且正、最多86400；整数参数拒绝bool/非整数；模型connect≤read≤logical≤execution，tool≤execution，cleanup<shutdown。未知`FAIT_RUNTIME_`键拒绝，避免拼写错误悄悄关闭保护。

## 6. 计量及后续门槛

M4.5使用metering.version=1的操作记录。逻辑调用和SDK实际HTTP尝试分开；失败、修订、重规划、续跑、取消、超时均按span/run记录，解释另建operation。usage使用可空数值；中止前未取得元数据为未知，不补0。已知响应合计和usage覆盖数单列；重试成功的末次usage不证明失败尝试的用量。只有记录收口、尝试可观测、各调用成功且usage完整、没有未知错误尝试时才显示完整token总量。确认未派发和明确usage=0仍可显示已知零。

原报告生成的节点telemetry保留历史语义，解释不重写它；runtime另提供各操作和累计快照。旧记录没有覆盖标记按未知读取；图的200条events上限不用于重建持久计量。HTTP尝试证明客户端发起，不证明提供方处理/计费；不估算金额。

队列、实际执行、用户等待、总体墙钟分别展示；节点latency_ms明确标作累计而非墙钟。事件重放和查询不重复计量、不增加operation.revision。客户端用Mission sequence、操作revision/run及read_at拒绝迟到快照，相同revision允许新read_at推进实时等待。日志只保留mission/request/operation/run、原因类型等运行元数据，不输出原始提供方错误正文。

M4.0的独立隔离原型不直接构成服务验收；M4.3验证时限、队列和清理，M4.4验证竞争和事务发布，M4.5验证SDK尝试、计量和展示，M4.6验证真实owner重启、固定材料、格式及计量尾段，M4.7验证停写快照、来源迁移与新候选恢复。M4.8已于2026-10-27独立重跑并在当前本地单用户Windows范围[正式验收通过](../completed/M4_阶段四验收与交接.md)；扩展范围、历史和当前验证分开记载。
