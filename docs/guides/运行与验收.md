# FootballerAiTeam Web 工作台 V0.1：运行与验收

当前可靠性状态：2026-10-27，[M4正式验收](../completed/M4_阶段四验收与交接.md)通过本地单用户Windows Career Companion范围。部署到实际工作区仍按下文停写备份、新候选预检及手动切换配置执行；本次验收没有切换现有数据。当前Windows进程隔离在其他系统显式拒绝，未认证全平台运行。

## 运行

要求 Node.js 22.12+（本轮使用 24.19.0）、Python 3.10+；真实任务继续使用仓库原有 `.env`、Agent、工具与模型配置。

在仓库根目录安装后端依赖，在 `frontend` 安装前端依赖：

```powershell
& .\venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-web.txt
cd frontend
npm.cmd ci
```

终端 A，在仓库根目录启动后端：

```powershell
& .\venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

终端 B，启动前端：

```powershell
cd frontend
npm.cmd run dev
```

工作台：<http://127.0.0.1:5173/>，API 文档：<http://127.0.0.1:8000/docs>。

后端绑定本机，面向指南中的单球员工作台。Vite 将 `/api` 代理到 8000 端口，5173 端口被占用时会退出，不会自动换端口。自定义 API 地址可在 `frontend/.env.local` 设置 `VITE_API_BASE_URL`（填写 origin，不加 `/api`）；若前端 origin 改变，需要同步修改 `backend/main.py` 的 CORS 来源列表，目前没有 CORS 环境变量开关。生产构建由 `npm.cmd run build` 生成 `frontend/dist`，部署时同样需要代理 `/api` 到 FastAPI，并关闭代理的 SSE 缓冲。

`GET /api/health` 返回的 `mode=live/demo` 表示任务引擎是否调用真实 Agent，不能据此判断球员数据是不是游戏观察。任务模式与球员数据模式分别配置，见下面的数据源说明。

M4.3后，当前真实任务服务要求Windows，以受监督子进程运行图和报告解释；默认模型逻辑调用180秒、工具90秒、累计执行1200秒、排队120秒，最多1个执行段和3个等待位。暂停/审批不扣执行预算，恢复沿用原checkpoint。配置和验证见[M4.3交接](../completed/M4_3_有界执行与队列.md)及[运行契约v1](M4_运行契约_v1.md)。FAIT_RUNTIME_*在服务创建时解析，修改后重启生效；[M4.4](../completed/M4_4_取消与统一发布.md)已接入取消和统一发布事务，M4整体仍未通过。

任务与独立解释可在各自操作上取消；请求绑定明确operation/run，暂停还需pause。取消回执表示已持久撤权，资源清理单独跟踪；重复请求返回原回执，当前清理状态读取operations。CLI的show提供目标身份；本地暂停可用cancel命令，运行中的Web owner使用显式api-url。参数示例、拒绝规则和关联新任务边界见M4.4交接。

## 演示模式

在后端启动终端中设置：

```powershell
$env:FAIT_DEMO='1'
& .\venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

页面会显示 DEMO 标识。新任务输入框提供四种确定性演示场景：一次通过、局部修订、人工输入、重新规划。球员面板读取配置的 Repository，默认是仓库 `memory/` 内的演示 JSON；`FAIT_DEMO` 不会覆盖球员数据源配置。演示任务只绑定 `FixtureRepository` 样本，不将 actual Repository 当作其确定性执行输入。演示报告明确标注示例，不调用模型、不修改球员记忆。

切回真实模式前停止演示后端，在同一终端执行 `$env:FAIT_DEMO='0'` 后重新启动。真实模式生成报告前保留 CLI 原有的人工确认步骤。

## 球员数据源与任务模式

`FAIT_DEMO=0` 表示调用真实模型与工具；默认的 `FAIT_PLAYER_DATA_MODE=demo` 仍读取演示球员 JSON。因此，真实 Agent 模式可以使用演示球员，不能将其表述为已读取 PES 生涯。

| 配置 | 用途与边界 |
| --- | --- |
| `FAIT_PLAYER_DATA_MODE=demo` | 使用 `FixtureRepository`，默认读取 `memory/` 的平铺 JSON；可通过 `FAIT_PLAYER_DATA_ROOT` 指定独立样本目录。 |
| `FAIT_PLAYER_DATA_MODE=actual` | 使用受控 `JsonPlayerRepository`，必须显式配置 `FAIT_PLAYER_DATA_ROOT`；数据根必须与 `memory/` 样本根分离且不互相包含。 |
| `FAIT_CAREER_ID`、`FAIT_BRANCH_ID`、`FAIT_PLAYER_ID` | 共同定位 Repository 的生涯、分支和球员；实际数据使用已经导入的身份，不因切换 actual 模式自动推断身份。 |
| `FAIT_DATA_DIR` | Web 任务、消息、事件、报告与 checkpoint 目录，独立于球员事实数据根。 |
| `FAIT_CLI_DATA_DIR` | CLI 任务与 checkpoint 目录，独立于 Web 默认任务目录和球员事实数据根。 |

actual 模式缺少身份对应的数据或读取失败时，不会回退演示球员；切换数据源后需要重启后端。D2 的隔离导入验收通过不代表当前 Web 配置已自动切换。排查配置、锁、SSE 与恢复问题见 [排障指南](排障指南.md)。

## 已实现的交互

- 左侧独立球员档案、训练记录与比赛记录；使用长期球员数据，不展示旧预测字段作为实际状态。
- 右侧 Mission Header、Plan/Subtask 进度、Agent Activity、Review/Revision/Replan、Conversation、Report。
- 明确的新建任务入口；完成任务的报告解释沿用原 Mission 与原材料，不触发专业图。新比赛/新约束可通过“根据新情况重新评估”创建关联任务，选择原报告/有效专业结果；失败任务可创建关联重试，子任务可返回来源任务。
- 关联创建草稿与 request_id 保存在浏览器本地，网络响应丢失后刷新并重试沿用同一请求；修改要求或历史选择生成新请求身份。
- BLOCKED 显示后端请求的信息；表单支持 text、number、scale、boolean、single_select；后端验证类型、范围和必填项。
- 审查结果 PASS/REVISE/REPLAN/BLOCKED 各有独立展示，可查看审查历史。
- 任务失败、网络故障、SSE 断线与等待人工输入分别展示；执行中断时不会保留运行中的 spinner。
- 完整 Markdown 报告独立查看，GFM 表格/列表支持，禁用原始 HTML 执行；支持 `.md` 下载。
- E1.1 训练焦点建议面板：显示成果/审查来源、固定基线、条件和游戏执行支持；刷新适用性后数据变化标待重评，失效/替代建议保留历史。可以查看来源报告；E1.2分别记录采纳/拒绝/暂缓与独立用户自报执行，支持更正、撤回历史与重启恢复。自报数值不写入A事实。
- 任务历史搜索与重新打开；刷新恢复已选任务、计划、审查、结果和报告。

## 边界与持久化

`backend/models.py` 定义公共 DTO 与支持的 Event Types。C1.1 增加原输入引用、可用操作与 `message.created` 解释消息事件；解释不会重新发布 `result.created/report.created/mission.completed`。C1.2 增加 lineage 和 `POST /api/mission-continuations`，返回新 mission_id/message_id 及 created 标记。`backend/events.py` 是内部 Graph State 到公开快照/事件的唯一映射边界。前端只读取 Public API，不理解 graph node 或 AgentState。

事件 Envelope 保留 `event_id/type/mission_id/timestamp/sequence/data`。`data` 提供语义字段及公开 `snapshot`；事件与快照在同一 SQLite 事务中保存。前端按 Mission 与 sequence 去重，计划按完整版本替换，连接恢复或事件缺口时通过 HTTP 读取快照。HTTP 返回旧快照时不会覆盖更新的 SSE 缓存。SSE 支持 `Last-Event-ID` 与 `after` 重放，并发送心跳。

E1.1 的 `career_actions/models.py` 定义建议与独立业务事件 DTO。`GET /api/missions/{id}/recommendations` 只读核验原来源和最新同 context 数据，返回建议及 current/needs_reassessment/superseded/withdrawn；`GET /api/missions/{id}/recommendation-events?after=0` 提供 created/superseded/withdrawn 重放，每页最多 200 项。业务事件未加入 Mission SSE；消费者不能仅凭 created 判断当前有效或已采纳。建议列表由前端 Query 获取，任务变化、重新打开及“刷新适用性”重新核验。

默认保存目录：

```text
memory/web/live/     真实任务
memory/web/demo/     演示任务
```

任务目录包含 `workspace.sqlite3`（公开任务、对话、事件、报告，以及 C1.2 的完整固定输入和创建请求去重）；实际图运行还会按需创建 `checkpoints.sqlite3`（内部 checkpoint），演示任务不保证存在该文件。设置 `FAIT_DATA_DIR` 可覆盖目录；此时调用方应自行保持演示和真实模式数据隔离。Mission、初始消息/事件、输入及去重记录在同一事务创建；同一 request_id 不同内容返回 409。

M4.2将核心任务库升级为user_version=1，增加operations和request_receipts。首次创建/报告解释的`POST /api/messages`必填request_id；`POST /api/missions/{id}/input`必填request_id、当前blocked.pause_id及values。成功回执含operation_id/accepted/replayed；相同请求返回原回执，同ID异内容或旧pause返回409，缺身份422。Web在发出前保存完整待确认请求与草稿conversation，丢响应后刷新沿用身份，编辑换ID；新暂停清空旧表单。`GET /api/missions/{id}/operations`只读查看独立工作流/解释；中断解释不影响原报告。CLI普通创建、`--continue`、新增`--explain`可用--request-id；原回执重放不自动继续下一暂停。部署前先停写备份，在候选副本验证升级；本轮未升级实际工作区。详见[M4.2交接](../completed/M4_2_请求防重与暂停身份.md)。

E1.1 增加 recommendations/recommendation_batches/recommendation_events 三张表，记录与其业务事件同事务提交；交付和重启补投影防重，普通 GET 不写库。缺少合法成果、原 checkpoint 或完整输入时不生成当前建议，旧报告仍可查看。建议不改变球员事实，游戏操作一律待验证；未提供指标/单位/窗口时不展示效果结论。

E1.2增量建立recommendation_actions/recommendation_action_heads/recommendation_action_requests三表。`GET /api/missions/{id}/recommendations/{rec}/activity`要求career_id/branch_id/player_id查询参数；同一路径下POST decisions/executions分别记录选择与执行。请求要求context、建议revision和request_id，来源由服务固定；选择要求previous_decision_id（首次null），执行更正要求corrects_execution_id及原因。对象、当前状态、防重和事件同事务提交，同id同内容返回原记录，不同内容409。业务事件增加decision.recorded/execution.recorded/execution.corrected及对象/更正引用，仍不进入Mission SSE。表单在提交前保存完整请求，丢响应后刷新原样重试防重。详见[E1.2契约与验收](../completed/E_E1.2_玩家选择与执行记录.md)。

C1.3 的 CLI 默认使用独立的 `local_data/cli/fixture` 或 `local_data/cli/actual`，由 `FAIT_CLI_DATA_DIR` 覆盖。CLI 与 Web 复用任务应用和存储格式；每个任务目录使用进程写入锁，不允许两个服务同时写入，只读历史不占锁。`--continue` 可跨进程恢复原缺输入/报告审批暂停；旧 CLI JSON 元数据继续只读且不可恢复。详见 [C1.3 实施与验收](../completed/C_C1_会话恢复与任务延续.md)。

M4.1另在actual根建立`.actual-writer.lock`，约束受控观察导入及collector的绑定/整批提交/回执写入。同根另一个写线程/进程会得到`writer_busy`；importer返回CONFLICT且不宣称当前版本，collector明确拒绝。先等待原写操作完成，再显式重新读取版本/预览；不自动刷新CAS覆盖。不同任务目录不绕过actual锁，只读快照/历史不占actual锁。`--sole-writer`操作声明继续保留；部署时须先停止旧版写进程，不删除锁文件解锁。M4.3/M4.4已分别接入受监督执行和取消发布门，见[M4分项交接](../completed/M4_运行可靠性实施与交接.md)。

服务重启后，完成任务可只读查看与解释；BLOCKED 任务续跑前核对 checkpoint、等待原因与原输入快照。缺失或不兼容时保留旧任务，显示无法恢复，不重建初始状态。正在执行或尚未启动的任务会标记为 FAILED 并保留快照，用户可创建关联重试；重复提交旧创建请求仍返回原任务，不自动重启执行。

M4.6按operation独立处理重启中断，解释失败不会改写已完成的报告；CANCELLED保留。启动在cleanup_seconds内等待`.checkpoint-writer.lock`释放，未释放则拒绝打开任务库。暂停接收前同时核对操作/pause、固定输入摘要/版本和checkpoint中的完整固定集合；不兼容结构或版本明确拒绝，不能通过删除数据库恢复。业务已提交但计量未收尾的记录保留终态，缺失时间标为未知并停止失效的执行时钟。格式与验证范围见[M4.6交接](../completed/M4_6_重启政策与必要兼容.md)；停写备份/新目录恢复见[M4.7交接](../completed/M4_7_停写备份与新目录恢复.md)。

已取消任务保持CANCELLED，原暂停输入不能恢复；可用新的关联retry重新执行，已取消checkpoint候选不能引用为专业历史。取消解释保留原报告和生成计量。M4.5已接入用量/时间展示；生命周期兼容矩阵及证据见M4.6交接。

`GET /api/missions/{id}/runtime`只读查看工作流及各次解释的运行记录和累计观察。Web“任务运行信息”和CLI `--show`区分逻辑模型调用、SDK HTTP尝试、已知响应token及完整用量；缺usage、错误重试或中断时完整用量可为未知，已知部分不是完整账单。排队、执行、用户等待、总体墙钟分列；旧节点latency明确为“节点耗时累计”。原报告生成telemetry不因解释而改写。详细口径及本轮验证见[M4.5交接](../completed/M4_5_计量与运行信息.md)。

普通新 Mission 创建全新的 Runtime Context。关联任务在提交时冻结同一生涯/分支/球员的最新快照与选定历史，执行只读持久化输入；原报告（最多 12,000 字符，记录是否截断）和有效结果的投影进入实际 Manager/专业输入及指纹，旧 completed 子任务不被导入新任务为 completed。历史预算为 32,000 字符，超过时要求减少选择；尚未接通的 E 建议/评估 id 拒绝引用。最新数据不可用时不创建任务、不回退旧快照或 demo。

报告解释只传原目标、原输入引用、原报告（最多 24,000 字符）与当前 Mission 最近六条解释消息，不读取最新球员档案，不带入其他任务对话。工作队列串行执行；Agent 球员访问保持 A/B 的只读快照边界。演示模式仅验证关联创建/跳转流程，专业结果不当作已验证材料；实际历史提示注入由后端真实节点的模型替身测试验证。

`graph.py` 工厂未传 checkpointer 时默认使用 MemorySaver；CLI/Web 的真实运行由 `backend/runtime.py` 注入 SqliteSaver及报告审批中断点，固定的 continuation_context 进入执行输入。不能据工厂默认值推断持久化任务仍只保存在内存中。

## 生涯记忆（C2.1）

工作台按任务的冻结context显示“生涯记忆”。可明确设置目标/偏好、确认候选、更正/撤回并查看来源历史；“同步E来源记录”只读取该context内的权威事件和原对象，不从聊天或档案目标猜测。普通刷新只GET并核验来源，不产生记忆。C不改A事实或E行动。C2.2已接通相关性检索与固定输入：新任务及重评默认引用相关记忆，可关闭；重评可只读预览当前来源，正式提交再核验。“本次固定记忆输入”只读原集合，后续更正不改变原任务或解释。见[C2.2契约](../completed/C_C2.2_记忆检索与固定输入.md)。

接口为`GET /api/missions/{id}/career-memory`、同路径下`POST /sync`及`POST /user-records`。任务SQLite新增career_memories/career_memory_events/career_memory_requests，增量建表不清库。请求防重、更正版本、候选边界、时间域、来源失效行为及限制见[C2.1交付说明](../completed/C_C2.1_生涯记忆与来源.md)。

## 后续观察与比较（E2.1）

每条建议可在实际观察来源可用、当前快照仍等于原建议基线时确认指标、窗口及可选目标。新事实出现后不能为原建议追加挑选目标；既有规范继续比较原窗口。仅game/day和已应用观察可比较，版本/时间不一致默认不可比；窗口不足不判失败，用户自报不是游戏执行证明。

GET建议下`/comparison`只读，POST `/comparison-plans`冻结规范，POST `/comparison-plans/{plan_id}/assessments`显式生成/刷新。新增comparison_plans/assessments/assessment_requests三表，事件和失效/新版本同事务。A只读观察视图保留稳定来源和更正关系；fixture不补成真实观察，C2.2已消费比较引用，[E2.2](../completed/E_E2.2_反馈驱动关联任务.md)已接通“根据结果调整方案”，显式传递建议/评估版本、reason/request_id与执行引用；新任务保存固定反馈、原任务保留。`GET /missions/{id}/feedback-input`只读原集合，建议下`GET /followups`按context查关联任务。[M3指定本地PES2021范围已通过](../completed/M3_阶段三验收与交接.md)，包含连续十场及真实玩家反馈/新建议。详见[E2.1契约与验收](../completed/E_E2.1_后续观察与比较.md)。

## 停写备份与候选恢复（M4.7）

先停止声明单元的全部写者，再以JSON spec显式列出一个actual根与所有Web/CLI任务根。共用同一任务根只列一次；不同actual根分别建立单元。工具不会猜测当前页面外有哪些库。原生来源从观察中发现，未产生观察的binding可在native_datasets中补充；非原生原始文件使用file_sources显式映射。附加知识资料可用assets保留；密钥和.env不进入配置备份。

