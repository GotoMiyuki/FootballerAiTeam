# 文档管理规范

生效日期：2026-10-27。适用于本仓库后续开发与文档交付；历史文件保留原时点。本规范的交付单元是一次有明确目标、准备提交或推送的开发批次。同一批工作分多次补充push，可以维护同一份日志，不按commit数量机械增加文档。

阅读入口：[版本变化](../../CHANGELOG.md) → [开发过程](../development_logs/README.md) → [操作指南](../README.md#当前说明与操作) → [验收交接](../completed/README.md) → [报告与证据](../reports/README.md)。

## 1. 分类与权威出处

| 位置 | 主要内容 | 更新方式 |
| --- | --- | --- |
| 根目录CHANGELOG.md | 每个发布版本的变化、兼容影响和限制 | 准备阶段标待发布；实际发布后据事实补日期/Tag，不补造历史版本 |
| docs/development_logs/ | 每轮目标、设计取舍、实现、问题、验证和遗留项 | 每个完整交付批次一份；补记须标注编写日期、覆盖期间和依据 |
| docs/guides/ | 当前运行、配置、操作、排障及协作规范 | 行为改变时同步维护，注明更新日期；旧用法需要时移入历史说明 |
| docs/completed/ | 功能/里程碑最终交付、验收范围和接续边界 | 在验收节点形成；当前汇总链接分项及原证据 |
| docs/reports/ | 审计、实验、测量、故障验证及机器证据 | 按次保存版本/命令/结果，区分实现状态与验证状态 |
| docs/roadmap/ | 目标、依赖、里程碑与当前进度 | 有实现/验收依据后更新状态 |
| docs/plans/（新规划按需建立） | 后续任务书与实施计划 | 新任务按需创建；现有guides中的任务书/计划保留路径并在导航标明性质 |
| docs/templates/ | 可复用的日志/报告骨架 | 修改模板不回写既有历史文档 |
| docs/archive/、合并历史章节 | 旧方案、旧日志及迁移保留正文 | 保留原时点和摘要；不在preserved-source区域追加新开发过程 |

一条信息指定主要出处，其他文档用短摘要和链接连接。日志说明“为什么”，guide说明“现在怎么用”，report承载精确证据，completed作范围判定；摘要不能把限制或未验证内容省略成新的能力承诺。

## 2. 每轮应写什么

| 变更情况 | 必需记录 |
| --- | --- |
| 一轮有明确目标的开发或文档交付 | 一份[开发交付日志](../templates/开发交付日志模板.md)，记录代码/文档范围、实际验证、问题和遗留项 |
| 准备发布新版本 | 更新CHANGELOG的待发布条目，并链接交付日志/验收；不因写了条目就声明已发布 |
| 运行方式、配置、接口、存储格式或恢复行为变化 | 更新对应guide，日志说明兼容/数据影响 |
| 完成功能或里程碑验收 | 新增或更新对应completed汇总，链接实际验证证据 |
| 专项审计、实验或故障复现 | 在reports保存可复现证据，日志链接其结论；普通小修不强制新增专项报告 |
| 仅修正文案、链接或记录 | 沿用本批次日志或写简短文档日志；运行文档检查，不要求无关的全量业务回归 |

本次M4补记与管理规范属于同一文档补齐批次，结果并入[M4交付日志](../development_logs/2026-10-27_M4运行可靠性交付.md)，不再生成同内容的第二份总结。

## 3. 开发日志写作规则

使用[改良模板](../templates/开发交付日志模板.md)，保留“上下文—摘要—设计/实现—调试表格—下一步—人工随笔”六部分。必填信息缺失时标待核实并说明来源缺口，不猜日期、版本、提交、根因或测试结果。

- 上下文写真实分支、代码提交范围、实际版本与目标版本、Tag/推送/发布状态；日期与commit可核对。当前Codex分支沿用`codex/`前缀，不为套用示例改分支名。
- 设计说明选择理由、替代方案和边界；实现说明关键文件/函数/协议。允许用链接代替代码，代码片段仅放实现部分。
- 验证表包含执行日期/版本、命令或证据入口、结果及范围。明确“本轮新执行”“引用历史结果”“未执行/不适用”；重复执行不累计成唯一测试数。
- 调试时间线必须用Action/Observation/Decision表格。只记录确实发生的问题，区分产品、测试脚本、环境和原因未查明；无障碍可写“无”，保留表格，不编造错误。
- 真正阻塞、待验证事项、已知限制分开。未做真实模型/实机复核不自动意味着已验收的软件范围被阻塞，也不能写成已经验证。
- 下一步区分已确认待办与候选建议；没有已确认工作可写“暂无”。人工随笔标题保留，Agent不代写个人感想。

建议文件名为`YYYY-MM-DD_交付主题.md`。标题可写实际版本或目标版本，但目标须注明待发布；期号可用真实交付批次ID，不追补无依据的连续编号。

## 4. 证据与历史保护

原审计失败、旧验收数量和当时待办保留原结论。后续结果在新的报告/日志或当前汇总中说明，链接替代依据；必要更正追加日期、原因和新证据，不覆写旧事实。已有M4分项交接与报告继续保留，不批量搬迁或重排以免失去引用关系。

Git内优先保存小型文本证据、版本/摘要与可复现命令；本机SQLite、游戏原件、实际球员材料、截图和运行目录按既有忽略策略保留。引用本地材料须标明不随Git分发及复现前置条件，不将缺少私有材料的克隆环境写成已通过。密钥、完整环境秘密和无关实际数据不进入文档提交。

## 5. 交付前检查

1. 确认本轮日志覆盖实际变化，相关guide、CHANGELOG及路线图状态一致；按需维护验收和报告索引。
2. 区分目标版本与实际声明、已提交与已推送/发布；不预写将来才会成立的状态。版本升级、Tag、Release和push仍是独立操作。
3. 在仓库根目录执行`.\venv\Scripts\python.exe tools/check_docs.py`检查本机引用，使用`--portable`核对Git内文档；另运行`python tools/check_version.py`核对VERSION与前端元数据。历史正文摘要随两种模式检查，数量以实际输出为准。
4. 执行`git -c core.whitespace=trailing-space,space-before-tab,cr-at-eol diff --check`，检查实际差异，保留用户已有数据修改。
5. 日志如实记录本轮检查及未执行项；完成记录后再按本轮授权提交/推送。

`--portable`从Git索引取得文档集合，只有[本机引用清单](../local_references.json)精确列出的未跟踪路径才可单列，不豁免Git内文件、错字或锚点错误。清单项须说明用途和不分发原因；普通未跟踪文件即使在当前机器存在也判错。独立[文档CI](../../.github/workflows/documentation.yml)在Ubuntu/Windows验证链接、历史正文、版本一致性及检查器拒绝边界；私有材料内容与M4业务验收仍按各自证据判断。发布状态以实际Tag/Release和CI运行记录为准。
