## 1. M4交付目标和范围

交付一个本地单用户的 Career Companion：任务能够有界执行、明确取消、抵抗重复请求，并在退出、重启和备份恢复后保持可解释的数据状态。M1—M3已有的数据和业务边界继续成立。

正式验收至少回答以下六个问题：

1. 模型或工具卡住，任务何时结束，后续任务如何继续，应用能否有界关闭？
2. 用户取消后，哪些请求可能仍在进行，什么时刻起保证不再发布报告或产生业务效果？
3. 响应丢失、刷新或重启后再次提交，会复用什么结果，是否重复调用模型或写入记录？
4. 哪些原任务可以续跑，哪些明确失败并创建关联重试，是否始终使用原固定输入？
5. 两个写进程和损坏的恢复副本会被怎样拒绝，完整备份能否在新目录恢复？
6. 用户看到的任务状态、报告、建议、调用次数和耗时是否一致，未知用量是否明确为未知？

范围限定为当前Web/CLI、A事实、E行动/评估、C记忆和现有SQLite/checkpoint体系。沿用[M3交接](../completed/M3_阶段三验收与交接.md)的通过范围及其报告文字质量等限制。

本阶段不纳入PES底层写回、原生消息/新闻/训练/转会系统重构、多用户、云部署、自动交易、复杂预测、完整历史自动迁移、在线热备份或全面重写Agent。测试默认使用隔离目录与可控模型/工具；不重新安排十场实机验收。

## 2. 先固定的实施原则

### 2.1 保留现有中断恢复政策

- 缺输入和报告审批：校验原固定输入、记忆、反馈和checkpoint后，继续同一个Mission。
- 正在执行或已经创建但尚未执行的操作：异常重启后明确失败，记录中断原因，不自动重放。
- 已完成任务：报告和历史保持可读；解释是独立操作。
- 失败、超时或取消后重新评估：显式创建有关联的新任务，不把原任务偷偷恢复成运行中。
- 完成任务上的解释失败、超时或取消：只影响该解释，原Mission仍为COMPLETED，原报告与E/C记录保留。

这一政策不要求建设可自动续跑任意节点的持久队列。内存排队可以保留，但已接收请求的身份、排队记录与重启后的处理必须持久且明确；拒绝回执必须说明请求是否已被接收。

### 2.2 区分四类身份

| 身份 | 职责 | 生命周期 |
| --- | --- | --- |
| `request_id` | 标识一次用户提交，关联请求内容摘要和原回执 | 网络重试/刷新后沿用；改变意图或内容才生成新ID；相同ID异内容拒绝 |
| `operation_id` | 标识一个工作流或一次报告解释 | Mission工作流可跨两个暂停点；每次解释单独创建，不能混入原报告终态 |
| `run_id`或执行代次 | 标识一次被派发的执行段 | 原工作流从暂停恢复时生成新代次；旧进程结果不能提交到新代次 |
| `pause_id`或暂停版本 | 标识某一次具体等待用户的表单 | 新暂停必须换版本；旧表单即使字段相同也不能应用于后来暂停 |

这些身份由应用和存储边界持有，不进入Agent的领域推理职责。SDK内部网络尝试另外计数，不能当成新的用户请求或新的Mission。

### 2.3 统一终态决定和发布入口

拟新增Mission的`CANCELLED`状态；超时、中断和排队超时仍归入`FAILED`，用结构化原因区分。操作使用QUEUED/RUNNING/PAUSED/COMPLETED/FAILED/CANCELLED等有限状态；具体DTO和事件在M4.0核对后冻结。

取消与完成以应用层持久提交的先后为准：

- 取消先提交：旧执行代次无权发布结果；之后到达的模型、工具、checkpoint或事件不能把操作改回完成。
- 完成先提交：取消返回“已完成、未执行取消”，不追溯撤回已交付报告。
- 已取消/已失败操作：重复取消或重放原请求只返回当前结果，不重新执行。
- 解释操作被取消：原报告不参与终态竞争。

最终报告文本、公开报告引用、Mission/operation终态、对应消息与事件应在同一任务库事务内作出发布决定。E建议投影可以在完成提交后按现有身份幂等执行或恢复；投影暂不可用须如实显示，不能为了取消协议重做整个E系统。

所有提交必须同时检查操作身份、执行代次和允许状态。单独在UI隐藏按钮、只timeout Future、仅关闭SSE或要求Agent自行遵守取消，都不满足此边界。

### 2.4 执行隔离的首选方案

首选“一个本地协调进程 + 至多一个受监督的执行子进程”，保留串行执行，给排队设置容量。协调进程独占任务库的业务写入；执行子进程构造现有图、使用固定输入并持有当前checkpoint写入权，通过有限的结构化事件回传进度/结果。执行子进程不直接写workspace、A事实或E/C业务记录，模型工具维持既有只读权限。

取消或截止时间到达后，协调进程撤销提交权，并在限定宽限期内清理自己创建的执行进程。Windows下必须验证父进程被强制退出时的子进程清理，例如受约束的进程作业或等价的有界机制；不能把父进程任务锁释放误当成子进程已经停止。

这是待M4.0试验验证的实施选择。若可证明更小的方案同样满足卡死隔离、父进程崩溃、后续任务与关闭有界，可以替代；不能以泄漏线程或无限等待换取表面上的超时状态。不引入微服务、分布式任务队列或外部消息中间件。

### 2.5 配置与时间必须有明确含义

| 配置/指标 | 必须定义的内容 |
| --- | --- |
| 模型请求 | 连接/读取时限、单次逻辑调用总时限、最多网络尝试次数、可重试异常；显式传给所有角色和解释 |
| 工具调用 | 工具总时限；联网工具和本地RAG/计算使用同一个上层截止时间原则 |
| 执行预算 | 工作流实际执行段累计上限，恢复时保留已用预算；暂停和排队分别计时 |
| 队列 | 有限容量、最大等待时间、满队列拒绝回执；同request重放不能再次占位 |
| 取消/关闭 | 取消回执、清理宽限期与应用关闭的上限；取消已确认与进程已清理分别可观察 |
| 用户等待 | 缺输入/审批暂停不消耗执行预算；MVP不自动把等待过久当作执行超时，用户仍可取消 |
| 重试 | SDK网络重试、ReAct轮次、修订/重规划、关联任务重试分别有预算，核算嵌套上限 |

M4.0结合已有M3耗时材料和本地冷启动样本给出初始配置表，M4.3已接入服务并执行故障验证，见运行契约v1及交接。故障测试使用缩短时限，正常图冷启动复核使用正式启动预算。配置值不作为性能承诺。

### M4.0：冻结契约，先证明执行单元能被控制

**改动范围**：先交付设计与隔离试验；涉及`backend/models.py`、`service.py`、`store.py`、`runtime.py`和前端类型的后续接口，先定契约，不一起重写业务。

**工作**：

- 定义身份、状态、终态原因、暂停版本和cancel语义，说明旧Mission如何读取。
- 定义协调进程与执行子进程的任务库/checkpoint/事件所有权，防止两边无协调写同一业务记录。
- 在新隔离目录验证：正常结束、永久挂起后的清理、父进程kill后的子进程清理、再次启动并读取checkpoint。
- 冻结API、事件、配置及错误码草案；满队列与已接受但等待过久的操作必须区分。
- 定义首次升级前的停写副本办法，保证后续格式改动先在副本验证；不等待M4.7产品化完成才考虑保护旧数据。

**离开条件**：不访问游戏/模型服务、不修改实际档案，四个进程边界实验均有独立PID和时间界限证据；实现路线可继续复用现有图和E/C接口。若无法证明有界清理，此处先解决，不同时推进取消和界面。

### M4.1：修复actual写入互斥

**文件起点**：`player_data/imports.py`、`json_repository.py`、`game_adapters/pes2021_import.py`、现有`backend/writer_lock.py`；新增专用锁模块是否需要以复用边界决定。

**工作**：actual根的写锁覆盖读状态→CAS→提交，以及collector绑定/批次提交涉及的registry/receipt写入；约定可重入方式和锁获取顺序，避免collector持锁再调用importer时自锁。继续保留任务目录锁与JSON原子replace。多个只读应用共享actual可以成立，不增加不必要的全局独占读取锁。

**验收**：两个独立写进程不再同时确认互相覆盖的更新；持锁者退出后可继续；importer/collector组合、不同任务目录指向同根、并行只读访问均有证据。重跑观察防重、响应丢失重试、fsync/replace失败测试，原观察记录和事实摘要不被破坏。

### M4.2：补齐请求身份与暂停版本

**文件起点**：`backend/models.py`、`store.py`、`service.py`、`main.py`、`app.py`、`backend/cli.py`；`frontend/src/api/`、`useConversation`及创建/解释/暂停表单。

**工作**：

- 首次提交和解释保存request摘要、operation及原回执；相同请求重放先查回执，不重读最新A、不重新冻结输入或启动模型。
- 补信息/审批同时提交request和pause身份；回复丢失后可取得原回执，旧pause不能作用于新pause。
- 请求接收、关联业务记录、消息及回执尽可能在同一任务库事务；入队在事务外的中断沿用明确失败政策，不自动重放。
- Web在发送前持久保存未确认请求；刷新继续原身份，编辑意图才换身份。CLI支持可复用请求身份及查询原回执，不能每次重试悄悄换ID。
- 保留已有continuation、E行动/比较、C记忆的防重方式；不为了统一字段重写全部写入口。

**验收**：并发重复、响应丢失、刷新/重启重试、同ID异内容、旧表单发往后来同字段暂停，均检查任务数、入队数、模型数、消息数和业务记录数。重复请求不增加效果，新请求仍可正常执行。

### M4.3：统一时限、重试、排队和关闭

**文件起点**：`config.py`、`utils/helpers.py`、`agents/base.py`、`tools/`、`backend/runtime.py`、`service.py`、`cli.py`及拟新增的执行监督入口。

**工作**：

- 按M4.0契约接入执行单元，不重写Manager/Coach等角色逻辑；专业角色、Reviewer、Document与报告解释全部使用显式策略。
- 单次模型/工具的截止时间不晚于剩余执行预算；次数重试和退避时间一起计入预算。400/校验等确定性失败直接结束，可重试异常有限尝试。
- 有限容量和排队等待；先查已接收回执，再判断新请求是否有容量。队列满在持久接收前明确拒绝，不创建Mission/operation，可用同一request身份稍后重试；已接收后排队超时则记录失败结果，重放返回原结果。
- 关闭先停止接收新执行，再有限等待和清理本进程拥有的执行资源；已暂停任务保留，未完成操作明确中断，不无界shutdown。
- 超时统一撤销结果提交权；不可立即终止的网络请求可能继续由服务端处理/计费，不承诺撤销已发生费用。

**验收**：慢模型、慢工具、可重试/不可重试异常、队列满、排队超时、执行预算跨暂停累计、第一任务失控后的第二任务、有界关闭、主进程异常退出后无遗留写者。每项注明阈值、实测时间及允许误差；不能只验证等待方返回。

### M4.4：取消协议与统一发布门

**文件起点**：`backend/service.py`、`store.py`、`models.py`、`events.py`、`main.py`、CLI与前端Mission/解释操作控件；对`graph.py`只做必要的生命周期适配。

**工作**：提供带request和目标operation/pause身份的取消入口，操作回执返回是否接受、当前终态和清理进度。可以采用Mission下的operation取消接口；具体路由在M4.0冻结，不能通过取消“当前最新任务”误伤用户已切换到的新操作。

取消覆盖排队、执行中、缺输入、报告审批，以及完成报告上的独立解释。发布前在持久化层验证状态和run代次；报告、消息、Mission终态和事件统一作出决定。E投影仅消费已有效交付的成果；旧run的图结果只能保留为未发布内部材料。

**验收**：挂起→取消→放行迟到结果；重复取消；取消与完成同时发生；旧run事件到新run；取消后的刷新/重启；取消解释保留原报告。逐项核对报告、建议、E/C记录和后续调用次数。用户按钮、API拒绝及CLI输出一致。

### M4.5：计量及前后端运行信息

**文件起点**：`utils/telemetry.py`、调用封装、service解释路径、事件/DTO、前端计量和操作展示。

**工作**：区分逻辑调用与传输attempt，覆盖成功、失败、重试、修订、解释、续跑、取消和超时；解释用独立operation计量，原报告生成指标保持历史语义，再提供累计视图。缺usage显示未知，并区分已知部分合计与完整总量；进程被中止时也不把未取得的usage算作0。分别记录排队、实际执行、用户暂停和总体墙钟时间。

保留事件sequence、SSE重放、HTTP迟到保护。展示当前operation和可用操作，错误提示说明重试原请求、创建关联新任务或恢复资料的区别。日志用mission/request/operation/run关联，不记录密钥、完整提示或原始敏感异常。金额估算和监控平台后移。

**验收**：两次尝试的失败/成功计量、解释2次、跨暂停/重启和重复SSE重放；未知usage不变0，节点累计耗时不标作任务墙钟。执行真实HTTP/SSE和模拟迟到响应的前端测试。

### M4.6：重启政策与B4必要兼容

**文件起点**：`backend/service.py`启动处理、`runtime.py`、`task_context.py`、`utils/sessions.py`、格式版本/迁移入口、公开DTO；必要时修改结果适配点。

**工作**：

- 用operation而非仅Mission判断中断，包括“Mission已完成但解释运行中”的情况；CANCELLED不得在启动时被改写为FAILED。
- 有界清理或确认旧执行者已经退出，再启动新的checkpoint写者；不盲重放已有效果。
- 两暂停点保持原固定A、选定历史、C记忆、E反馈；缺失/损坏/错位/不兼容明确拒绝。
- 规定支持的任务库、固定输入、图checkpoint格式范围；新增表/字段采用小范围、可检查的升级。旧CLI元数据只读，不虚构可恢复任务。
- 保留Plan/Review/Hypothesis兼容表达，以共同的operation终态及发布门约束它们；仅修复可复现的正确性冲突。

**验收**：创建未入队、排队、Manager、专业Agent/工具、Reviewer、Document、报告提交窗口、两个暂停、完成、失败、取消/超时、报告解释等代表边界；正常关闭和独立进程kill/restart分开记录。完整旧版本迁移不作承诺，但明确支持或拒绝，不能删除checkpoint解决问题。

### M4.7：停写备份与新目录恢复

**文件起点**：新增独立本地备份/校验/恢复入口，复用Store、snapshot/checkpoint只读检查和写锁；更新运行/排障文档。

**工作**：

- 备份单元声明actual根及所有纳入的任务目录，允许Web/CLI目录分别列出；清单保留整库涉及的context，不能只导出当前页面球员而静默遗漏其他引用。
- 停止写入后取得相关锁，按固定顺序持有到备份结束；如果仍有服务或执行者占用则明确拒绝，不自动终止用户进程。
- 清单包含格式/代码依赖版本、摘要、context、两个数据库、固定输入/报告/E/C记录、collector绑定/回执、必要原始来源和非秘密配置。通过SQLite安全方式处理WAL，不把两个正在写的数据库分别热拷贝。
- 原生来源中的绝对路径采用显式路径映射与摘要校验，或完整保留可达依赖；不修改历史观察的语义hash。真实来源依赖缺失时不能声称完整恢复。
- restore先进入新候选目录，校验文件、SQLite、身份/版本、固定引用和两个暂停点，再输出配置切换步骤；预检失败不激活候选，不覆盖已有actual/任务目录。

**验收**：完整恢复核对事实版本、报告、E/C记录及两暂停续跑；恢复后的latest改变不污染原输入。缺checkpoint、坏库、缺来源、错context/版本/路径映射均有拒绝证据；重新运行恢复不产生重复业务效果。使用隔离副本验证真实格式来源，保持原M3数据字节不变，不操作游戏。

### M4.8：正式验收和交接

以新提交和新运行目录重建A—H检查矩阵；沿用审计中的“实现状态/验证状态”双轴。每个缺口关联实施提交、复现/回归命令与结果；失败区分产品、脚本和环境。

重新选跑受改动影响的M1—M3测试。137后端、7单元、8浏览器只是2026-10-26审计基线，不能直接计作实施后的结果。生命周期/DTO改动应补前端类型和构建检查；跨进程、取消、备份等必须保留新故障证据。

交付`docs/completed/`下的M4验收与交接、运行/排障指南更新和最终限制清单。只有所有阻断项和必要配套满足、有新验收证据，才能更新路线图的M4状态；M3原验收不回写成新的实机结果。

## 5. 数据、兼容和代码撤回约束

- 先把当前审计、计划和所需基线整理为可引用提交，再开始实施分支；不把用户已有`memory/player.json`、`memory/sessions.json`等改动自动加入提交。新工作区必须包含相应未跟踪文档/接口，不能从不含它们的旧提交重复实现。
- 共享的`backend/service.py`、Store、DTO/事件和前端类型按任务串行修改。`graph.py`/`loop_contracts.py`只处理必要适配，保持B结果权威边界。
- 每个任务记录正常/失败路径、依赖接口、数据影响、兼容措施和撤回方式。涉及schema时，旧代码是否能读新数据必须明确；不能默认撤回代码就能撤回数据，不能删除旧记录降级。
- 实施与故障实验使用新的`local_data/game_imports/m4-implementation/<run-id>/`或临时目录；fixture与actual分开；原审计目录保留原证据。
- 对现有工作区的升级先做停写副本与只读预检，再在候选副本验证；计划和开发测试不隐含授权覆盖实际球员数据或游戏存档。
- 默认确定性替身、真实HTTP/SQLite/checkpoint/独立进程；任何真实模型或实机复核要单独说明目的和范围，不能替代故障实验。

## 6. 可后移项和范围控制

| 可后移 | 保留理由/触发条件 |
