# 当前运行与排障指南

本指南按 2026-10-23 的源码核对，面向本机单球员工作台。历史设计、早期故障假设和旧日志保留其时间语境；复现当前问题时先核对这里的配置与入口。命令默认在仓库根目录执行，前端命令另行标出。

## 1. 先确认执行模式与数据源

这两组配置分别生效，不能互相代替：

| 配置 | 实际作用 |
| --- | --- |
| `FAIT_DEMO=1` / `0` | 确定性演示任务 / 真实 Agent 任务。`GET /api/health` 的 `mode` 只表示这一项。 |
| `FAIT_PLAYER_DATA_MODE=demo` / `actual` | 读取平铺样本 JSON / 读取受控的实际球员 Repository。默认是 `demo`。 |
| `FAIT_PLAYER_DATA_ROOT` | 球员数据根。actual 模式必须配置，并与仓库 `memory/` 根分离且不互相包含。 |
| `FAIT_CAREER_ID`、`FAIT_BRANCH_ID`、`FAIT_PLAYER_ID` | 指定同一生涯、分支和球员；必须与导入的数据身份一致。 |
| `FAIT_DATA_DIR` | Web 任务库与 checkpoint；默认 `memory/web/demo/` 或 `memory/web/live/`。 |
| `FAIT_CLI_DATA_DIR` | CLI 任务库与 checkpoint；默认 `local_data/cli/fixture/` 或 `local_data/cli/actual/`。 |

球员事实根与任务存储根是两种目录。使用真实模型不代表数据来自游戏；切换 actual 不会导入 PES 数据，也不会在缺数据时回退样本。演示模式下，球员面板仍读配置的 Repository；演示任务只绑定样本 Repository，不把 actual 数据作为确定性演示输入。

配置在进程中加载，修改后重启对应服务。依据：[配置](../../config.py)、[Repository 选择](../../player_data/repository.py)、[Web 启动与球员 API](../../backend/main.py)、[任务提交](../../backend/service.py)。

## 2. 安装与最小启动检查

```powershell
& .\venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-web.txt
```

在 `frontend/` 执行 `npm.cmd ci`。`requirements-web.txt` 是 Web 补充依赖，不代替核心依赖。若虚拟环境尚不存在，可先用已安装的 Python 3.10+ 执行 `python -m venv venv`。前端要求 Node.js 22.12+。

用于独立排查的演示后端示例（仓库根目录，单独终端）：

```powershell
$env:FAIT_DEMO='1'
$env:FAIT_PLAYER_DATA_MODE='demo'
$env:FAIT_PLAYER_DATA_ROOT=(Join-Path (Get-Location) 'memory')
$env:FAIT_CAREER_ID='demo-career'
$env:FAIT_BRANCH_ID='main'
$env:FAIT_PLAYER_ID='demo-player'
$env:FAIT_DATA_DIR=(Join-Path (Get-Location) '.web-test-data/manual-demo')
& .\venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

这里的球员样本只读，任务写入 Git 忽略的独立目录。另开终端，在 `frontend/` 执行：

```powershell
npm.cmd run dev
```

工作台为 <http://127.0.0.1:5173/>，API 文档为 <http://127.0.0.1:8000/docs>。独立终端检查后端：

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health
Invoke-RestMethod http://127.0.0.1:8000/api/player
```

`health` 成功但 `player` 返回 404，优先检查球员身份和数据是否已初始化；返回 503 时检查球员数据是否损坏或不兼容，不用替换为 demo 掩盖错误。恢复真实模型模式时，先停止上述后端，设置 `FAIT_DEMO='0'` 并按目标数据源重新配置后启动。

## 3. 前端无法连接或实时进度不刷新

| 现象 | 核对方法 |
| --- | --- |
| Vite 启动失败、5173 被占用 | `frontend/vite.config.ts` 使用 `strictPort: true`，不会自动改到 5174。停止占用进程或明确修改端口与相关配置。 |
| API 404、地址出现 `/api/api/` | `VITE_API_BASE_URL` 只填写后端 origin，如 `http://127.0.0.1:8000`，不加 `/api`；修改后重启 Vite。 |
| 浏览器 CORS 错误 | 当前后端只允许 `http://localhost:5173` 和 `http://127.0.0.1:5173`；来源改变需修改 `backend/main.py`，没有现成 CORS 环境变量。默认 Vite `/api` 代理指向 8000。 |
| 任务可通过 HTTP 读取，页面进度却停住 | 检查浏览器网络面板中的 `/api/missions/{id}/events` 是否保持连接；反向代理需支持 SSE 且关闭响应缓冲。 |
| 页面恢复一个不存在的任务 | 当前任务编号保存在浏览器 `localStorage` 的 `fait.mission`；点击“新建任务”清除选中任务，不需要删除服务端历史。 |

SSE 使用按 Mission 递增的 `sequence`，支持 `after` 与 `Last-Event-ID` 重放；每条事件携带公开快照。前端重连或发现事件缺口时通过 HTTP 恢复，并避免旧快照覆盖新状态。不要仅凭 SSE 断线推断任务执行失败。

依据：[Vite](../../frontend/vite.config.ts)、[API 地址拼接](../../frontend/src/api/client.ts)、[连接与恢复](../../frontend/src/hooks/useMissionEvents.ts)、[事件解析](../../frontend/src/api/events.ts)、[公开 DTO](../../backend/models.py)。

## 4. 写入锁、历史与暂停恢复

“任务目录已有写入进程”表示另一个 CLI/Web 服务持有该任务目录的进程锁。关闭原服务，或为独立实例配置不同任务目录；删除 `.writer.lock` 文件不是解锁方法。只读 CLI 历史不占写入锁。

```powershell
& .\venv\Scripts\python.exe app.py --list
& .\venv\Scripts\python.exe app.py --show <mission_id>
& .\venv\Scripts\python.exe app.py --continue <mission_id>
```

前两项只读原任务；`--continue` 仅恢复缺输入或报告审批等待点，需保留相匹配的完整输入和 SQLite checkpoint。旧 `memory/sessions.json` 只有元数据，不能恢复为完整任务。CLI 默认不会读取 Web 的任务目录；需要跨入口读取同一任务时，应显式对齐任务目录，并保持单写者。

服务重启时，完成任务保留供查看、解释；兼容的 BLOCKED 任务可从原等待点继续；执行中或尚未开始的任务标为 FAILED 并保留快照。checkpoint 缺失、损坏或等待原因不兼容时，界面显示无法恢复，不会重新制造初始状态。重新评估和失败重试创建关联新任务：

```powershell
& .\venv\Scripts\python.exe app.py --reevaluate <mission_id> "新的要求" --reason "数据变化" --request-id <new_request_id>
& .\venv\Scripts\python.exe app.py --retry <mission_id> "重试要求" --reason "原任务失败" --request-id <new_request_id>
```

以上参数中的尖括号是占位标记，执行时替换为实际编号。同一创建请求重试沿用同一个 `request_id`；改变内容后使用新编号。重复请求不会自动续跑已经暂停或失败的关联任务。

依据：[CLI](../../app.py)、[任务锁](../../backend/writer_lock.py)、[恢复校验](../../backend/task_context.py)、[只读 checkpoint 检查](../../backend/runtime.py)、[任务生命周期](../../backend/service.py)。

## 5. 模型、工具和知识库故障

真实 Agent 使用 `.env` 中的 `OPENAI_API_KEY`、`OPENAI_BASE_URL`、`MODEL_NAME`。查看任务的失败原因、审查可用状态与终止原因；模型失败、空输出、格式错误、必需工具失败或循环预算耗尽不会生成固定答案，也不能按“成功完成”解释。

`SearchTool` 缺少 Tavily 配置或模块时返回 `UNAVAILABLE`，无结果为 `NO_DATA`，执行异常为 `EXECUTION_ERROR`。它不会在自己的实现中自动调用 RAG。联网搜索为可选工具，其他必需工具失败会影响该次 ReAct 成果的有效性。

RAG 问题依次核对：

1. `knowledge/` 是否存在实际 PDF/TXT/Markdown 内容。PDF 由 Git LFS 管理；如果只有 LFS 指针，先恢复文件内容再重新评估检索。`git lfs ls-files` 可检查 LFS 跟踪清单。
2. 本地模型目录 `EMBEDDING_MODEL_DIR` 与 `RERANK_MODEL_DIR` 是否有效。目录不存在时，代码会使用配置的模型 ID，可能触发下载；不能把所有加载错误归因于 API Key。
3. 日志是否显示重排序降级。`RERANK_ENABLED=false`、候选不足或 reranker 异常会保留原始向量顺序；正常检索输出不代表本轮一定执行了精排。
4. `chroma_db/` 是持久化索引，新增语料不会自动保证现有索引更新。`tools.rag.reload_knowledge_base()` 会重新加载语料并写入现有集合，当前没有清空旧集合或基于稳定文档ID去重，不能保证干净替换、删除旧语料或无重复。运行前保留索引副本，用独立索引验证，不把它当只读健康检查。

RAG 评估入口是 `python -m evaluation.run_eval`。它会实际加载本地模型、访问/可能初始化索引，也可能下载缺少的模型；这里只说明入口，不将其当作无模型回归测试。

依据：[ReAct 终止与工具契约](../../agents/base.py)、[搜索](../../tools/search.py)、[RAG](../../tools/rag.py)、[精排与降级](../../tools/reranker.py)、[评估入口](../../evaluation/run_eval.py)。

## 6. 选择匹配问题的验证

后端当前确定性回归可从相关测试模块开始，不需要调用真实模型：

```powershell
& .\venv\Scripts\python.exe -m unittest evaluation.test_web evaluation.test_session_semantics evaluation.test_cli_persistence evaluation.test_reevaluation evaluation.test_recommendations -v
```

前端在 `frontend/` 执行：

```powershell
npm.cmd test
npm.cmd run build
```

Playwright 不会自动启动服务。先启动使用独立任务目录和样本数据的演示后端与 Vite，再在 `frontend/` 执行 `npm.cmd run test:e2e`；若使用已安装的 Chrome，设置 `$env:FAIT_TEST_BROWSER='chrome'`。未安装测试浏览器时才使用 `npx.cmd playwright install chromium`。历史日志中的通过数量只代表当次范围，不是当前全量测试总数。

`python -m evaluation.smoke_web_live` 是可选的真实模型验收，会消耗 API tokens。它复制样本到 `.web-test-data/live-*/player-memory`，保存运行日志与报告，并由脚本在报告审批点自动提交 `approved=True`；不要把它作为本节确定性测试的替代品。

依据：[前端命令](../../frontend/package.json)、[Playwright 配置](../../frontend/playwright.config.ts)、[真实模型验收](../../evaluation/smoke_web_live.py)。
