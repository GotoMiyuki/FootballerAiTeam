## 1. 目标、范围与开发顺序

E 要让系统能回答：建议是什么、玩家如何选择、实际是否执行、后来观察到什么、下一次为什么调整。近期只贯通一种经确认可在目标游戏中执行的建议及少量有来源指标，不把全部 Agent 的输出都改造成可执行行动。

**未指定子任务时先核对实施记录；E1.1 已完成，下一轮只执行 E1.2。** 一个子任务包含必要前后端与状态变化，不一次完成整条生涯系统。

| 子任务 | 交付目标 | 前置条件 |
| --- | --- | --- |
| E1.1（已完成） | 将有效成果中的建议变成有来源、适用范围的记录 | A/B 接口；D 可执行能力表仍待验证 |
| E1.2 | 玩家采纳/拒绝/暂缓与独立执行记录 | E1.1 |
| E2.1 | 关联后续观察，进行可复核的目标/指标比较 | E1.2、A2.2；真实路径需 D2 |
| E2.2 | 玩家触发关联新评估，完成连续生涯验收 | E2.1、C1.2；相关记忆接入 C2 |

E1 可先用确定性样本验证结构与交互；目标游戏的具体可执行性待 D 证据确认。E2.1 的比较算法可离线开发，真实闭环验收必须使用真实游戏观察或明确人工反馈。F2 校准预测不是 E2 必需前置，E 不借此发明风险/身价算法。

C2 消费 E 的事件。建议先确定本指南的对象/事件语义，再按顺序 E1.1 → E1.2 → C2.1；E2.1 产生评估事件后完善 C2.2，最后贯通 E2.2。C1.2 的后续任务入口先由 C 交付，E 调用它。

实施前读取适用 AGENTS.md、最新源码和已合并接口；保留已有修改。当前预设球员档案仅为样本，无需修复历史污染；真实选择/执行/观察记录不得因演示初始化或模型输出而产生。

## 3. 核心不变量

| 编号 | 要求 |
| --- | --- |
| I1 | 模型建议、用户采纳、实际执行和观察结果是四件不同的事 |
| I2 | 生成或采纳建议不改变实际能力/比赛记录；事实仍只由 A 受控导入 |
| I3 | 建议有 source Mission/subtask/result version、固定输入快照和适用范围 |
| I4 | 失败、未经规定审查或已失效成果不能冒充当前可采纳建议 |
| I5 | 玩家能否执行由目标游戏/模式证据决定；无法执行的内容明确为叙事/辅助建议 |
| I6 | 执行证据缺失时维持未确认，不因时间经过或比赛发生而推断执行 |
| I7 | 无可比数据不生成有效率、改善分或达标结论；未知与零分别表达 |
| I8 | 观察到的变化不自动证明由建议导致 |
| I9 | 同一点击/反馈/观察重复提交不重复记录、评估或新建任务 |
| I10 | 不同生涯、分支和球员隔离；回档/更正不混入同一比较窗口 |
| I11 | 新评估使用明确的新身份与最新固定输入，保留旧报告和行动历史 |
| I12 | C 的记忆投影能够追溯 E 原记录；模型摘要不能成为行动权威状态 |

## 4. 对象与事件契约（E 拥有，C 消费）

字段名可调整，但必须先定义最小模型与应用接口，再接消费者；本节不要求新的事件平台或后台消息队列。

### 4.1 建议 Recommendation

| 字段 | 语义 |
| --- | --- |
| recommendation_id、revision | 稳定记录与版本；同一来源投影重复执行不重复创建 |
| context | career/branch/player，来自任务冻结输入 |
| source | mission/subtask id、result source_version、payload 位置、审查版本与输入指纹 |
| content | 用户可理解的建议、预期目标、依据和限制 |
| applicability | 适用条件、数据快照、游戏版本/模式、有效窗口 |
| execution_support | 已验证可操作 / 明确人工选择 / 待验证 / 辅助叙事及证据引用 |
| evaluation_spec | 可比较指标、基线引用、单位/量表、观察窗口；无法比较则明确原因 |
| validity | current / needs_reassessment / superseded / withdrawn；不与用户选择混用 |

source 的 payload 位置必须绑定结果版本，不能把数组下标当跨版本稳定建议 id。修改建议形成新版本/新关联，不把已经采纳的原建议原地改成另一项内容。

### 4.2 选择 Decision 与执行 Execution

选择为明确用户操作：ADOPTED / REJECTED / DEFERRED，记录 decision_id、recommendation id/revision、context、时间、可选理由和 request_id。选择改变追加新事件并关联前次，不能抹掉历史。

执行是独立记录：UNKNOWN / CONFIRMED / PARTIAL / NOT_EXECUTED，记录实际行动、窗口和来源。来源至少分为用户明确反馈与游戏观察；有 A 观察时保存 observation/source_record 引用。用户自报只能证明其明确反馈，不能自动认证游戏统计或能力值。

“采纳”不触发自动执行；“已执行”不能凭一个按钮把预期增长写进 A。首版允许玩家明确填写执行反馈；除非游戏提供直接证据，不自动检测每项行动。

用户撤销采纳不等于过去的执行未发生；执行记录更正需要显式关系。允许记录未采纳但实际尝试的行为，保留选择与执行差异，不为了状态机简单而强制它们相等。

### 4.3 评估 Assessment

保存 assessment_id/revision、建议和执行引用、context、比较规范版本、基线/后续观察 id 与快照、单位/时间域、具体指标值/变化、缺失信息、限制和被更正关系。

分别表达证据状态与目标判断：证据可能 COMPLETE / INSUFFICIENT / INCOMPARABLE；目标可能 MET / NOT_MET / UNDETERMINED。执行不明时仍可报告观测变化，但不能把它命名为“建议有效”。

C 消费明确事件，例如 recommendation.created/superseded、decision.recorded、execution.recorded/corrected、assessment.created/superseded。每项含 event_id、schema_version、对象 id/revision、context、source 引用与时间。初期可在同一 SQLite 中按需读/重放；源版本和撤回要能检查，不依赖即时推送才保证有效。

公开 SSE 如需新增事件，保持现有序号与 snapshot 约定，连同 DTO、解析器、缓存和 UI 一起交付。E 的业务事件不必全部塞入 Mission 的执行事件枚举，可使用独立查询/业务事件流；同类状态只定义一套语义。

## 5. E1.1：有效建议投影

2026-10-02 已完成：映射版本 `training-focus-v1` 从有效 `skill_training.focus_areas` 逐项保存建议，绑定 Mission/subtask/result version/位置及输入/审查引用。交付和服务启动时幂等投影；GET 只读核验来源及最新同 context 快照，数据变化/不可核验标 `needs_reassessment`，来源失效退出当前状态，原报告与基线保留。

新增只读 `GET /api/missions/{id}/recommendations` 和 `recommendation-events?after=0`，业务事件为 created/superseded/withdrawn，独立于 Mission SSE；C2 消费事件仍需核验当前来源和有效性。当前执行支持一律待验证、比较规范未定义，未实现 Decision/Execution/Assessment 或 C 的建议引用解析。73 项后端回归、7 项前端单元测试、生产构建及 16 个浏览器场景通过，最后来源完整性补充后 10 项 E 专项通过；均使用隔离数据与模型替身，见实施记录。以下保留原实施要求供复核。

1. 建立只读的 Mission 成果访问适配，获取 B 已验证、有效、符合规定审查的 subtask payload 与输入引用。不能从 `domain_outputs[Agent]` 或报告非空推断建议有效。
2. 首版从选定 capability 的结构化字段确定性投影，例如明确的 recommendation 条目或训练焦点。只选一种可解释映射，不改全部专业 Agent schema。
3. 报告自由文本如需抽取，模型只能产生带原文位置的候选，用户核实后成为记录；不得给抽取文本伪造已验证专业来源。默认不新增抽取模型。
4. 来源唯一键含任务、子任务、结果版本与条目身份；重复投影不重复建议。同一 Agent 多任务分别定位，不按字符串相似度合并。
5. 建议当前有效与旧任务历史可用分别表达。新球员数据不改旧任务固定快照；对当前采纳则检查适用条件。首版无法证明跨版本仍适用时标 needs_reassessment，不自动承诺可继续执行。
6. D 还未证明的游戏操作标“待验证”，允许查看/讨论，但不能用其作为真实可执行闭环里程碑。营养、恢复等游戏不支持内容标辅助叙事；原报告仍可阅读。
7. UI 展示建议来源、依据、条件、执行支持和可比较窗口；不是只加一个“采纳整份报告”按钮。

验收：合法来源投影正常；FAILED/UNAVAILABLE/INVALIDATED 的成果不产生当前可采纳记录；重复投影稳定；同 Agent 多任务隔离；旧数据适用性不足有标记；无法执行内容不会被伪装成可观察行动。

## 6. E1.2：选择与执行记录

- API/application 分别提供选择与执行操作，检查 context、建议版本和当前适用性，payload 不能任意指定另一个球员或 source_type。
- request_id 防重，同 id 不同内容冲突；事件与对象当前投影在同一任务数据库事务中提交。明确本地单进程支持范围，不扩成 G 的通用队列/取消控制。
- 已过期/失效建议的历史选择可查看；当前采纳需先重新评估或重新核实适用性。拒绝旧建议可作为历史选择记录，不把它恢复为有效建议。
- 执行表单记录实际内容和时间/比赛窗口，未知维持未知；时间域不一致不强行排序。用户点击“我执行了”最多形成 user_reported 执行，不生成比赛或能力事实。
- 用户反馈包含现实数值时，E 默认只保存反馈引用与来源标签；若要进入 A 事实，必须另走明确人工核实应用入口和 `ObservationImporter`，不得用聊天采纳自动导入。
- UI 分别显示“选择”“执行”和“等待观察”；支持更正/撤回关系，不因刷新、重复点击或更正丢历史。
- C2 读取 E 事件形成记忆，E 不自行写一份自由摘要到模型短期缓存冒充长期记忆。

验收：采纳不改 A 快照/hash，不增加实际属性；采纳与执行可不同；重复请求一次生效；更正有原记录引用；跨 context/无效版本拒绝；刷新和重建服务后记录可恢复，待执行不显示为已经执行。

## 7. E2.1：后续观察与比较

### 7.1 数据来源与窗口

通过 A 的只读 snapshot/origins/观察引用查询形成观察视图，不读写散落实际 JSON。若现有公开读取缺少稳定观察引用，先做 A 的小范围只读扩展；不把 matches 的数组索引当永久比赛身份。

只使用目标 context、目标球员、指定时间域/量表/窗口中的有效观察。APPLIED 历史或当前投影与 RECORDED_ONLY 原记录分开；未应用记录不自动进入普通成果比较。若需评估归档原件，必须定义独立策略并标来源，不静默混入。

窗口可为“后续 N 场有效比赛”“明确游戏日期区间”或已核实选择后的事件范围。现实提交时间不能代替游戏顺序；没有可排序事件证据时返回无法比较。根据 D 可读能力选择指标，不硬要求有不存在的训练数据。

基线在建议/选择时冻结并引用真实数据；不能在比赛结束后挑一个有利基线。实际已采纳执行的历史建议可用于其原观察窗口评估，不因新数据出现抹掉过去行动；对未来再次采纳则另查当前适用性。

### 7.2 比较方法

首版采用可复核的确定性比较，不新增“成长收益评分”：同字段前后值差、窗口内出场场数/时间、有效评分均值或明确目标是否达到。每项必须有一致字段、单位、量表、样本数及计算规则；游戏版本或量表不同默认不可比。

| 情况 | 输出 |
| --- | --- |
| 基线与后续数据可比且充足 | 具体前后值/变化、样本数、目标判断与限制 |
| 部分比赛字段缺失 | 有效样本数和缺失项，不将缺值补零 |
| 窗口尚未达到 | 待观察/INSUFFICIENT，不能当 NOT_MET |
| 回档或分支混合、时间不可排序 | INCOMPARABLE，说明需要绑定或确认 |
| 执行情况未知 | 可显示观测变化，执行关联未确认，不能结论“建议有效” |
| 一场表现更好 | 只报告变化；不声称训练建议造成提升 |

目标阈值必须来自明确用户目标或既定规则及版本；无法定义时只比较变化，目标 UNDETERMINED。不同位置/赛事/出场时间的样本不足以自动形成因果或公平优劣判断，保留限制。

新观察不足时不调用模型补造评估。更正/撤销源观察后，旧 assessment 标 superseded，基于新证据生成新版本；不得原地改旧评估数值而保留旧来源。D 回档新分支不追加进主线窗口。

验收：可计算结果与手工核对一致；明确零值纳入、缺失排除并计数；窗口未满不判失败；同观察重复读取不重复评估；更正后旧版不可作为当前结论；不混时间域/分支/球员；执行未知和因果限制展示准确。

## 8. E2.2：反馈驱动关联新任务

1. 在评估面板提供“根据结果调整方案”。玩家操作调用 C1.2 的后续应用入口，包含 parent Mission、recommendation/assessment 版本、reason、新约束与 request_id。
2. C 冻结最新 A 快照与相关 C2 记忆，E 提供有效执行/评估短投影和来源。不是把旧报告最后六条消息交给单次问答就算新分析。
3. 提交前检查评估是否因更正失效；若最新事实已变化，明确实际提交使用的最新快照，保存当时选择的评估版本及限制，不在任务运行中继续变动上下文。
4. 默认由玩家触发，不每导入一场比赛就自动创建任务。重复点击/重试通过 C request_id 返回同一新任务。
5. 新任务失败按 B 表达未输出结果；原建议、选择、执行与旧报告仍可查。新建议关联来源，不自动把旧采纳状态移到新建议。
6. 建议记录 → 选择 → 执行 → 观察 → 评估 → 新任务的关系可逐项查看；C 的记忆引用和 B3 的实际 prompt 中包含此次相关反馈，不只新增装饰性来源字段。

真实生涯里程碑：同一明确游戏版本、生涯/分支中至少连续十场有来源记录；至少一项明确采纳或拒绝，其中至少一次有可核实执行反馈；至少一次基于后续观察的新评估与新建议。字段不足时调整可观察目标，不能模拟十场比赛冒充实测。

离线样本可以证明接口联通，真实模型建议质量和真实游戏采集分别记录验证范围，不将界面点击成功等同建议有效。
