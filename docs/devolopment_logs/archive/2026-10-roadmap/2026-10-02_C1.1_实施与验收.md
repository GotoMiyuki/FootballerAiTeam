# C1.1：历史、解释与暂停续跑——实施与验收

日期：2026-10-02

范围：按总路线图与 C 方向任务书完成 C1.1，保留工作区已有 A1–B3 改动。没有实施 C1.2/C1.3/C2、游戏接入或行动/反馈存储。

## 1. 交付行为

| 操作 | 任务身份与材料 | 验证结果 |
| --- | --- | --- |
| 查看、刷新、选择历史 | 原 Mission，只读取任务、报告、消息；暂停任务可只读核验 checkpoint | 不执行节点，不调用模型，不读取最新球员状态 |
| 解释旧报告 | 原 Mission；原目标、原输入引用、原报告与本任务最近六条解释消息 | 不执行专业图；原报告、结论、审查和数据版本保留 |
| 解释失败、空输出或非文本输出 | 独立解释消息标记 FAILED，原 Mission 保持 COMPLETED | 不发成果/报告/任务完成事件，不生成固定答案 |
| 补充缺失信息 | 原 Mission、原 SQLite checkpoint 与原球员快照 | 跨服务重建续跑，继续既有审查/修订路径 |
| 确认生成报告 | 原 Mission，明确布尔审批；同一原快照 | 审批后仅执行 document；普通聊天文本不能代表批准 |
| 原 checkpoint/快照/等待位置缺失或不兼容 | 旧任务保留只读，显示无法恢复 | 校验失败发生在追加消息、改变状态或执行节点之前 |
| 根据新情况分析 | 用户明确选择“根据新情况新建任务”，进入独立任务草稿 | 不重跑旧任务；本轮没有实现 parent/reason/request_id 的关联评估 |
| CLI `--continue` | 只读旧会话元数据，明确无法恢复原执行 | 不要求模型配置，不创建初始状态，不构建图，不改旧索引 |

## 2. 接口与实现

- `MissionView.input_reference` 持久化提交时的生涯/分支/球员身份、state_version、snapshot_id 与允许公开的来源类型。引用只投影身份和版本，不携带本机路径、原始来源引用或内部图状态。
- `verification=VERIFIED` 表示已从 Repository 固定并记录输入引用，不表示测试样本是真实游戏观察；`source_types=demo_fixture` 仍显示为测试样本。确定性演示任务使用 `DEMO`；缺少新字段的旧记录为 `UNVERIFIED`，不反查当前数据来补造旧来源。
- `available_operations` 根据任务状态、报告发布门槛、等待原因和恢复错误投影 view/explain/supply_input/approve_report；历史 GET 只读检查可恢复性，不修改存储。
- `MessageRequest.intent` 增加 `explain`。旧 `followup` 兼容：完成任务默认解释；缺输入仅兼容单一 information 文本字段，并经过相同表单校验；多字段等待和报告审批必须使用表单。
- `MessageView` 增加 kind、operation_status、in_reply_to。解释仅发布新增 `message.created`，SSE 保留原有完整公开快照、Mission sequence 去重与消息刷新机制；旧成果事件的含义保持不变。
- `inspect_checkpoint` 使用只读 SQLite 连接和相同图拓扑的不可执行节点读取状态，不初始化表、不构造真实模型。恢复前核对等待节点、原快照结构及输入身份/版本；实际运行时再次核验。连接均关闭。
- 解释不绑定工具，不读取 Repository 或 checkpoint，不加入其他任务消息及未经分类的旧聊天。材料仍受原报告 24,000 字符和六条解释消息预算限制；生成新方案的要求被明确指向新任务。
- CLI 历史行为同步 README 与会话索引说明。检查时另修复既有报告节点的未定义变量，并取消未发布正文的打印回退与“流程完成”提示；同进程审批路径有专项验证。

主要改动：`backend/models.py/service.py/runtime.py/main.py`、新增 `backend/task_context.py`、`app.py/utils/sessions.py`、前端任务/对话/审批入口与事件类型。没有重写 B3 调度、结果失效、审查或存储表结构。

## 3. 验收证据

后端命令（仓库根目录）：

```powershell
& .\venv\Scripts\python.exe -m unittest evaluation.test_session_semantics evaluation.test_looping_plan evaluation.test_web evaluation.test_dependency_context evaluation.test_result_invalidation
& .\venv\Scripts\python.exe -m compileall -q backend app.py utils\sessions.py evaluation\test_session_semantics.py
```

结果：33 项测试通过；编译检查通过。其中 C1.1 专项 6 项覆盖只读历史、解释失败、v1/v2 隔离、跨服务重建续跑、恢复缺失/不兼容、CLI 元数据历史和同进程报告发布门槛。多个失败情形使用 subTest，不另计为独立测试数量。

前端命令（`frontend`）：

```powershell
npm.cmd test
npm.cmd run build
$env:FAIT_TEST_BROWSER='chrome'
npm.cmd run test:e2e
```

结果：7 项事件单元测试、TypeScript/生产构建和 10 个 Chrome 浏览器场景通过。浏览器场景包含四种确定性 demo 流程、三个已有失败/失效/旧记录契约场景，以及三个 C1.1 场景：解释失败仍能读取原报告、审批只提交布尔表单、缺 checkpoint 时禁用续跑。

新增浏览器用例首次把任务 result 字段误当作页面正文定位；改为通过报告入口核验原正文后，专项及最终完整 10 场景均通过。前端测试与构建遇到沙箱上级目录读取限制，获准在沙箱外执行；没有安装依赖或下载浏览器。

后端使用临时 SQLite、临时球员目录、真实图路由/Manager 修订与确定性专业节点；解释使用模型替身。浏览器 demo 数据隔离在忽略目录 `.web-test-data/c1-1-browser/`，语义场景使用公开接口替身。没有调用真实模型、采集游戏数据或更新实际球员事实。本记录的通过数量来自本轮执行，未引用旧记录数量。

## 4. 数据、兼容与回退

- 新字段存入已有 SQLite JSON 任务/消息快照，不新增第二套球员真值，不修改实际球员档案。完整输入快照仍在既有 checkpoint；首次执行前的内存缓存持久化属于 C1.2/G 后续工作。
- 旧快照/消息缺字段时使用明确的未验证引用和 task 消息类别；不将旧元数据推断为可恢复执行，不迁移或修复历史测试样本。旧报告仍按现有发布门槛读取。
- 没有新数据库表或破坏性迁移。撤回代码不要求重建球员数据；旧客户端不认识 `message.created` 时应一并回退前后端，或通过 GET 刷新历史消息。
- 没有承诺运行中崩溃自动恢复、多进程写入协调、长期记忆、真实游戏闭环或最终正文全文语义审查。CLI 跨进程恢复仍待 C1.3。
