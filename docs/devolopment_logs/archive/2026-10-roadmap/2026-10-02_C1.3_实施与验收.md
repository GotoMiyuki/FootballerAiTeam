# C1.3：CLI 持久化暂停恢复与历史入口——实施与验收

日期：2026-10-02

范围：按 C 方向任务书完成 C1.3，保留已有 A/B、C1.1–C1.2 修改。CLI 复用现有任务应用、固定输入与 SQLite checkpoint，不重写执行图或新增另一套任务状态。没有实施运行中崩溃自动恢复、跨数据库灾难恢复、长期记忆或 E 业务闭环。

## 1. 交付行为

| 命令/场景 | 结果与身份 |
| --- | --- |
| `python app.py "需求"` | 创建并持久化新 Mission、完整输入、消息/事件，使用既有运行时执行 |
| 缺输入或报告审批时输入 `q` | 保留 BLOCKED 与 checkpoint，退出并关闭连接；打印原任务 id 与恢复命令 |
| `--continue <mission_id>` | 先只读核验原等待节点、原快照身份和版本；仅支持缺输入/报告审批，再从原状态续跑 |
| 缺输入恢复 | 原 Mission，明确补充的信息经现有表单校验进入原 checkpoint，再进入既有局部修订路径 |
| 报告审批恢复 | 回车/y/yes/确认代表明确批准；只续跑 document，不重做 Manager/专业节点 |
| 普通文字或重新规划要求出现在审批提示中 | 不当作批准，不触发重规划；要求有效输入或保存退出 |
| `--list`、`--show`、已完成任务的 `--continue` | 原任务与原报告只读，不构造执行运行时、不要求模型配置、不读取最新球员状态 |
| `--reevaluate/--retry` | 调用 C1.2 的关联创建入口，新身份、最新固定输入、lineage 与持久化请求去重 |
| 重复关联创建请求 | 返回同一原创建结果，不隐式恢复该任务的暂停；恢复必须使用 `--continue` |
| 原 checkpoint、快照、版本或等待位置无效 | 在追加消息、修改任务或执行之前拒绝；不重新创建初始状态冒充恢复 |
| 旧 `memory/sessions.json` 元数据 | 仍显示未验证历史和不可恢复说明，不覆盖或迁移为新 Mission |
| 同目录第二个 CLI/Web 写入进程 | 启动时明确拒绝；只读历史可同时读取，关闭服务/进程退出后写入锁释放 |

## 2. 运行与数据目录

基础依赖 `requirements.txt` 增加 `langgraph-checkpoint-sqlite==3.1.1`，与现有 Web 版本一致；本轮使用已安装依赖，没有安装或升级包。

CLI 默认任务根按球员数据模式隔离：

```text
local_data/cli/fixture/   以测试样本作为输入的 CLI 任务
local_data/cli/actual/    actual 模式 CLI 任务
```

可通过 `FAIT_CLI_DATA_DIR` 指定任务根。真实球员输入仍由 A 的 `FAIT_PLAYER_DATA_MODE=actual`、`FAIT_PLAYER_DATA_ROOT` 及身份配置控制；任务目录不替代球员事实库。CLI 默认根独立于可重建的平面样本 `memory/*.json` 和 Web 目录；没有将真实任务索引写回旧样本根。

每个目录复用 `workspace.sqlite3` 与 `checkpoints.sqlite3`，保存 C1.2 的完整固定输入及既有任务/消息/报告/事件。`local_data/cli/` 已加入忽略规则。`.writer.lock` 为操作系统文件锁载体，文件存在本身不表示占用，不需要用户删除它。

```powershell
# 可选：使用指定的独立任务根
$env:FAIT_CLI_DATA_DIR='C:\football-data\cli-tasks'
& .\venv\Scripts\python.exe app.py "制定训练安排"
# 在审批或缺输入提示处输入 q 保存退出，使用打印的 mission_id
& .\venv\Scripts\python.exe app.py --continue <mission_id>
& .\venv\Scripts\python.exe app.py --show <mission_id>
& .\venv\Scripts\python.exe app.py --list
& .\venv\Scripts\python.exe app.py --reevaluate <mission_id> "每天只有20分钟" --reason "新比赛" --request-id request_new_01
& .\venv\Scripts\python.exe app.py --retry <failed_mission_id> "重新尝试" --reason "明确重试" --request-id request_retry_01
```

实际任务保存后，后续命令需指向同一任务根。关联请求的同 id 同内容返回同一任务；编辑要求/原因须换新 request_id，省略时 CLI 生成并打印。CLI 当前默认只引用来源报告，专业结果的显式选择仍由 C1.2 API/UI 提供。

## 3. 实现与协作边界

- `backend.cli.CLIMissionService` 是现有 MissionService 的阻塞适配，仅等待现有队列 Future；执行、暂停校验、输入、固定快照、审查、发布和关联创建继续使用同一应用代码。
- `app.py` 使用显式命令区分只读历史、原暂停恢复及关联新任务。旧的重复 Agent 构建替换为持久化 runtime 工厂；直接图流式/报告打印帮助函数保留兼容，实际 CLI 不再创建 MemorySaver 图。
- `SessionRepository` 通过只读 SQLite 连接投影任务身份、conversation、原输入引用、格式和记录位置；不新增第二份可变会话状态。目录不存在时读取返回空，不创建目录或初始化库；连接显式关闭。旧 JSON 管理函数保留兼容，新的 CLI 执行不调用旧创建/更新函数。
- 续跑先只读检查，使用现有 `validate_pause()` 验证原状态；实际服务与执行运行时再校验。恢复不调用 `create_initial_state()`，不读取当前 Repository 来替代旧快照。
- `backend.writer_lock.WorkspaceWriterLock` 在 MissionService 初始化、读改任务之前取得目录锁，Windows 使用 msvcrt，其他平台使用 fcntl。CLI 与 Web 都执行同一守卫；只读索引/历史不占锁。服务关闭或启动失败时释放锁和连接。这只是落实单写入进程约束，没有实现分布式锁、多个执行 worker 或写入平台。
- `requirements.txt`、`config.py` 与忽略规则完成 CLI 依赖和根目录配置；`graph.py`、B3 路由、专业 Agent、发布条件及前端本轮没有改动。

## 4. 验收证据

实际运行的完整命令：

```powershell
& .\venv\Scripts\python.exe -m unittest evaluation.test_cli_persistence evaluation.test_reevaluation evaluation.test_session_semantics evaluation.test_looping_plan evaluation.test_web evaluation.test_dependency_context evaluation.test_result_invalidation -v
& .\venv\Scripts\python.exe -m compileall -q app.py backend utils\sessions.py config.py evaluation
```

结果：**50 项后端测试通过，编译检查通过**。其中 C1.3 新增九项专项，其他 41 项来自本轮实际重跑的 C1.1/C1.2、Web、执行、依赖与失效回归，不引用旧轮通过数量。

`evaluation.cli_process_fixture` 在独立 Python 进程中执行生产 `app.main()`，仅替换模型配置和节点工厂，保留真实 MissionService、LangGraph 路由、SQLite checkpoint 与表单/审批适配。调用真实模型的入口被替身明确禁止。专项验证：

1. 进程一停在审批后退出；球员从 44 改为 99；进程二只执行 document，仍使用速度 44 的原快照，Mission id、输入版本与完整固定输入不变。
2. 缺输入暂停在进程一保存；进程二补充信息并完成原局部修订，停在报告审批；进程三批准并交付。记录三种不同 PID，补充信息存在原 checkpoint，报告只生成一次。
3. 已完成的 list/show/continue 不要求模型配置、执行运行时或最新读取，任务库和 checkpoint 内容保持不变。
4. 丢失 checkpoint、缺原快照、错版本、错等待原因均在变更前拒绝；旧元数据和不存在的目录不被初始化为可恢复执行。
5. CLI 关联评估/失败重试生成新身份、保留来源，固定最新输入；同 request_id 跨进程重试不重新执行或恢复。
6. 同目录第二个写入进程被拒绝，只读历史可读取；原写入者关闭后可继续恢复。
7. 普通文字不能替代报告审批，退出保持原暂停和任务内容。

首次七项专项运行发现两个测试检查问题：SQLite 测试连接的 context manager 没有关闭连接，导致 Windows 临时目录清理失败；内部 human_input 节点不属于模型工厂回调，不能用该回调统计它。改为显式关闭测试连接，并核验补充信息及实际局部修订节点；新增审批/重试场景后，最终完整 50 项通过。

本轮未改前端，也未重跑前端构建或浏览器场景，C1.2 的前端结果仅保留在对应历史记录。所有数据来自临时样本根与任务根，未调用真实模型或游戏、未更新实际球员事实。没有下载、安装依赖或新增外部服务。

## 5. 兼容、回退与限制

- 新 CLI 使用现有 Mission/固定输入格式，没有破坏性表迁移，也不迁移旧 JSON 样本。`mission_id` 同时作为 checkpoint 的 thread_id，旧 JSON 的 thread_id 保持其原含义。
- Web 默认根和 API/SSE 契约不变。新增的进程锁会拒绝以前可能同时打开同一目录的多个写入服务；使用独立根或关闭原服务后再执行。
- 撤回 C1.3 时可保留 CLI 的两份 SQLite 库及锁载体文件，不删除球员事实或任务记录。旧 CLI 不读取新目录，暂停恢复应使用 C1.3 版本；不要用旧 MemorySaver 实现声称原执行已恢复。
- 仅保证支持的 BLOCKED 位置。运行中/排队任务重启仍按既有策略标记 FAILED，缺 checkpoint 的历史不重建；运行中中断/取消、超时与任意节点自动重放仍归 G。
- 进程锁只约束任务目录，不实现球员库和任务库的跨数据库恢复或备份平台。CLI/Web 任务默认隔离，不提供自动双向迁移。
