## 2. 球员数据接口与配置

### 2.1 只读入口

`PlayerRepository.read_snapshot(context)` 返回 `PlayerSnapshot`。快照含 `profile/training/matches/career/metadata`，读取属性返回副本；`to_dict()` 用于 Graph/checkpoint 序列化。`snapshot_scope()` 让 Agent 内工具读取任务已冻结的数据。

上下文是 `PlayerContext(career_id, branch_id, player_id)`，三个标识各限制为 1–64 位字母、数字、下划线或连字符。路径解析同时检查目录边界，拒绝路径穿越与符号链接越界。

`metadata` 包含 `schema_version/state_version/snapshot_id`、来源与质量标记。版本是不透明值，消费方只比较相等性。来源映射将字段或历史记录指向样本标识/观察标识；实际数据另提供来源类型、provider、原始/确认引用以及采集与生效时间。

规范投影保留当前领域字段，过滤样本中的预测顶层字段和非规范别名，并记录 `ignored_fields`。未修复历史污染、未猜测别名真值。职业历史估值仍保留在 `estimated_value_eur`，不改成已观察市场价值。

缺字段保持缺失，显式 `null` 保持未知，数值 `0` 保持零。伤病 `"None"` 表示明确记录无伤病；缺失或 `null` 不代表健康。原始游戏量表须由 D/F 提供明确适配，本轮规范能力值为 0–100，其他特征使用各自量表。

### 2.2 两种数据模式

| 配置 | 用途 |
| --- | --- |
| `FAIT_PLAYER_DATA_MODE=demo` | 默认；显式只读 flat JSON 样本适配器 |
| `FAIT_PLAYER_DATA_ROOT` | demo 可指定替代样本根；actual 必填，且不得与仓库样本根重叠 |
| `FAIT_CAREER_ID`、`FAIT_BRANCH_ID`、`FAIT_PLAYER_ID` | 当前应用上下文；任务提交后固定，不随之后的数据切换改变 |
| `FAIT_DEMO=1` | 独立的工作流演示模式；不等同于球员数据模式，不作为真实运行失败的降级入口 |
| `FAIT_DATA_DIR` | 任务 SQLite/checkpoint 存储；与球员数据根是不同配置 |

例如真实档案配置：

```powershell
$env:FAIT_PLAYER_DATA_MODE='actual'
$env:FAIT_PLAYER_DATA_ROOT='C:\FootballerData\actual'
$env:FAIT_CAREER_ID='career-01'
$env:FAIT_BRANCH_ID='main'
$env:FAIT_PLAYER_ID='player-01'
```

实际档案聚合位于 `contexts/<career>/<branch>/<player>/state.json`。缺档案时读取失败，不自动建档、不复制 demo 数据；API 缺数据返回 404，损坏或不兼容数据返回 503。配置独立根不会自动导入观察。

旧 `PLAYER_FILE/TRAINING_HISTORY_FILE/MATCH_HISTORY_FILE/CAREER_HISTORY_FILE` 配置只接受同一个样本目录；与显式根矛盾时拒绝，不让 API/工具各读一份数据。

应用可通过 `create_app(player_repository=..., player_context=...)`、`MissionService(...)`、`create_initial_state(..., repository=..., context=..., snapshot=...)` 注入数据。工具公开读取函数保持原有形状，内部统一读取快照。

### 2.3 受控导入

导入接口仅供受信采集/人工确认应用调用，不注册给模型，未新增 HTTP 事实写入端点。调用方必须在模型之外验证采集来源或人工确认凭据；载荷中的 `source_type` 标签本身不提供权限。

```python
from player_data.models import PlayerContext
from player_data.json_repository import JsonPlayerRepository, EMPTY_VERSION
from player_data.imports import Observation, ObservationImporter

context = PlayerContext('career-01', 'main', 'player-01')
repository = JsonPlayerRepository(
    actual_root, fixture_root=fixture_root, context=context,
)
importer = ObservationImporter(repository, source_type='user_confirmed', provider='manual')
# 这些值来自应用已验证的确认过程，不能直接采用模型建议。
observation = Observation(
    context=context, observation_id=confirmed_observation_id,
    source_type='user_confirmed', provider='manual',
    collected_at=timezone_aware_collection_time,
    effective_at=confirmed_real_effective_time,
    time_domain='real', time_precision='instant', kind='profile_patch',
    payload=confirmed_domain_fields,
    expected_state_version=current_version,  # 首次初始化使用 EMPTY_VERSION
    confirmation_reference=verified_confirmation_reference,
)
result = importer.import_observation(observation)
```

支持 `profile_patch/training_record/match_record/career_event`。游戏观察要求 `game_version/adapter_version/source_record_id/raw_reference`；人工确认要求独立的 `confirmation_reference`。游戏生效时间保留 day/month/week 精度，现实时间使用有时区 instant；未知生效时间必须为 `None` 且精度为 unknown，不用采集时刻猜测游戏日期。

| 导入结果 | 行为 |
| --- | --- |
| APPLIED | 观察和事实投影一起提交，新版本生效 |
| RECORDED_ONLY | 观察归档并更新聚合版本，不覆盖当前事实；用于未知时间、稀疏历史、旧/同时间或无法比较的更新 |
| DUPLICATE | 同 provider/observation_id 同语义重试，返回已提交版本，不再次写入 |
| CONFLICT | 同观察 id 内容变化，或新观察的期望版本已过期；不写入 |
| REJECTED | 来源、身份、字段、数值、时间或更正引用非法；不写入 |

防重语义不包含重试的采集时刻与 CAS token。显式更正使用新 observation id 和 `corrects_observation_id`，保留旧观察；只有可比较且对应当前来源的更正才能更新投影。历史追加不会覆盖当前球员属性；其来源的时间域保留可追溯。

每个上下文的事实、来源、观察、防重索引、revision/hash 放在一个聚合 JSON 中。同进程按上下文路径加锁，同目录临时文件序列化、flush/fsync 后原子 replace；序列化、同步或替换失败保留旧档案。损坏数据明确报错，不通过空状态重置。

**限制：仅支持单写入进程。** 进程内锁不保证跨进程竞争；hash 是完整性检查，不是来源签名。原子替换与 fsync 不宣称提供所有文件系统/断电条件下的灾难恢复。跨进程一致性、备份、取消和全面恢复留给 G。

## 3. 执行、审查与发布契约

| 层次 | 状态及意义 |
| --- | --- |
| 执行 | SUCCEEDED / NO_RESULT / FAILED / BLOCKED；未形成结果、技术故障、缺必需外部输入分别表达 |
| 子任务 | COMPLETED 只表示专业输出已通过接受校验；FAILED 不映射为业务修订；INVALIDATED 表示旧结果不可用于当前交付 |
| 专业结果 | `validated`、`validity`、递增 `source_version`、`input_fingerprint/input_material`、球员与依赖版本引用 |
| 审查 | NOT_RUN / COMPLETED / UNAVAILABLE；未完成时 decision 为空，不认证 reviewed_subtasks |
| 交付 | NOT_GENERATED / PUBLISHABLE；正文 hash、检查范围、被审查结果版本单独记录 |

全部计划子任务默认必需。PARTIAL 可表示有限观察，但未授权为完整依赖或 Mission 完成；本轮没有新增 Mission.PARTIAL。内部技术故障终止为 FAILED，不让用户补造数据来“修复”；必需外部信息缺失才进入 BLOCKED。

ReAct 退出原因包括 FINAL、BUDGET_EXHAUSTED、MODEL_FAILED、EMPTY_OUTPUT、INVALID_CONTENT、TOOL_ERROR。实际工具调用记录 call id、SUCCESS/ERROR、required、error_type 与有效观察。SearchTool 为可选补充检索，其失败保留为限制；其他当前工具失败不能用后续模型文本冒充成功结果。

专业 schema 校验字段/类型/当前可解释数值范围，排除 bool、NaN、Infinity，不校准科学规则。Plan 校验 id、capability、目标、依赖存在/无环、预算，不接受规划器自报 completed。Reviewer 必须覆盖当前必需结果，严重 finding 不能通过删除范围变成 PASS；REPLAN 要有核心证据，INFO/LOW 不触发无意义循环。

当前发布策略是 **专业输入审查 + 正文确定性门槛**：检查非空、模式、明确任务要求、依据与限制、支持的带标签球员数值及引用 URL；记录 `semantic_review=NOT_PERFORMED`。数值检查覆盖年龄、身高、体重、综合评分等支持标签；未声称验证全部散文、所有数据陈述或引用语义。正文改变后原 hash 无效，支撑结果改变后旧专业审查与交付均无效。

报告生成前的人类确认不代表生成后的正文已审核。CLI/UI 已准确标明审查范围。`MissionService.complete()` 复核当前发布契约，报告 GET/下载和前端按钮还需当前 COMPLETED/PUBLISHABLE。

新增公开事件：`subtask.failed/subtask.invalidated/agent.failed/review.unavailable/review.invalidated`。保留有效子任务的简要专业结果；公共 DTO 不传原始提示词、工具参数与异常堆栈。旧记录缺少审查可用性或发布元数据时显示未验证，旧结果无指纹不能自动复用；没有实施全面历史迁移。

## 4. B3 输入与失效

统一上下文包含 Mission/subtask/Plan 身份、capability/goal、全局与局部约束、实际使用的关键假设、该子任务范围内已确认反馈、固定球员上下文/快照/版本，以及显式依赖的有效 payload、版本、证据与限制。首轮和修订共享构建入口，提示词实际注入；无关 Agent 字符串与全部观察历史不作为依赖来源。

依赖按 capability 最小完整字段投影，超过 64,000 字符明确失败，不简单截断关键证据。上下文为副本，上游文本不会增加工具权限或控制路由。祖先结果指纹变化时，即使直接依赖还带 completed 标签，也拒绝消费；损坏循环同样拒绝。

输入指纹覆盖结果契约版本、capability/goal/purpose、Mission objective、约束、实际使用假设、确认输入、A 的快照与状态版本、依赖集合与 source_version；Plan 版本、优先级、展示语气和读取时刻不造成伪失效。使用整份球员版本进行保守失效，未实现字段级影响分析。

修订目标与传递下游立即失效，独立有效任务保留。重规划先校验新 Plan，再按依赖拓扑认证复用；删除任务转为失效历史，新增任务或相同 id 新语义不能继承旧 Agent 输出。结果变化撤销 PASS、reviewed_data、Document 聚合、正文、摘要和发布状态。Reducer 使用明确的有效性与删除标识，不能靠空字典假定清空旧键。预算耗尽不保留假 completed。
