## 1. 目标与默认范围

D 负责从用户电脑上的游戏个人生涯获得真实、可核对、可重复读取的数据，再转换为 A 能接收的观察。近期只选一款游戏、一个明确版本、一个测试生涯，不同时开发 PES 2021 与 FC 26 两套完整适配器。

**未指定子任务时只执行 D0.1。** 不因用户提到游戏，就预设存档格式、安装某编辑器、猜内存地址或创建假采集数据。

| 子任务 | 交付目标 | 前置条件 |
| --- | --- | --- |
| D0.1 | 本机环境、个人生涯需求与可读字段调查 | 无；可独立于 C/E |
| D0.2 | 候选方式证据与首个试验方案 | D0.1 |
| D1.1 | 对隔离原始样本做读取、身份与字段验证 | D0.2 已选定方法，有明确样本 |
| D1.2 | 验证指定游戏环境下的重复采集与运行影响 | D1.1，明确采集方法/工具/测试存档范围 |
| D2.1 | 原始记录转换、预览及受控导入 | D1，现有 A2.2 |
| D2.2 | 生涯/分支绑定、回档与更正行为 | D2.1 |

D0 先产出证据，D1 先证明采集，D2 才写实际应用数据。D2 不需要重新实现 B 执行图。D 完成不会自动触发模型分析或玩家操作；后续任务归 C/E。

执行前读取适用 AGENTS.md、最新代码和已合并接口。当前预设球员档案属于测试样本，无需修复历史污染；真实采集原件、来源标记与实际生涯隔离必须正确。

## 2. 已有接口与边界

| 接口/文件 | 当前可复用能力 | D 需要补充 |
| --- | --- | --- |
| `PlayerContext` / `PlayerSnapshot` | 生涯、分支、球员身份；固定快照和来源版本 | 游戏标识到内部 context 的明确绑定 |
| `PlayerRepository.read_snapshot(context)` | 统一只读状态 | 导入后核对投影与来源，不直读散落 JSON |
| `JsonPlayerRepository` | 每上下文受控 JSON，独立实际根 | 复用，保留单写入进程约束 |
| `Observation` / `ObservationImporter` | 来源、时间、版本、字段校验，防重与原子提交 | 原始记录解析、可追溯映射与可信调用入口 |
| `player_data/schema.py` | 当前能力字段采用规范 0–100；其他特征各有量表 | 逐字段证明语义/量表映射，不能仅因数值落入范围就导入 |
| `execution_context.py` | B3 使用固定 context/snapshot/version | 导入只影响后续读取，不修改在途任务 |
| 当前仓库 | 尚无已验证的游戏采集模块 | 新增独立 `game_adapters/` 或等价目录 |

游戏观察支持 `profile_patch/training_record/match_record/career_event`。Observation 已要求：context、observation_id、source_type/provider、采集时间、生效时间与精度、kind/payload、expected_state_version；游戏来源还需 `game_version/adapter_version/source_record_id/raw_reference`。更正用新观察 id 和 `corrects_observation_id`，不得偷偷覆盖旧观察。

导入结果已有 APPLIED、RECORDED_ONLY、DUPLICATE、CONFLICT、REJECTED。**RECORDED_ONLY 已保存观察并改变聚合版本，但未更新当前事实投影**；不可显示为“球员状态已更新”。后续任务不能把归档但未应用记录混成当前事实。

没有单个观察内的多 kind 事务，也没有整批跨文件原子保证。D 可以逐项导入、显示每项结果并通过防重续传；不得宣称整次采集批次全部成功或全部回滚。若闭环确需新领域字段/一致快照，先提出小范围 A 接口变更及消费方，不绕过 importer。

## 3. 核心不变量

| 编号 | 要求 |
| --- | --- |
| I1 | 采集来自已核实的目标个人生涯和球员，不将队伍统计或经理生涯数据冒充个人记录 |
| I2 | 原始数据保留游戏版本、模式、采集方法、字段路径/页面来源和内容摘要 |
| I3 | 未提供、未读到、解析失败、明确零值分别表达；不补造 RPE、负荷或比赛统计 |
| I4 | 采集、映射和应用导入分层；模型不拥有游戏工具或事实导入能力 |
| I5 | 采集不写回游戏属性、存档或比赛结果；目标是单机个人生涯读取 |
| I6 | 游戏内时间与现实采集时间分开；没有游戏日期不能以今天代替 |
| I7 | 身份、路线或游戏版本无法确认时不自动导入当前档案 |
| I8 | 同一记录重读不重复生效；相同记录变化走冲突/更正，不生成第二场相同比赛 |
| I9 | 预设/合成样本标为 fixture；不能因为从适配脚本读取就认证为游戏观察 |
| I10 | 导入错误有明确结果；原实际状态可读，不靠清库、删除档案或回退 demo 解决 |

## 4. D0：本机可行性调查

### 4.1 D0.1：环境和字段需求

在明确安装目录、常见启动器记录和已有配置中做有限只读调查。若安装位置无法确认，先完成不依赖路径的需求/接口盘点，再询问缺失位置；不要默认遍历整块磁盘或读取无关个人文件。

记录：游戏准确名称/版本与平台、个人生涯模式名称、补丁/mod 环境、已有导出工具及版本、测试存档候选、读取方式所需条件。每项注明“本机已验证/文档证据/待验证”，不能把用户说“装了游戏”当成完整兼容结论。

最小需求分层：

| 优先级 | 数据 | 验证重点 |
| --- | --- | --- |
| P0 | 生涯/球员身份、快照关联、当前属性或综合评分 | 能绑定正确 context，可核对字段语义 |
| P0 | 可排序的比赛事件与目标球员参与情况 | 能区分单场、重复读取与缺失记录；可用比赛顺序不一定有完整游戏日期 |
| P1 | 对手、赛事、出场时间、评分、进球/助攻等实际可读项 | 按每个游戏/模式核实，不假定全部存在 |
| P1 | 游戏日期/赛季、角色、合同与发展事件 | 记录精度和可观察范围 |
| P2 | 细粒度比赛技术统计、训练选择/成长事件 | 有证据才加入，不作为首次读通的必需条件 |

“未踢完”“替补未出场”“未提供统计”要有可解释区别；统计属于全队还是个人也须标明。训练无法读取时允许先以比赛为闭环来源，不生成虚拟训练数据补空缺。

### 4.2 D0.2：候选方法与试验方案

比较候选：存档副本解析、游戏/已有工具导出、屏幕读取或用户核实输入、指定版本的进程内读取。列出实际覆盖、个人生涯兼容证据、稳定性、运行影响、维护成本和可核对方式。

查外部资料时核实日期和适用版本，优先官方资料或工具项目的一手说明/源码，保存页面链接或 commit。本文没有断言 Sider、Live Editor 或其他工具能读取目标个人生涯；经理模式功能、第三方介绍或旧版本截图不足以证明。

D0 不安装或启动新的接入工具、不注入进程、不修改游戏文件。其产出是具体方案：指定方法、版本、样本取得方式、读取字段、执行范围、停止条件和验证步骤。涉及工具安装或改变游戏启动环境的试验，另在 D1.2 的明确任务范围中安排，不隐含在调查里。

首选有证据支持、影响小且能重复的方式，不预设技术路线。没有可靠自动化方案时，可先使用带截图/页面引用的人工核实样本验证 A/E；必须标为人工来源，不能宣称自动采集已完成。

交付 `docs/D0_游戏接入可行性_YYYY-MM-DD.md` 或同等报告：候选比较、首个游戏选择、字段覆盖、尚未证明的环节、可执行 D1 试验。证据不足时明确原因，仍完成已能完成的调查，不写一个永远返回 demo 的适配器。

## 5. D1：采集与样本验证

### 5.1 D1.1：离线原始样本读取

新增独立适配模块，最低职责为：读取器、raw envelope、字段映射、context binding 和预览。它们不依赖 Agent/Graph 的具体类型，不直接改 `memory/player.json`。

原始 envelope 至少记录：capture_id、schema/game/adapter version、采集方式、目标模式、采集时间、身份候选、游戏内时间/精度、原始文件或页面引用、内容 hash、采集质量与错误。身份未确定可先保留 raw，不生成实际 Observation。

- 存档读取只操作明确的副本；保留原游戏存档，对读取前后摘要做核对。
- 导出文件保留原件与导出环境；复制未完成的文件不直接解析为完整快照。
- 屏幕读取保留页面/截图与字段位置，不用模型编造看不见的属性；识别不确定字段必须核实或保持未知。
- fixture 原始样本只进入 fixture/quarantine 根。真实测试存档样本仍标记其真实来源与测试用途；需要导入时明确绑定独立测试生涯，不能混入用户实际当前档案。
- 第一个样本要覆盖可核对的球员快照和至少一场实际记录；仅读取菜单标签不算比赛数据采集完成。

验收用原始样本对照游戏页面/可信导出：身份和字段准确、未知不填零、异常格式明确失败、同样本结果确定、只读原件、适配器不产生任何实际档案写入。

### 5.2 D1.2：重复采集与运行影响

在已指定游戏版本、采集方法和测试存档上进行：首次读取 → 重复读取 → 正常游戏推进 → 再次读取 → 采集失败/停止。首版可手动触发一次采集，不要求后台常驻监控或自动操控游戏。

核查重复导出身份、事件范围、文件完整性与新增记录；仅验证游戏未退出不足以说明采集稳定。记录读取耗时、是否要求特殊启动方式、失败后能否停止、是否改动存档/游戏字段、如何核对结果。

若方法需要进程内宿主或编辑工具，分别验证宿主影响与读取脚本影响；脚本只读不能证明宿主没有修改行为。安装、运行、路径和测试存档必须在该轮具体试验范围中写清楚，不能顺手换工具或扩展到其他模式。

验收至少含三个不同游戏推进节点和相同节点的重复采集；连续比赛数据不足时给出实际覆盖，不以合成比赛补齐。D1 结论注明“离线读取已验证”“真实运行采集已验证”各自范围。

## 6. D2.1：映射、预览与受控导入

### 6.1 字段映射

每个规范字段记录：原始路径/页面、意义、单位/量表、转换规则、适用游戏版本、缺失与错误行为。语义不同的 PES/FC 属性不能只按名字相似合并。

当前 A 的属性 0–100、比赛 rating 0–10、特征 1–5/1–8 是规范契约，不证明游戏原值与之等价。可直接对应的字段以证据确认；不支持的值先留 raw/扩展记录，不截断或硬缩放来通过校验。需要新增规范字段时提交小范围 A schema 变更；解释/预测校准移交 F。

不导入未观测的训练负荷、RPE、现实疲劳或伤病概率。游戏给出的属性/评分可以是观察，模型解释与未来收益仍为推断/预测。未知值不更新已有事实，显式 null 只有来源明确表示未知且字段允许时才接受。

### 6.2 身份、时间与防重

- 内部 context 由已核实的生涯绑定记录决定，不能仅凭球员姓名、俱乐部或当前窗口标题。
- D2.1 在首次导入前就必须核实一个目标的绑定；D2.2 再扩展持久化绑定、切换和回档流程，不能等到 D2.2 才确认 D2.1 已写入的是谁。
- 保存 native 生涯/球员/事件 id（若存在）与内部 id 的映射；内部标识遵守 A 校验规则，原始标识不直接拼接磁盘路径。
- observation/source_record id 优先来自稳定原始身份；无稳定 id 时使用已定义的、包含上下文和事件语义的确定性摘要。不能只用采集时间、比赛日期或内容里同一组进球数。
- 同一场多个页面/批次的字段应先合并并核对为一个候选事件；不能作为多场比赛追加。无法辨别重复比赛时进入待绑定/待确认，不猜测唯一身份。
- effective_at 保留游戏内 day/month/week 精度；只有比赛顺序而无日期时保留顺序和 raw，effective_at=None/unknown，按 A 可能 RECORDED_ONLY。不能把赛季第 N 场伪造为日期。
- 对同一游戏日期多次属性快照，A 当前保守时间策略可能不应用后续变化。需要同日顺序契约时先做明确的小范围 A 扩展，不能伪造时间绕过限制。

### 6.3 导入应用入口

先显示 dry-run/预览：目标 context、原件引用/hash、规范 payload、映射版本、未知/拒绝字段、拟新增或更正的记录。dry-run 不写球员 Repository。

配置 `ObservationImporter(repository, source_type='game_observation', provider=...)`，仅受信采集应用调用；不注册模型工具，不从 payload 自报来源获取权限。原件引用必须确实对应采集记录，hash 是完整性证据，不是来源真实性证明。

首建上下文使用 `EMPTY_VERSION`，实际根独立且无 demo 基线。导入前读取当前版本；逐项消费返回版本。遇到 CONFLICT 不无限读新版本重试覆盖，先区分正常重复、更正、并发或绑定错误。

APPLIED/DUPLICATE/RECORDED_ONLY/CONFLICT/REJECTED 分别展示。批次部分成功时保存每项结果与原件引用；响应丢失后重试通过 A 防重，不整批补建另一组新 id。导入失败不输出虚假“球员状态已更新”。

导入应用必须遵守单写入进程：若使用 CLI，明确实际数据写入入口不会与另一个进程并发写；若接 Web，同进程调用受控服务，不新增绕过验证的通用写 JSON API。跨进程锁/后台调度归 G。

## 7. D2.2：分支、回档与更正

建立明确的 context binding 表，记录游戏版本/生涯身份、内部 context、确认依据和最近核对位置；不是模型可写的球员事实工具。

| 发现情况 | 默认处理 |
| --- | --- |
| 同一记录未改变、再次采集 | 使用原身份重试，DUPLICATE |
| 同一事件统计更正 | 新观察显式关联旧观察；不追加第二场 |
| 读取较早存档 | 停止更新当前路线，提示选择历史归档或新 branch |
| 同日期/赛程重新踢比赛 | 无法确认是否重踢时待确认；明确重踢归指定新分支 |
| 球员/生涯身份改变 | 要求新绑定；不沿用旧 context |
| 游戏/补丁或 adapter 版本改变 | 重新核对字段映射；不默认认证兼容 |

日期倒退可作为回档线索，不能作为唯一检测；身份/赛程/原件差异都须检查。没有足够证据时拒绝自动导入比静默混写更正确。

新分支首版默认独立上下文，不自动复制全部主线历史。若需要共同历史，显式定义 parent branch、分叉位置和共享只读基线，再安排 A/C 小范围扩展；不得复制历史后丢失观察来源。对旧比赛更正的处理还须区分真实修正与另一条重踢路线。

D 不自动续跑或撤销在途任务。已有任务仍引用原快照；更新后由 C/E 创建最新快照的新评估，记录版本差异。

## 8. 验收、文件责任与交付

| 场景 | 必须满足 |
| --- | --- |
| 首个原始样本与页面对照 | 正确个人生涯/球员；字段、单位和缺失可解释 |
| 再次读取同样本/同事件 | 身份稳定，不重复比赛/属性增长 |
| 不支持版本、损坏/半写文件、识别不确定 | 明确失败或待核实，不用 demo 替代 |
| 预览与导入 | 预览零写入；提交只走 A，结果与投影核对一致 |
| 真实游戏未提供训练/技术字段 | 未知保持未知，不产生人工生成统计 |
| 更正、旧存档、重踢、另一生涯 | 不混入当前路线，不静默覆盖 |
| 部分批次失败/响应丢失 | 显示逐项结果，防重续传，不虚报全成功 |
| 模型分析正在执行时导入 | 原任务快照不变，后续评估读取新快照 |

主要新增范围：`game_adapters/`、受信采集命令/应用层、隔离样本、来源 manifest 和专项测试。通常不改 `graph.py`、专业 Agent 或 C/E 任务逻辑。必须改 A schema/应用 API 时先完成小范围接口任务与消费方，不复制 importer。

离线解析、映射、重复身份/回档可用临时原件与 Repository 验证；真实采集运行影响必须在指定游戏环境实测，不能靠 mock 证明。按涉及接口运行 `test_player_imports/test_player_repository` 和相关回归。演示 fixture 与真实测试存档证据分开标识，不要求现在修复预设档案。

交付：子任务、实际游戏版本/模式、字段覆盖与证据、采集/映射规则、导入结果与隔离验证、尚未验证条件。D0 调查不称已接通；D1 读通不称正式导入；D2 导入不称完整职业业务闭环或跨版本兼容。
