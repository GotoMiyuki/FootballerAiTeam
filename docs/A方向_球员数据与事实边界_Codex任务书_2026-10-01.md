## 1. 给执行 Codex 的任务摘要

你正在维护 FootballerAiTeam。执行本指南指定的 A 方向子任务，解决“预测可以写成事实”和“各入口读取的球员数据不一致”两个根本问题，并为后续游戏数据提供受控导入边界。

**执行单位是子任务，不是整份指南。未指定子任务时，默认只执行 A1。**

实施顺序：

1. A1：停止预测写入实际档案。
2. A2.1：统一只读访问、上下文与来源版本。
3. A2.2：增加受控观察导入、防重和原子提交。

A1 可以独立落地。A2.1、A2.2 均应另行执行；不因本文列出了后续工作，就在同一轮全部重构。

执行前读取仓库适用的 AGENTS.md 与最新源码，确认本指南指出的问题是否仍存在。保留已有未提交修改。发现其他方向问题时记录，但不扩展到其实现；本任务中的正常修复和验收不需要反复询问用户。

**数据基线（用户已明确）：当前预设数据与档案都是测试样本，可按测试需要重建或替换。历史样本污染不要求清洗、恢复真值或保全迁移。验收针对最终真实功能：预测不能写成事实，测试样本不能进入实际生涯，真实档案的更新必须受控。** 本指南不要求为了处理样本增加迁移系统，也不要求现在重建样本；其他已有代码修改仍须保留。

## 2. 产品目标与核心不变量

近期环境是本地、单用户。未来会读取一个游戏生涯，但 A 不负责接入游戏。

必须保持以下不变量：

| 编号 | 不变量 |
| --- | --- |
| I1 | 生成、审查、修订、重规划或解释一份建议，不改变球员实际能力或实际比赛记录 |
| I2 | 模型建议、预测、虚构叙事和用户采纳，不自动变成观察事实 |
| I3 | 当前事实更新必须经过明确的数据导入边界，携带身份、来源、时间与输入版本 |
| I4 | API、Graph 初始球员状态、Agent 数据工具从同一数据源和同一上下文读取 |
| I5 | 未知、明确的零值、明确的“无伤病”分别表达；不可用数据不自动补成正常值 |
| I6 | 不同生涯、不同分支和不同球员的数据隔离；读取旧存档不静默覆盖当前分支 |
| I7 | 同一观察重复导入不重复生效；冲突、无效数据或提交失败不留下半份事实 |
| I8 | 测试样本与实际生涯存储明确隔离；样本不能被自动初始化、迁移或导入为实际观察 |

例如：当前速度 80，Coach 建议四周后达到 83。报告可以展示“预测 83”，数据库仍是 80；只有后续真实观察或独立的人工核实记录能够更新它。

用户点击“继续生成报告”，不是确认预测已经发生；用户说“我采纳这个训练方案”，也不是能力已经增长的证据。

### 4.2 本方向不做

- 不接入 PES/FC、不安装 Sider/Live Editor，不研究内存地址或存档格式：属于 D。
- 不修固定答案降级、Reviewer PASS、ReAct 退出、依赖调度与结果失效：属于 B。
- 不重做 CLI 会话恢复、对话滑动窗口和长期语义记忆：属于 C。
- 不实现建议采纳、训练执行、效果回访或玩家操作自动化：属于 E。
- 不校准身价、成长收益、现实伤病或游戏风险算法：属于 F。
- 不实现任务取消、全面运行中恢复、跨数据库事务、多进程锁或云部署：属于 G。
- 不迁移全部数据到 PostgreSQL、Redis或新的微服务架构。

边界例外仅限当前子任务必需的薄适配：例如统一 Graph 的档案读取不等于允许改执行图；公开未知值需要类型同步不等于允许重设计整个工作台。

## 5. A1 开发步骤：停止预测写入

### 5.1 修改要求

1. 删除 Coach 输出解析后的自动属性写入。输出中的预测可以保留，不能以报告确认、Reviewer 通过或任务完成作为写入条件。
2. 从 Coach 的工具列表移除档案/属性写入工具，覆盖模型主动 function call 这条路径。
3. 检查所有运行时 Agent 工具列表以及 `ALL_TOOLS`、`DATABASE_TOOLS`。默认聚合列表应只提供读取；不要保留一个容易重新绑定的含写入工具通用列表。
4. 更新 Coach 对可用工具和预测字段的描述，明确它只是建议，未写入真实档案。
5. 为兼容可保留写入包装函数的定义，但它们不得出现在任何模型绑定列表中，也不得由 Agent 自动调用。后续业务写入改由 A2.2 的应用接口承担。
6. 保持输出字段兼容，优先保留 `attribute_update_suggestions` 名称，只澄清语义；不顺手重构训练算法、默认答案或整个输出契约。

### 5.2 A1 验收矩阵

所有测试使用隔离的临时球员数据和模型/工具替身，不调用外部模型或实际 RAG。

| 场景 | 必须满足 |
| --- | --- |
| Coach 正常输出预测属性 | 原四份球员记忆文件字节内容均未改变，预测仍存在于任务输出 |
| 替身模型主动请求属性更新工具 | 调用被白名单拒绝或不可绑定；没有实际写入 |
| 同一任务重复运行或局部修订 | 不累计提升能力，不追加虚假比赛/训练记录 |
| 报告生成失败、拒绝或未确认 | 球员事实不改变；不能仅在最终报告阶段检查 |
| Agent 与聚合工具列表检查 | 所有模型可用工具集合均不含事实写入工具 |
| 测试样本准备与任务运行 | 准备阶段可重建样本；任务运行阶段的建议、预测和修订仍不得修改事实文件 |

可以通过包含真实 Coach 节点的轻量图或应用替身验证流程边界，无需真实模型。测试要验证存储和能力绑定两方面，不能只检查被删除的某一行不再调用。

A1 完成后输出：改变了哪些写入路径、保留了哪些兼容入口、验收证据及是否调整测试样本。无需修复历史样本污染；不得宣称所有 A 方向工作已完成。

## 6. A2.1 开发步骤：统一读取与身份

### 6.1 统一访问入口

建立一个可注入的 PlayerRepository，以及只读视图/适配接口。关键职责：

| 操作 | 语义 |
| --- | --- |
| 读取档案 | 当前上下文的档案投影，含可追溯状态版本 |
| 读取训练/比赛/职业历史 | 同一上下文中的相应记录，不跨生涯混合 |
| 读取状态元数据 | 身份、来源、版本、时间和质量标记 |
| 读取完整原始记录 | 用于来源核对或诊断；不自动注入专业 Agent 上下文 |

API、Graph 初始加载、Agent 的预读取、LangChain 数据工具均通过同一入口。`tools/database.py` 可以保留现有函数签名，内部委托 Repository，避免一次修改所有专业 Agent。

应用根部持有 Repository 配置；Agent 只收到只读访问能力。若当前工厂需要无参函数，可先使用一个统一配置的只读提供器，但禁止多个独立路径缓存，或任务执行时随意修改全局配置。

定义清楚：一项执行中的任务固定使用其创建时的数据上下文。不能仅因为 UI 切换了生涯，就让这个任务后续读到另一名球员。无需新增生涯切换 UI，但上下文可通过构造参数测试。

### 6.2 身份与版本约定

| 字段 | 最小要求 |
| --- | --- |
| `career_id` | 生涯/存档身份；不能仅由球员姓名或俱乐部决定 |
| `branch_id` | 同一生涯的路线分支；用于隔离回档、重踢或另一路线 |
| `player_id` | 在该上下文中稳定的目标球员身份 |
| `schema_version` | 数据结构版本，与球员状态变化版本分开 |
| `state_version` | 同一上下文内已提交状态的版本；读取相同状态得到相同版本 |
| `snapshot_id` 或内容摘要 | 将具体读取结果绑定到可复核快照，不仅记录当前可变文件路径 |

标识必须经过长度、字符和路径校验，不能原样拼接含 `..` 或绝对路径的输入。物理路径解析后仍须位于配置的数据根目录内。

A2.1 的只读适配器可用规范化内容摘要作为 `state_version`；不要为了读取或补元数据自动写盘。A2.2 的受控存储可以采用递增 revision，并同时保留内容摘要。对外把版本当作不透明标识使用，比较相等性即可，避免 B 方向依赖两种格式的数值含义。

内容摘要排除纯读取时间和访问次数，否则读一次就会改变版本。涉及档案与历史的一致性摘要必须覆盖实际被消费的数据和身份，不能只对档案文件取摘要。

### 6.3 来源、时间和数据质量

每个当前字段或历史记录都应能追溯到相应观察，至少通过字段/记录到观察标识的映射；不能用一条顶层“最后更新来自游戏”覆盖所有字段的来源。

最小来源类型：

- `game_observation`：来自经验证的游戏采集入口。
- `user_confirmed`：来自独立、明确的人工核实输入。
- `demo_fixture`：演示或确定性测试数据。

若未来确有导入来源不明旧档案的需求，可增加 `legacy_unverified`；当前测试样本直接归 `demo_fixture`，不要求实现旧档案迁移。

来源类型是数据来源分类，不是自动真实性认证。模型输出不能通过自报 `source_type=user_confirmed` 获得事实写入资格。

时间至少区分：

- `collected_at`：现实中的采集时间，带明确时区。
- `effective_at`：数据在业务世界生效的时间，可为游戏内日期。
- `time_domain`：`game` 或 `real`，不同时间域不直接比较。

允许未知时间，并记录未知；但时间无法验证的导入不能凭更晚的采集时间覆盖已知的当前事实。

### 6.4 规范数据与样本兼容

建立最小明确的数据结构，不为历史测试样本做全面修复：

1. 可直接重建符合规范的样本，标记为 `demo_fixture`。旧别名、冲突值与预测字段不要求逐条还原；已有交互所需的读取兼容可通过薄适配保留。
2. 当前事实投影只接受规范字段。`after_4_weeks`、`after_12_weeks`、`预期变化_*`、`expected_improvements_*` 等预测不能进入事实投影；实际输入中的未知字段不得静默提升为事实。
3. 实际采集的别名转换由明确映射处理；含义或值存在冲突时拒绝或报告质量问题，不能交给模型猜测合并。无需为所有历史样本别名建立兼容表。
4. `estimated_value_eur` 等估计值继续保持估计身份，不能变成 `observed_market_value`。
5. 缺失比赛评分、出场时间或能力值保持未知，不补为 0。
6. 缺文件、无数据和损坏数据明确区分。实际档案损坏不自动重建空文件；API 不应把损坏成功返回为正常档案。测试初始化时显式重建样本是独立操作。

A 负责不在数据访问层制造默认事实；专业 Agent 里仍有默认参数和简化规则，需要标记为 B/F 后续事项，不在 A2.1 扩大为全部算法重写。

### 6.5 配置与公开数据

- 新增明确的球员数据根目录/Repository 注入配置；与 `FAIT_DATA_DIR`（Web 任务存储目录）区分。
- 现有默认 `memory` 路径明确属于 demo；实际模式必须显式选择实际数据根目录，不回退读取 demo。保留必要的旧接口读取兼容，明确旧文件路径覆盖与新配置的优先级，矛盾配置不得静默选择。
- 更新真实 smoke 的隔离方式，确保 API、Graph 和工具全部使用临时副本。
- 公开球员接口保持现有核心字段形状，必要时增加只读元数据对象；训练与比赛历史不能突然从列表变成任意 envelope。
- 涉及 null/缺失值时同步 DTO、前端类型和显示，未知显示“未记录/未知”，不要渲染为 0 或默认健康。
- 当前历史列表和职业历史对象的兼容由适配器完成；来源信息可使用附加字段或独立只读元数据接口，不要求改 Mission 事件协议。
- 不把本机原始路径、秘密配置或整个原始档案暴露到公共 DTO。

### 6.6 A2.1 验收矩阵

| 场景 | 必须满足 |
| --- | --- |
| 根目录为临时数据目录 | API、初始状态、专业预读取和 LangChain 工具得到相同数据 |
| 仓库与临时档案名字/能力不同 | 所有测试断言临时数据值；不能恰好读取相同样本而误判通过 |
| 两个生涯/分支/球员上下文 | 隔离读取；正在执行的任务不因另一个上下文被选中而变更 |
| 读同一份数据两次 | 版本稳定，无写盘副作用 |
| 档案或被消费历史改变 | 状态版本/摘要变化；身份不同不能被视为相同快照 |
| 预测字段、冲突输入与估计身价 | 预测不进入事实投影；实际冲突不静默合并；估计不冒充观察 |
| 明确 0、缺字段、null、“无伤病” | 可以分别表达；损坏数据不伪装成普通空档案 |
| demo 模式、模型 smoke 和 Web 测试 | 使用明确隔离的样本；真实模型 smoke 也不意味着样本是真实生涯数据 |
| 实际模式缺少配置或没有档案 | 明确报错或返回未初始化；不回退 demo，不自动复制预设球员 |

## 7. A2.2 开发步骤：受控观察导入

### 7.1 最小导入接口

提供 Python 应用接口即可，不新增通用模型写入工具，不要求新建 HTTP 写入端点或完整档案编辑 UI。

接口接收已经转换为领域格式的观察；游戏原始字段解析和游戏版本专有规则归 D。首版至少支持档案局部观察、训练记录、比赛记录。职业历史的新增事件采用兼容原对象的追加映射；若当前结构不允许安全更新某子字段，明确拒绝，不开放任意深层覆盖。

最小输入约定：

| 项目 | 要求 |
| --- | --- |
| 上下文 | `career_id`、`branch_id`、`player_id` |
| 结构版本 | `schema_version` |
| 观察身份 | 稳定的 `observation_id`，以及采集端可提供的 `source_record_id` |
| 来源 | `source_type`、`provider`、游戏/适配器版本或人工核实记录引用 |
| 时间 | `collected_at`、`effective_at`、`time_domain` |
| 观察类别 | 档案 patch、训练记录、比赛记录、职业事件；明确类别与对应 payload |
| payload | 已规范化且通过字段与类型校验的观察数据 |
| 并发控制 | 新的写入请求携带 `expected_state_version`；初始创建使用明确的空状态条件 |

人工确认是一个独立来源操作，必须有明确的确认记录引用。报告完成事件、报告前批准和模型文本不自动生成确认记录。

导入入口不能接受“预测字段改名为 attributes”的模型结果作为事实。第一道保护是能力边界：该接口不注册给模型，只有明确的采集/人工核实应用入口调用。来源标签本身不是安全凭证。

### 7.2 字段、缺失值与 patch 语义

- 字段名采用明确 allowlist。未知扩展保留在原始观察或扩展区域，不能任意注入当前档案、配置路径或执行状态。
- patch 中未提供的字段表示不更新；显式 null 表示“本次明确将该字段标记为未知”，只在字段允许未知时接受。
- 删除已有事实不得用“字段没传”实现；更正和撤销需有显式操作和来源，并保留旧观察。
- 首版不支持不明确的全量替换；D 需要全量快照时，先新增对应契约，明确快照未包含字段的含义。
- 数值校验排除 bool、NaN、Infinity 和不可解释的字符串。正值、计数、比例和属性量表按字段定义检查；不将所有属性粗暴套入同一 0–100 范围。
- 对 `other_features` 的 1–5、1–8 等量表明确各自规则；PES/FC 原始量表的转换由 D/F 约定后再接入。
- 当前日期字符串、训练周、比赛日和职业月份精度不同；保持精度元数据，不伪造一天或具体时间。
- 稀疏观察可存为观察记录；如果缺少形成当前投影所需的关键数据，明确说明“已记录但未应用”，不能补造字段。

### 7.3 时间、防重和冲突

导入结果至少区分：`APPLIED`、`DUPLICATE`、`RECORDED_ONLY`、`CONFLICT`、`REJECTED`。实现可用结构化结果或明确异常，但不得只返回一个模糊成功字符串。

- 防重键包含生涯、分支、球员、provider 和观察标识；不能只使用比赛日期。
- 同一防重键、语义内容相同：返回 DUPLICATE，不追加事件、不增加状态版本。
- 语义摘要排除纯重试采集时间；身份、生效时间、来源记录和 payload 应纳入比较。
- 同一防重键、语义内容不同：返回 CONFLICT，不静默覆盖。更正使用新观察标识并显式关联被更正的观察。
- 重试已成功请求时，先判定它是同一观察，再处理版本要求；不能因原 expected version 已过期而让正常幂等重试失败。
- 新观察的 expected version 不匹配：返回 CONFLICT，不覆盖新状态。
- 更早的游戏内状态不能按更晚采集时间替代当前状态；可只记录为历史或拒绝。分支识别交 D，A 提供显式 branch 隔离及拒绝歧义写入的边界。
- 游戏内时间相同不等于同一事件，状态版本与观察标识共同防重；无法确认顺序时不能自行推断。
- 时间域不同、缺少生效时间或更正涉及歧义时，保持当前投影不变并返回明确结果。

### 7.4 存储与原子提交

继续使用 JSON，默认采用每个上下文一个受控状态文档，包含档案投影、相应历史、来源映射、观察记录/导入索引与状态版本。目录名或文件名可调整，路径须在配置根目录内。

测试样本与实际受控数据使用独立根目录，实际目录不包含默认复制的样本基线：

```text
<fixture-root>/                # demo 与测试样本，可重建
<actual-player-data-root>/     # 实际生涯，必须显式配置
  contexts/
    <validated-context-key>/
      state.json
```

选择一个聚合状态文件，是为了把“事实更新、防重记录和版本”放在同一次提交里，不是为了迁移现有 Web/Checkpoint SQLite。

提交步骤：加载并验证当前状态 → 在上下文锁中检查防重与 expected version → 计算完整候选状态 → 同目录临时文件写入/刷新 → 原子替换 → 返回结果。

注意事项：

- 事实、观察索引和版本必须一起提交。禁止先更新档案、再写防重日志。
- 成功替换前失败，原状态必须保持可读；成功替换后即使响应丢失，重试也能识别为 DUPLICATE。
- 同进程同上下文的锁和版本检查必须覆盖整个读改写过程；不能只锁最后的写文件。
- 失败临时文件可清理，但不删除旧数据来“修复”。Windows 替换失败不能先删目标文件再重试。
- 原子替换不等于跨数据库事务，也不承诺所有断电场景的绝对可靠性；说明本轮保证范围。
- 多进程写入暂不支持，明确单写入进程约束；CLI/Web 不能各自无协调地写同一受控状态。
- 不为每次读取重写状态，返回可复制快照，避免调用方原地修改内部缓存。

如果采用其他存储布局，需证明其同等的事实/防重/版本原子性；单纯对四个 JSON 分别原子替换，不满足一次导入跨文件的一致性。

### 7.5 样本隔离与实际档案保护

- 当前预设档案无需迁移、历史修复或保全；按测试需要重建即可，不单独开发清洗和恢复系统。
- 实际生涯从明确的空状态开始，只通过受控游戏观察或独立人工核实初始化。禁止用仓库样本作为实际档案的默认基线。
- `demo_fixture` 不得由实际模式导入入口接受；来源标签还须与应用入口和存储配置一致，改标签不能将样本认证为实际观察。
- 如确需样本重建工具，只允许操作显式测试根目录，并校验解析后的目标路径；测试与实际根目录不得相同或相互包含。不能仅凭档案内的 `source_type` 标签授权删除或重建目录。本轮不要求新增重置工具。
- 一旦某上下文进入受控存储，明确它是该上下文的权威数据，不再同时双写旧 JSON。
- 旧 `update_player_profile`、`append_*` 等写函数应废弃、拒绝缺失来源的写入，或明确路由到受控接口；不能成为绕过导入验证的后门。
- 实际数据形成后，格式不兼容须明确拒绝；代码回退不能靠删除实际档案或重置为样本实现。未来实际数据的版本迁移另行安排，完整备份恢复仍归 G。

### 7.6 A2.2 验收矩阵

| 场景 | 必须满足 |
| --- | --- |
| 合格游戏/人工观察 | 原子更新投影、记录和版本；字段可追溯到具体观察 |
| 仅有模型预测或报告批准 | 不获得写入能力，不产生实际能力更新 |
| 档案 patch 不含某字段 | 该字段不改变；null 与未提供语义不同 |
| 相同观察重试、采集时间变化 | DUPLICATE，无重复记录或 revision 增长 |
| 同 id 不同 payload | CONFLICT，原状态不变 |
| 新观察使用过期版本 | CONFLICT；成功导入的正常重试不误判 |
| 不同上下文同 observation id | 隔离处理，不误判为同一观察 |
| 旧日期、未知日期、跨时间域、回档 | 不静默覆盖；形成 RECORDED_ONLY、CONFLICT 或 REJECTED |
| 两个同版本并发写入 | 至多一个新写入成功，另一个返回冲突；没有丢失更新 |
| 写临时文件/替换失败 | 原受控状态可读取，防重记录与投影不分裂 |
| 替换成功但响应失败后重试 | 能识别前次提交，不重复应用 |
| JSON 损坏、路径越界、无效数值/字段 | 明确拒绝，没有自动空档案或任意路径写入 |
| 新建实际生涯、样本导入实际入口 | 新生涯无预设事实；样本导入被拒绝，实际状态不变 |
| 样本初始化/重建（若实现） | 仅影响明确的测试根目录；越界、与实际根重叠时拒绝 |
| 重新创建 Repository | 已提交状态、版本和防重记录可恢复；不只存在内存缓存里 |

## 8. 与其他方向的接口与冲突处理

| 方向 | A 提供 | 本轮不替其完成 |
| --- | --- | --- |
| B | 不可变数据快照、上下文标识和状态版本 | 不做依赖结果失效算法或失败枚举重构 |
