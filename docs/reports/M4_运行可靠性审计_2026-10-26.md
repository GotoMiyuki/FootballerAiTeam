# M4 运行可靠性缺口审计

审计日期：2026-10-26。结论：**补齐明确缺口后可收尾**。现有 Career Companion 可以作为本地单用户 production-like MVP 的基础，主要成本集中在执行生命周期、请求身份、actual 写入互斥和恢复流程。没有证据要求重写全部 Agent、重做 M1—M3 或先开发 PES 写回。

**本报告是缺口审计，M4 未通过。** 本轮仅新增审计脚本、隔离实验和本报告；未修复业务实现，未操作游戏，未修改路线图、M3 验收状态或既有实际数据。

## 2. 入口和持久化边界

Web POST `/messages`、`/input`、`/mission-continuations` 进入 MissionService。CLI 复用该服务和持久化图，`CLIMissionService.wait()` 阻塞等待 Future。两者可使用同一任务格式，但任务目录必须只有一个写进程。

| 数据 | 实际位置/权威来源 | 备份和恢复要求 |
| --- | --- | --- |
| actual 球员事实、观察、origins、import_index | `<actual>/contexts/<career>/<branch>/<player>/state.json`，JsonPlayerRepository/ObservationImporter | 保留整份聚合、context、schema、revision 和摘要；不能只复制 profile |
| 导入绑定、回执 | `<actual>/collectors/pes2021_native/bindings.json`；collector 回执目录，见 `pes2021_import.py:129,277` | 绑定身份、版本和来源基线需一起保留；`--sole-writer` 目前只是声明 |
| 任务、事件、消息、固定输入、报告 | `<task>/workspace.sqlite3`，Store | inputs 中含固定 A、选定历史、记忆和 E 反馈；不能恢复时改读最新数据 |
| 专业成果及图暂停位置 | `<task>/checkpoints.sqlite3`，SqliteSaver | 与任务库成套；是建议来源复核及续跑依赖，不能当普通缓存删除 |
| 建议、选择、执行/更正、比较规范、评估版本 | 同一个 workspace SQLite 的 recommendations、recommendation_actions、comparison_plans、assessments 等表 | E 是行动/评估权威；选择、自报执行、观察分开 |
| 生涯记忆、消费事件、请求防重 | 同一个 workspace SQLite 的 career_memories/events/requests | 保留来源引用、修订、撤回和消费身份；C 不改写 E/A |
| 原始证据 | 观察 source_reference/raw_reference 指向的原生包、原始文件和必要账本 | actual 聚合并不内嵌所有原始材料；原生引用含绝对 dataset 路径，换目录恢复需要验证引用可达或明确定义映射；本轮仅恢复合成相对引用 |
| 配置和版本 | 环境变量、.env 的非秘密路径/context、源码/依赖版本 | 备份清单记录配置来源和格式支持范围，密钥独立配置；同时覆盖 Web `FAIT_DATA_DIR`、CLI `FAIT_CLI_DATA_DIR` 和 actual 根 |
| 其他文件 | 旧 memory/sessions.json 为旧 CLI 元数据；fixture 为演示输入；模型/向量索引/知识文件为外部运行依赖 | 不冒充可恢复任务；模型/索引可重建但需固定版本，知识来源如需重现 RAG 应保留；无需备份整个游戏安装目录 |

任务库使用 WAL。`Store.create()` 的一次事务包含任务、固定输入、首条消息、事件和可选创建防重记录；`emit()` 将快照与单条事件一起提交。入队在事务外，运行中的多次事件、报告、建议投影、终态也不是一个跨库事务。原子 JSON replace 保证单个文件可读，不提供跨进程 CAS 或跨文件一致性。

### 4.2 重试层次和最大边界

1. 当前安装的 OpenAI SDK 常量是600秒/连接5秒、默认重试2次（`venv/Lib/site-packages/openai/_constants.py:9`）。但 LangChain 工厂实际传 `timeout=None`，实测底层 `Timeout(timeout=None)`。**不能用SDK常量替代实际配置证据**。
2. SDK默认重试最多使一次逻辑invoke产生3次传输；E01验证500、400和超时的上述路径，没有验证所有状态码和真实服务端行为。工具调用自身没有通用重试；ReAct接着生成新的工具调用不是同一次工具重试。Tavily当前SDK `search(timeout=60)` 提供局部请求限制，未解决通用工具/任务限制。
3. ReAct默认最多5次模型调用；在一次全部进入ReAct的专业节点中，粗上限为5×3=15次传输。每次模型响应的工具调用列表没有仓库单独的数量预算。并非每个角色都用ReAct：Manager有任务/假设/计划/重评调用，Reviewer和Document另有直接调用入口。
4. LoopControl单子任务最多1次revision、任务最多2次replan、总循环最多4；图还有64次节点迭代保险丝，运行时递归限制100。它们限制重复执行次数，不提供时间限制，也不能据此把整任务简化为“15次调用”。任务重试是新的关联任务，默认不自动重放中断任务；用户新请求总次数本来就没有跨任务上限。
5. 因单次调用、工具和排队未统一有界，**当前无法给出整任务有限墙钟上限**。用户暂停应从执行预算中单独处理。未来需明确每类角色实际调用预算、嵌套重试乘数和截止时间，不能简单再套一层重试。

### 4.3 本轮不计为产品失败的运行问题

- 进程实验首轮遇到 Windows venv launcher PID与实际Python子PID不同；改用相同基础解释器+显式venv PYTHONPATH后重跑，核对子进程自身写出的PID，再通过本轮Popen句柄中止。旧实验子进程按审计安全时限自行退出，并确认PID不存在。第二轮读取中文JSON漏UTF-8导致脚本异常；有效结论仅取完整的 `20261026-03`。没有终止用户服务或PES。
- 首次Vitest在沙箱默认TEMP rename发生EPERM，0测试执行；换新隔离TEMP后7项通过。原失败JSON保留，归类环境限制。
- 首轮浏览器误选依赖真实demo API的一个场景，因本轮没有启动demo API而失败；其余8项通过。新增浏览器桩的宽路径匹配还误拦截了 `/src/api/client.ts`，导致MIME错误。修正为pathname以`/api/`开头并排除demo场景后，最终8项和新增场景通过。这两次属于实验选择/脚本错误，不是前端业务缺陷。

### 暂不升级为阻断的项

执行中断后统一FAILED并允许创建关联重试，是现有运行指南明示的政策，且本轮进程证据支持它。G2没有要求自动恢复所有运行阶段。因此“落库后未入队”和“report已写但终态未写”的窗口应纳入正式状态矩阵、提示与审计，不应仅因为存在窗口就强制引入持久队列、跨库分布式事务或自动重放。

报告窗口实验在重启后保留了库内report文本，但公开接口404、原任务FAILED、没有运行Document或虚构完成。可以接受保留为中断产物，前提是明确支持范围、不会当可用报告或当前建议发布，并在取消/超时设计中覆盖全部发布门。若后续新增自动恢复，再评估事务发布/恢复标记，不能直接重放这个窗口。
