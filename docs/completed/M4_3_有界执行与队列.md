## 1. 交付行为

默认Web/CLI服务通过[ProcessRunner](../../backend/process_runner.py)运行真实图及独立解释。[worker](../../backend/execution_worker.py)接收提交时固定的球员、历史、记忆和反馈材料，执行原有Graph/Agent并保存checkpoint；协调进程继续独占workspace、公开事件、报告和E/C业务写入。没有改写角色逻辑，也没有引入外部任务队列。

每个执行段使用一个子进程。暂停/完成时先结束并清理子进程，再由协调者记录相应公开结果；恢复创建新的进程，读取原checkpoint，沿用operation并递增run。Windows Job负责本次进程树的所有权；父进程意外退出时其私有Job句柄关闭，子进程随之退出。其他平台仍明确拒绝，Job不是文件系统权限沙箱。

[调用边界](../../backend/call_limits.py)覆盖七个Agent的模型入口、工具入口及独立报告解释。模型连接/连接池、读写时限和SDK重试次数使用同一RuntimePolicy；默认最多2次网络尝试。父进程独立监督启动、单次逻辑模型调用、工具调用和累计执行截止时间；SDK内部尝试及退避都在逻辑调用时限内。工具内的本地模型加载/挂起也受父进程时限约束。SearchTool另外将传输timeout裁剪到剩余执行预算。

执行预算跨缺输入/审批累计，含冷启动、执行和本次资源清理；排队和用户等待不扣执行预算。每次执行结束持久化execution_seconds，排队另计queue_seconds；新任务标明预算历史完整，旧operation按默认未知历史读取。系统崩溃前尚未落盘的末段不能伪造成已知耗时；完整时间/usage展示仍属于M4.5。

## 2. 队列和停止

[TaskQueue](../../backend/task_queue.py)保留最多1个执行段和配置数量的等待位，默认3个，允许1—16。排队时限由独立时钟处理，第一任务卡住不会阻止第二任务排队超时。继续使用现有request回执和operation/run身份。

| 情况 | 返回或持久结果 | 请求重试 |
| --- | --- | --- |
| 同request已接收 | 202，原回执，replayed=true | 不再占位、不读latest、不重新执行 |
| 队列满，尚未接收 | 429/QUEUE_FULL，accepted=false，Retry-After: 1 | 沿用原request及内容，稍后重试 |
| 已接收后排队超时 | operation FAILED/QUEUE_TIMEOUT | 原request仍返回原失败；新意图用新身份 |
| 服务停止接收 | 503/SERVICE_STOPPING，accepted=false | 不创建新任务或解释 |
| 正在执行时关闭 | 先清理所属worker，FAILED/SERVICE_SHUTDOWN | 原ID不自动重执行 |
| 异常退出后重启 | 遗留QUEUED/RUNNING变FAILED/INTERRUPTED | 原ID不自动重执行；暂停仍按原校验恢复 |

首次创建、解释、关联创建和暂停输入都在持久接收前检查容量；满队列不会留下新的Mission、operation、消息、事件或回执。非法输入仍先按原规则拒绝，不用容量判断绕过字段校验。已暂停任务在正常关闭时保持暂停。

关闭先停止入队，结束等待项并通知监督循环停止当前执行，有限join后再关闭Store和释放任务写锁。若清理超出关闭预算，明确报错并保留写入所有权，不能在旧执行者仍可能写入时释放任务目录。

## 3. 执行协议与发布范围

子进程stdout仅传版本化JSON，校验operation/run，单帧最多4MiB，父进程接收队列最多8帧并施加背压。内部messages和LangGraph的Interrupt对象留在checkpoint，暂停以最终snapshot.next为准。坏JSON、超大帧和身份不匹配明确失败并清理进程。

固定输入通过任务目录内runs/operation/run/input.json交给可信worker；只保留恢复所需材料，不含API密钥。密钥仍从受信的进程环境/原配置读取。模型回复、工具原始异常及日志不混入stdout控制通道，公开失败使用固定原因码。

监督器在超时/停止后清理本次进程，不再消费其候选结果；有效结果返回后仍检查当前执行时限并通过既有成果、审查和正文发布门。**取消入口、持久撤权以及报告/消息/operation/事件的统一最终事务仍待M4.4**，不把本项的单执行者监督当作完整发布竞争协议。

解释使用原报告和固定记忆，创建自己的operation；解释超时只追加失败消息，原Mission、报告和生成计量保留。中止本地进程不能撤回提供方已经处理或计费的请求。

## 4. 配置与运行

配置初值及约束见[运行契约v1第5节](../guides/M4_运行契约_v1.md#5-初始预算)。FAIT_RUNTIME_*在服务创建时解析；修改后重启生效。模型180秒、工具90秒、累计执行1200秒、排队120秒、启动60秒、清理3秒、关闭10秒是试运行初值，不是实测性能承诺。

服务仍使用workspace核心版本1；OperationView增加带默认值的执行/排队耗时、历史标记和本次worker PID，不要求重写旧记录。旧格式显式续跑的未知历史不补成零消耗的完整历史。发布到已有工作区仍先停写并保留完整一致副本；本轮只在新隔离目录验证，没有升级或启动用户实际任务库。

直接在开发脚本里调用原始graph不经过MissionService监督。演示模式为固定本地流程，使用同一队列及可中断等待；不启动真实模型worker。测试专用InlineRunner由测试fixture显式注入，用于原有业务语义回归，不能作为进程清理/硬时限证据；生产默认没有根据Mock或环境变量自动绕过隔离的路径。
