## 1. 交付行为

带operation/run身份的工作流支持取消排队、运行、缺输入和报告审批；完成报告上的独立解释也可取消。取消首个事务保存operation的CANCELLED/USER_CANCELLED、相应Mission或解释消息、事件和请求回执。事务成功后才通知执行器停止、移除对应等待项；接收事务失败会回滚撤权，原执行仍有原来的提交资格。

工作流取消后保留原输入、计划、审查和内部checkpoint，清除等待表单及公开报告引用；运行中的Agent/步骤显示已取消。旧暂停输入不再续跑。重新执行使用关联新Mission/operation，重新冻结输入；已取消checkpoint的专业候选不能作为关联任务的选定历史，前端隐藏该选择，API明确拒绝。独立解释取消保留原报告、原Mission完成状态及原E/C记录。

取消与完成按同一workspace事务的先后顺序决定。取消先提交，后续结果/进度/失败不能改写它；完成先提交，取消返回ALREADY_TERMINAL并保留交付。相同request重复取消返回原回执，不增加消息/事件，也不另选“最新任务”。run或pause不符时拒绝，不转而取消更新的执行。

## 2. 持久发布门

[Store](../../backend/store.py)的嵌套事务统一使用外层SQLite提交/回滚。执行作用域内的Mission快照、事件、消息和报告写入会在该事务内核对数据库中的operation仍为RUNNING且operation/run完全匹配。协调者接收worker进度时也使用同一门禁，包含worker PID更新，旧run不能通过进度回包恢复提交权。

报告正文、公开摘要/报告引用、assistant消息、Mission终态、相应事件和operation COMPLETED在一次事务中提交；独立解释的回答、消息事件和operation终态也一起提交。两个暂停点把Mission BLOCKED与operation PAUSED/pause身份一起保存。执行收尾只累计耗时和清理资源，不把已取消操作重新标成完成/失败。

原成果、审查版本和正文发布条件保留。E投影在报告事务提交后读取已完成的公开Mission核验来源；投影失败单独处理，不重新调用模型。取消/回滚后，即使checkpoint已有final_report候选，也不会发布报告、产生当前建议或通过取消任务的历史选择进入新任务。

未引入新队列或角色框架；复用M4.3的单执行槽、有限等待队列和Windows Job。直接调用原始graph的开发脚本不属于这个服务发布协议。已有语义测试中曾直接调用私有_execute的fixture已改为显式经过实际入队/运行身份，再注入进程内图替身，没有在生产代码中增加测试绕过。

## 3. API和清理状态

```text
POST /api/missions/{mission_id}/operations/{operation_id}/cancel
```

```json
{
  "request_id": "cancel-client-001",
  "expected_run_id": 2,
  "expected_pause_id": "当前operation.pause_id；非暂停时传null或省略"
}
```

| 情况 | HTTP与结果 |
| --- | --- |
| 当前QUEUED/RUNNING/PAUSED且身份匹配 | 200，accepted=true、outcome=CANCELLED、status=CANCELLED |
| 已经COMPLETED/FAILED/CANCELLED且目标身份匹配 | 200，accepted=false、outcome=ALREADY_TERMINAL，返回原终态 |
| 相同request与内容重放 | 原回执，replayed=true |
| 同ID换内容/跨入口复用、错误run或pause | 409；不撤销其他操作 |
| 不存在的Mission/operation或归属不符 | 404 |
| 缺失/非法请求字段，含非正整数run、bool代替run | 422 |
| 服务已关闭 | 503/SERVICE_STOPPING；未接收 |

回执包含request_id、mission_id、operation_id、run_id、accepted、outcome、status、cleanup_status和replayed。GET operations继续只读，增加cleanup_status：NOT_NEEDED、PENDING、COMPLETE。

取消回执确认已持久撤权。PENDING表示协调者还在清理本次执行，COMPLETE表示相应执行资源已经结束；等待项可直接移出队列，运行项由现有监督器结束其私有Job。**重放仍返回原回执中的初始清理快照**；当前清理进度读取GET operations，不能因为旧回执仍是PENDING就再次执行取消。清理状态更新使用operation.updated事件，保持Mission sequence递增。

服务重启保留CANCELLED；旧owner退出后的取消清理记录可收口为COMPLETE。完整的各阶段崩溃/格式兼容矩阵仍由M4.6验收，本项不把它标为已全部覆盖。外部提供方已处理或计费的请求不承诺撤销。

## 4. Web与CLI

Web从operations读取明确目标，为任务/解释分别提供“取消任务”和“取消本次解释”。取消请求发送前按Mission+operation+run+pause保存到localStorage，丢响应后保持原请求；后来的执行代次使用新的目标身份。取消后跟踪资源清理、关闭暂停表单和运行标识，并保留历史审查；切换任务后收到旧取消响应不会切换或覆盖当前任务。

CLI的只读show输出operation、run、pause和清理状态。取消本地停止的任务库不需要模型配置；已有写者运行时，使用显式api-url调用该owner，继续遵守任务目录单写者锁。

```powershell
.\venv\Scripts\python.exe app.py --show mission_xxx
.\venv\Scripts\python.exe app.py --cancel mission_xxx --operation-id op_xxx --expected-run-id 2 --expected-pause-id pause_xxx --request-id cancel_xxx
.\venv\Scripts\python.exe app.py --cancel mission_xxx --operation-id op_xxx --expected-run-id 1 --request-id cancel_running_xxx --api-url http://127.0.0.1:8000
```

替换示例身份；非暂停操作不带expected-pause-id。自动生成的request身份在发送前打印并flush；重试保持身份和全部目标字段。CLI输出CANCELLED或ALREADY_TERMINAL及初始清理状态；跨入口复用取消ID作为continue输入会明确拒绝。取消成功命令退出0；请求拒绝退出非零。取消后可用原有retry创建关联新任务，不能继续已取消的执行。

任务库仍为user_version=1，复用request_receipts；新增取消回执kind和带默认值的OperationView字段，没有重写旧记录或checkpoint。没有operation的旧任务继续按已有只读/兼容边界处理，不伪造取消目标。发布到已有工作区仍需停写和完整一致副本；本轮未升级、部署或打开用户实际任务库。
