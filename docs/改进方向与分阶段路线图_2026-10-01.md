# FootballerAiTeam 改进方向与分阶段路线图

日期：2026-10-01

状态：规划文档；已完成开发见第 14 节与汇总索引。A1/A2、B1–B3、C1、D0、E1.1 已交付；D1 仅试操作，个人样本及正式游戏导入未完成。
依据：当前对话中的架构审查与后续讨论，以及当前仓库实现。

## 1. 目标与范围

目标是把现有足球多智能体工作台逐步做成可靠的 Career Companion：从游戏存档获得可追溯的状态与事件，围绕玩家实际选择提出建议，记录后续结果，并调整下一次决策。

近期验收范围是本地、单用户、一个游戏版本、一个测试生涯存档。游戏数据用于检验游戏生涯中的建议和系统行为，不作为现实训练效果的验证数据。

按业务职责拆分工作，避免按“前端 / 后端 / Agent”分别大改：同一功能需要的前后端改动应在同一个小任务中完成。每轮优先完成一个有独立验收条件的任务，而不是完成整条方向。

明确约束：

- 游戏观察、用户确认的事实、预测、建议和虚构叙事分别记录；建议生成不改变实际球员能力。
- 无效输出不能用固定答案补成有效结果；审查不可用不能算作 PASS。
- 保留有明确标识的 demo 和确定性测试替身；它们用于交互与控制流验收。
- 当前预设数据与档案均为测试样本，可按需重建；历史样本污染不安排修复、真值恢复或保全迁移。验收重点是最终实际功能不污染真实档案：样本与实际存储隔离、实际模式不回退 demo、预测不写成事实、真实观察受控导入。
- 优先复用现有 Agent 和工作台。暂不把多人权限、复杂部署、数据库整体迁移作为前置条件。
- 面试与展示措辞只作为文档准确性事项，暂不安排独立的面试优化任务。
- 以下文件范围和接口名称是规划建议；实施前需重新检查源码与最新变更，不能直接视为已实现。

## 2. 七条改进方向

| 编号 | 方向 | 负责回答的问题 | 主要交付物 | 不承担的职责 |
| --- | --- | --- | --- | --- |
| A | 球员数据与事实边界 | 什么是真实记录，来自哪里，能否被更新？ | 球员数据访问接口、来源与版本、事实与预测分离 | 不决定 Agent 调度，也不研究游戏内存结构 |
| B | 执行、协作与审查正确性 | 任务是否得到有效结果，下游是否使用正确输入？ | 结果契约、失败语义、依赖上下文、结果失效与审查规则 | 不负责长期生涯记忆或采集游戏数据 |
| C | 会话恢复与生涯记忆 | 恢复什么，记住什么，下次怎样使用？ | 暂停任务恢复、完成任务延续、相关记忆检索 | 不负责训练或比赛数据采集，不制定身价算法 |
| D | 游戏接入与采集适配 | 哪些游戏字段能稳定获取，如何导入？ | 本机可行性结论、只读采集、原始记录、适配器 | 不给 AI 直接改游戏或球员事实的权限 |
| E | 球员业务闭环与交互 | 建议是否采纳，执行后怎样反馈？ | 建议与行动记录、反馈比较、后续任务 | 不从聊天记录猜测行动已执行，不创建虚假比赛 |
| F | 领域规则与建议质量 | 建议和预测有什么依据，适用范围是什么？ | 游戏属性解释、风险维度、身价与成长预测校准 | 不承担流程编排或把游戏指标当作现实运动指标 |
| G | 运行可靠性 | 卡住、断线、重启、重复提交时怎样处理？ | 时限与取消、提交防重、恢复策略、备份与运行指标 | 不以多用户平台化或无限自动重试为目标 |

测试、质量评估与文档维护是每条方向的交付责任，不留到最后统一补。需要跨方向的完整生涯验收，另作为里程碑组织。

## 3. A：球员数据与事实边界

主要范围：`tools/database.py`、`config.py`、Coach 的属性写入位置、`backend/main.py` 球员读取入口，以及相应球员数据接口与面板。

### A1：停止预测写入实际档案

- 将 `attribute_update_suggestions` 保留为建议或预测；生成、修订报告时不自动应用到当前档案。
- 同时处理 Coach 工具列表中的写入能力，避免仅删除末尾自动写入、却保留另一条模型写入路径。
- 此任务只收紧事实写入边界，不重写训练提示词、身价模型或执行图。
- 验收：首次运行、局部修订、报告失败、人工拒绝或未确认时，实际球员能力均不因预测而改变。

### A2：统一球员读取与导入边界

- API 和 Agent 从同一数据访问入口读取，不再一个固定读仓库目录、另一个读配置目录。
- 初期可以继续使用 JSON；先建立接口和单球员一致性，再决定存储实现。
- 为接入增加生涯、分支、球员标识，以及来源、游戏内时间、采集时间、数据版本。
- 导入只接受校验后的观察记录。缺失值是未知，不默认补成 0、正常或低风险。
- 同一数据导入需能防重；更新需避免留下不完整文件，并明确失败后的原记录可用性。
- 验收：切换数据目录后，API 与 Agent 一致；两份存档隔离；重复导入不增加重复记录。

## 4. B：执行、协作与审查正确性

主要范围：`agents/base.py`、各专业 Agent 的输出解析与兜底、`agents/reviewer.py`、`agents/document.py`、`graph.py`、`loop_contracts.py`，以及公开状态映射和对应 UI。

分阶段实施见 [B 方向 Codex 任务书与开发指南](./B方向_执行协作与审查正确性_Codex任务书_2026-10-01.md)；未指定子任务时默认只执行 B1.1，B3 在 A2.1 的只读上下文与版本接口稳定后开展。

### B1：确定有效结果和失败语义

- 明确区分有效结果、缺少输入、技术失败、未完成审查和有条件的部分结果。
- 拒绝用固定训练、营养、职业建议填补模型输出失败。
- Reviewer 不可用时保留“未经审查”事实，不转换为普通 PASS。
- 报告生成失败时保留有效分析，但不宣称已生成最终报告。
- 有效的代码计算和工具观察可保留；保留数据不等于补出完整建议。
- 从内部结果到公开 API、任务界面建立一致映射。新增状态或字段需显式评审，不能只更改一层枚举。
- 验收：同一失败在子任务、任务、审查面板和报告入口中表达一致；demo 正常成功路径仍可用。

### B2：校验输出与工具循环退出

- 对专业输出建立字段、类型和必要业务约束校验，不能仅凭可解析 JSON 或非空文本判为完成。
- 工具循环达到预算时，不能返回最后一个 ToolMessage 充当模型结论。
- 工具失败需要保留类型和上下文，并判断是否影响任务成立；重试有上限。
- 明确报告正文的最终检查边界，避免审查只覆盖支撑材料却宣称已审核最终内容。
- 验收：无效 JSON、缺字段、空输出、工具失败和循环耗尽分别形成真实结果状态。

### B3：打通依赖结果与失效机制

- 首轮专业任务也得到所需的上游结果，而不是等到 Revision 才获得依赖上下文。
- 上下文携带关联证据、来源版本和适用约束，不传入全部历史状态。
- 结果复用需检查输入状态、依赖结果版本和相关约束。不能只比较 capability 与 goal。
- 上游结果变更时，明确下游失效范围；不扩大到无关任务。
- 验收：上游唯一事实确实进入下游调用；依赖改变后下游不能沿用旧 completed；无关有效结果保留。

### B4：收敛重复状态（后续整理）

- 在 B1–B3 稳定后确定唯一权威状态，逐步收敛新旧 Plan、Review、Hypothesis 和结果表达。
- 迁移与兼容通过边界适配处理，不同时重写全部 Agent。
- 此整理不是首次游戏接入的硬前置；若已有双写机制能可靠工作，可后移。
- 验收：兼容路径有明确范围；既有 checkpoint 和界面数据能读取，或有明确迁移与拒绝策略。

## 5. C：会话恢复与生涯记忆

主要范围：`utils/sessions.py`、`app.py`、`backend/service.py`、消息与记忆访问接口，以及上下文构建位置。

分阶段实施见 [C 方向 Codex 任务书与开发指南](./C方向_会话恢复与生涯记忆_Codex任务书_2026-10-01.md)。当前 A/B 接口可用后，默认从 C1.1 开始；C 拥有后续任务入口和记忆检索，行动/反馈的权威记录归 E。

### C1：明确恢复与延续的行为

| 用户操作 | 推荐语义 |
| --- | --- |
| 补充暂停任务所需信息 | 恢复同一任务 checkpoint，继续其执行 |
| 查看完成任务 | 读取历史结果和对话，不重新执行 |
| 解释旧报告 | 当前任务上下文中的对话回答 |
| 根据新比赛或新约束调整方案 | 新建有来源关联的后续任务，使用最新状态 |

- 修正 CLI “恢复历史会话”的承诺：要么提供实际恢复，要么明确它是引用历史的新任务。
- 完成任务后的追问，需要区分解释与重新评估；后者不能只走一次报告问答。
- 旧任务引用原数据快照；新任务使用最新状态，不能把两者混同。
- 此阶段明确语义，不先重构全套长期记忆存储。
- 验收：任务身份和上下文来源可解释；暂停恢复、查看历史、问答和新分析各走正确路径。

### C2：建立有来源的长期记忆

- 保存长期目标、重要建议、明确选择、后续结果与更正记录，关联任务和生涯。
- 将 E 方向记录的行动与反馈作为明确输入，不从“AI 建议了”推断“玩家做了”。
- 根据相关性、游戏内时间、有效范围和版本选择记忆。
- 不要求每个 Agent 都持有私有对话缓存；清理或接通现有滑动窗口接口要以真实上下文需求为准。
- 验收：新任务能取到相关旧决策；无关存档、过期反馈和已被更正的事实不污染建议。

## 6. D：游戏接入与采集适配

主要范围：独立游戏适配目录、采集工具和原始样本；正式导入仅调用 A 提供的接口。

分阶段实施见 [D 方向 Codex 任务书与开发指南](./D方向_游戏接入与采集适配_Codex任务书_2026-10-01.md)。默认从 D0.1 的有限只读调查开始，未验证目标版本与个人生涯兼容前不预设工具或采集字段。

### D0：本机只读可行性调查

- 确认 PES 2021 / FC 26 的安装版本、平台、补丁和工具环境。
- 列出个人生涯模式实际能读取的字段，分别标记已验证、待验证和不可获取。
- 对比存档副本解析、已有导出能力、进程内工具与屏幕识别等候选方式；不预设必须安装某工具。
- 特别区分经理生涯和个人生涯；已有经理生涯导出不能直接证明个人生涯兼容。
- 不安装或启动新接入工具；调查先产出候选方式、限制和具体试验方案。工具安装与游戏运行在后续明确范围内实施。
- 验收：能据实际数据覆盖和接入影响选定首个游戏；若不可行，应给出具体阻碍，不强行造适配器。

### D1：独立采集验证

- 围绕一个测试存档采集球员快照与连续比赛记录，保存原始数据和采集环境版本。
- 先离线读取样本，不接 Agent，不写当前球员档案。
- 验证游戏继续正常运行、采集错误可停止、字段可与游戏界面核对。
- 如果使用进程内工具，整体运行影响需单独验证；“导出脚本只读”不代表宿主工具完全无侵入。
- 验收：字段确实来自目标球员和目标生涯；未知字段被保留；没有假定完整比赛统计已可用。

### D2：接入统一数据层

- 原始数据经校验与版本化映射转换为球员观察和生涯事件，再导入 A。
- 分开记录采集时间和游戏内时间；检测旧存档加载、时间倒退、比赛重踢和生涯切换。
- 时间倒退或重复比赛有歧义时，不自动覆盖历史；显式选择分支或待确认状态。
- 不把游戏专用内存地址、CSV 列或 Lua API 泄漏进 Agent prompt 与 Graph State。
- 验收：重复导入不重复、两个生涯隔离、回档不混写；采集端中断不产生伪造观察。

## 7. E：球员业务闭环与交互

主要范围：建议、行动和反馈对象，相应 API、界面与后续任务入口。通常是一个功能内的前后端联合小改动。

分阶段实施见 [E 方向 Codex 任务书与开发指南](./E方向_球员业务闭环与交互_Codex任务书_2026-10-01.md)。E1.1 已完成，下一轮为 E1.2，详见第 14 节；建议、选择、执行、观察和评估分别记录，后续分析调用 C 的应用接口。

### E1：记录建议与玩家选择

- 建议具有标识、适用状态和预期观察窗口；支持采纳、拒绝、暂缓。
- 记录玩家能在游戏中实际执行的选择；游戏不支持的内容明确作为可选叙事，不伪装成可验证操作。
- 采纳不等于已执行；由实际数据或玩家明确反馈确认执行。
- 有些决策无法自动观察，允许玩家提供有来源的说明，不把自动采集设为所有行动的必要条件。
- 验收：能回答“系统建议了什么、玩家选了什么、是否实际发生”。

### E2：反馈驱动后续任务

- 将后续比赛、属性变化或玩家反馈与建议关联，评估目标是否达到或是否有新约束。
- 区分观察到的变化与因果判断；一次表现变好不能证明建议导致了提升。
- 缺少可比较数据时说明无法评估，不生成“已有效”的结论。
- 发起关联旧建议的新任务，使用最新事实和相关长期记忆。
- 验收：至少贯通连续数场的“建议 → 选择 → 观察 → 调整”，而非只重复生成报告。

## 8. F：领域规则与建议质量

主要范围：专业 Agent 的规则与计算模块、知识检索、引用证据和场景评估；不改任务调度策略。

### F1：游戏指标与风险维度

- 区分游戏原始属性、标准化解释和模型推断，不先把 PES 与 FC 属性强行视为相同。
- 风险先分为比赛可用性、职业发展和决策风险；逐项标明依据、缺失信息和适用范围。
- 游戏未提供的真实 RPE、训练负荷等指标不补造；不沿用无法解释的统一风险分。
- 营养、恢复等角色按可观察、可执行的游戏能力适配；暂时不能参与闭环的内容可保留为明确的辅助叙事。
- RAG 引用绑定具体任务和工具调用，索引绑定知识与模型版本；检索不足可被识别。
- 验收：每个关键风险结论能追溯到观察或明确规则；无法判断与低风险有不同表达。

### F2：身价与成长预测

- 游戏已显示的身价与能力变化记为事实；未来收益记为预测。
- 根据目标游戏版本的样本评估预测，不以另一款游戏的规则直接换算。
- 先用实际字段提供准确解释，再考虑统计或规则预测；样本不足时不宣称已校准。
- 验收：估计有适用版本、依据和误差评估；预测不更新事实。

## 9. G：运行可靠性

主要范围：服务运行、任务提交与恢复、存储生命周期、模型调用配置和运行指标。

### G1：时限、取消与重复提交

- 定义模型、工具和整任务的时限与有限重试策略。
- 区分界面停止等待与后台真正停止；同步线程无法即时取消时应明确边界，并阻止后续提交效果。
- 增加重复提交与重复续跑防护，明确排队行为。
- 成本和耗时指标覆盖失败、追问与重试，不能只统计成功节点。
- 验收：超时或取消后不长期显示执行中；重复请求不重复执行行动或写入记录。

### G2：重启恢复、备份与迁移

- 区分可恢复暂停、执行中断与已完成任务；执行中恢复不能盲目重放有副作用的步骤。
- 覆盖球员事实、任务快照、报告与内部 checkpoint 的备份和恢复，验证同一生涯的一致性。
- 明确单进程运行约束，避免 CLI 与 Web 同时无协调地写同一档案。
- 公开部署需要的权限控制单独安排，不混入本地单用户 MVP。
- 验收：服务重启和备份恢复后，任务与球员状态可解释；发生中断时不冒充成功。

## 10. 方向之间的最小接口

接口先定义职责与语义，字段名和具体实现再通过小范围设计确定。保持同进程模块即可，暂不引入微服务或消息中间件。

| 接口 | 负责方向 | 消费方向 | 必须一致的语义 |
| --- | --- | --- | --- |
| 球员观察与状态访问 | A | B / C / D / E / F | 生涯、分支、球员身份；来源、游戏内时间和版本；事实与未知 |
| 游戏原始快照 | D | D 的转换层 | 采集环境、原始字段、完整性；不直接当领域状态使用 |
| 执行输入与结果 | B | C / E / G / UI | 有效输出、缺少输入、技术失败、审查状态；依赖与输入版本 |
| 任务恢复与延续 | C | UI / E / G | 恢复原执行、查看旧结果、解释与新评估分别定义 |
| 建议、选择和反馈 | E | C / F | 建议、采纳、实际执行和观察结果不能互相替代 |
| 运行控制与指标 | G | B / C / UI | 取消、超时、重试、排队与恢复状态一致 |

跨方向需要修改共享接口时，先完成一个接口变更小任务和兼容映射，再分别实现消费方。不能让两个方向分别定义不同的失败状态或球员版本。

## 11. 实施顺序与里程碑

### 阶段 0：明确接口和研究游戏

- 确认上表的最小语义，不一次设计完所有未来字段。
- D0 可与 A1、B1 的设计独立推进；游戏调查不会修改执行图。
- 阶段结果：首个游戏候选、接入限制、事实写入规则和失败处理约定。

### 阶段 1：先得到可信的工作台

建议串行完成：A1 → B1 → B2 → A2 → B3。

- A1 先阻止预测污染，任务规模小、可独立验收。
- B1–B2 先修复输出与失败处理，不叠加长期记忆大改。
- A2 为正式游戏导入提供稳定访问边界，并向 B3 提供输入数据版本。
- B3 随后修复依赖传递与结果复用，复用 A2 的版本语义。
- D1 在 D0 通过后可独立采集样本，不导入生产球员数据。
- 里程碑 M1：无预测写入；无固定答案冒充成功；依赖上下文和复用正确。

### 阶段 2：获得可维护的游戏事实

- A2 + D1 通过后进行 D2。
- 同期可完成 C1 的会话行为和 F1 的指标解释；涉及 B 共享结果契约的改动需等其稳定。
- 里程碑 M2：真实测试存档可连续导入；生涯隔离、防重和回档行为明确；系统不猜补数据。

### 阶段 3：形成生涯业务闭环

- E1 先明确建议、选择和反馈接口；C2 以该接口保存与检索长期记忆。
- 在 A2、B3、C1、D2 可用后完成 E1，再贯通 C2 与 E2。E1 可使用确定性样本验证接口，但这不计为真实游戏闭环完成。
- F2 在得到足够观察样本后开展，不作为 E2 的强制前置。
- 里程碑 M3：一个实际生涯中至少连续十场记录，包含至少一次明确采纳/拒绝，以及基于后续结果的新建议。

### 阶段 4：达到本地 production-like MVP

- G1 可在 B1 结果语义稳定后逐项提前实施；G2 在 C1 和数据边界明确后实施。
- B4 的重复状态整理按风险和迁移成本安排，不与其他方向同时改共享状态。
- 里程碑 M4：M1–M3 均通过，且超时、取消、重启、重复提交、备份恢复都有明确行为。
- M4 不要求游戏写回、多用户、云部署、自动交易或复杂预测模型。

## 12. 改动冲突与任务拆分规则

共享文件是主要风险，技术分层本身不能消除冲突：

| 共享区域 | 改动协调规则 |
| --- | --- |
| `graph.py` / `loop_contracts.py` | B 负责权威执行语义；C / G 通过小范围适配接入，不同时重写状态 |
| `backend/service.py` | B 的结果发布、C 的延续行为、G 的运行控制分任务串行落地 |
| 公共 DTO / 事件 / 前端类型 | 由引入功能的方向完成端到端变更，其他任务先复用稳定版本 |
| Coach 与数据库工具 | A1 只处理事实写入；F 后续改领域规则；不要一起大改训练逻辑 |
| 数据访问与导入 | A 负责统一访问，D 负责游戏映射；采集脚本不自行修改 `memory/player.json` |

每个实施任务应具备以下内容：

1. 一个具体问题和一个可观察的结果。
2. 明确文件范围、依赖接口和本轮不扩展的职责。
3. 可独立验收的正常路径与相关失败路径。
4. 数据影响、兼容措施及撤回代码后的数据处理方式。
5. 变更后的检查结果；采用替身还是实际游戏/模型必须注明。

一个方向内的任务仍要拆小。例如 B1 不应同时承担所有专业输出校验、取消、长期记忆和 UI 重设计。规模取决于验收边界，不按预设“一轮必须完成整条方向”推进。

未来若分开工作区或聊天，任务只携带所属方向、依赖接口、验收标准和当前版本。不重复发送整份重构愿望，也不让多个任务同时修改共享核心文件。本文件没有创建新聊天或派发并行任务。

创建后续 worktree 前，确认起始提交包含已完成的 A/B 改动和所需指南。Git worktree 不自动复制当前未提交修改或未跟踪文件；从旧基线开始会丢失新接口，不能据此重复实现或覆盖已完成工作。
